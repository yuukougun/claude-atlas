    - **何が分かるか**：AI に書かせたテストは、バグ入りの挙動を正解にしたり、コードを壊しても落ちなかったりする。それを見分けて確かめる手が選べる。

AI に書かせたテストの落とし穴は、「通る」ことと「バグを見つける」ことが別の性質である点にある。Claude はテストを速く大量に書ける。ただし、そのテストが何を守っているかは、書かせた側が確かめる必要がある。このページは、落とし穴の形 2 つと、テストそのものの強さを確かめる手と、テストのないコードに足させる頼み方を扱う。

## 今の挙動を正解として固める {#pinning-bugs}

Claude に「このコードにテストを書いて」と頼むと、期待値を今のコードが返す値から取りやすい。コードにバグがあっても、バグ入りの出力がそのまま正解としてテストに残る。そのテストは通るので、緑の表示がバグの不在の証拠に見える。

次の例では、うるう年の 2 月が 28 日のままになっている。

```python
def days_in_month(year, month):
    if month == 2:
        return 28  # うるう年を見ていない
    return 30 if month in (4, 6, 9, 11) else 31

def test_leap_february():
    assert days_in_month(2024, 2) == 28  # 実装の出力を写しただけ
```

期待値の出どころが実装しかないので、このテストは実装と必ず一致する。バグを直すとこのテストのほうが落ち、直した側が悪く見える。

研究にも同じ向きの報告がある。人が書いたバグ入りのコードを対象に、LLM を使うテスト生成ツールの設計を調べた研究（Mathews と Nagappan、2024 年）である。現在のコードで失敗する生成テストを捨てる設計は、バグを暴くテストを捨て、バグを正当化するテストを残すと指摘した。対象は Claude に限らない生成ツールで、現行の Claude にそのまま当てはまるとは限らない（根拠：中）。

同じ型の失敗は、Claude が通すことを目標にしたときにも起こりうる。落ちたテストは、期待値を実装に合わせれば消えるからである。

実務家の報告にも、Claude が書く初期テストはもっともらしく見えるが実装とかみ合わないことがあり、テストを弱めたり変えたりして通そうとすることもある、というものがある（根拠：弱。単独の経験談）。テストの変更は特に注意して読む、という結論は共通している。

防ぎ方は 2 つある。1 つ目は、期待値を実装ではなく仕様から決めること。その手順は <!-- link:begin tests-first#steps -->[テストを先に書かせる › 手順](tests-first.md#steps)<!-- link:end --> にある。2 つ目は、通すためにテストが書き換えられる経路をふさぐこと。依頼と鍵の層は <!-- link:begin protect-tests#why -->[テストを守る（改ざんを防ぐ） › なぜテストが書き換えられるか](protect-tests.md#why)<!-- link:end --> にある。

## 通るだけのテスト {#weak-tests}

通るだけのテストとは、実行されても何も確かめていないテストのことである。カバレッジは、テストが通った行や分岐の割合を測るだけで、その結果を検査しているかは測らない。たとえば `assert result is not None` や「例外が出ないこと」だけを確かめるテストは、行を実行するのでカバレッジを稼ぐが、戻り値が正しいかは見ない。

カバレッジを目標にして「カバレッジを上げて」と頼むと、この種のテストが増えやすい。数値の指標を渡すと、その指標を満たす最も安い方法が選ばれる、という見立てである（根拠：弱）。

極端な例が、LLM によるテスト生成を扱う論文（MutGen、2025 年）の要旨に挙がっている。カバレッジが 100% なのに、ミューテーションスコアが 4% だったテストスイートがある（根拠：弱。単一の例で、一般化しない）。ミューテーションスコアは、コードにわざと小さな変更（変異）を入れたとき、テストが落ちて検出した割合である。この例では、変異の大半がテストをすり抜けた。

プロパティテストにも似た穴がある。入力を自動で作るため、既定の乱数では、バグが起きる狭い領域にほとんど届かないことがある。PBT-Bench（2026 年）は、既定の戦略ではほぼ当たらない領域にバグを仕込んだ課題で、8 つの LLM のプロパティテストの力を比べた。結果はモデルごとに差が大きかった（根拠：中。対象は Claude に限らない）。プロパティテストの頼み方は <!-- link:begin property-based-tests -->プロパティテストを書かせる<!-- link:end --> にある。

見た目がそろっているテストは、品質の証拠にならない。理由は <!-- link:begin looks-are-not-quality -->[見た目は品質の証拠ではない](looks-are-not-quality.md)<!-- link:end --> にある。

## テストの強さを確かめる {#test-strength}

テストの強さは、「コードを壊したときに落ちるか」で確かめる。通ることは、テストが書けたことしか示さない。ここでいう変異とは、コードにわざと入れる小さな変更のことで、ミューテーションテストは、変異を入れてテストが落ちるかを調べる方法である。確かめる手は次のとおり。

| 確かめる手 | 向く疑い | 手間 |
| --- | --- | --- |
| 手で壊す | 重要な関数のテストが、実際に何かを守っているか | 少ない |
| ミューテーションテストの道具 | 多数のテストのうち、弱い所はどこか | 実行に時間がかかる。対象を絞る |
| 期待値を人が手で計算する | 期待値が実装の写しになっていないか | 要の数件だけなら少ない |
| 遅くて確かな解と比べる | 正解が分かる処理で、入力を変えても合うか | 比べる解が要る |
| プロパティで確かめる | 例を並べても見つからない誤りがないか | 性質を決める手間 |

手で壊す方法は、コードを小さく壊してテストを実行し、落ちるかを見る。壊し方は、比較演算子の反転、境界の値を 1 ずらす、分岐を消す、などである。落ちないなら、そのテストはその箇所を守っていない。

Claude にやらせるときは、作業用のブランチの上で壊させ、落ちた出力を見せさせる。最後に元へ戻させ、`git diff` で変更が残っていないことも見せさせる。依頼の形は、後ろの雛形にある。

ミューテーションテストの道具は、この壊す作業を言語ごとに自動で行う。出力されたスコアは、テストの強さの目安であって、正しさの保証ではない。スコアの低い所のテストを足させ、足したテストが変異を検出するかを再度確かめる。

期待値を人が手で計算する方法は <!-- link:begin test-the-verifier#hand-calculated -->[検証器そのものを確かめる（red/green・手で計算したケース） › 手で計算したケース](../eval/test-the-verifier.md#hand-calculated)<!-- link:end --> にある。わざと壊した検証器で落ちるかを確かめる方法は <!-- link:begin test-the-verifier#broken-copy -->[検証器そのものを確かめる（red/green・手で計算したケース） › わざと壊した検証器で落ちるか](../eval/test-the-verifier.md#broken-copy)<!-- link:end --> にある。遅くて確かな解と比べる手順は <!-- link:begin differential-testing#steps -->[答えの分かる遅い解と比べる（差分テスト・オラクル） › 手順](../eval/differential-testing.md#steps)<!-- link:end --> にある。テストを人が読むときに見る箇所は <!-- link:begin diffs-humans-must-read#red-flags -->[人間が読むべき差分の箇所 › 赤信号の一覧](diffs-humans-must-read.md#red-flags)<!-- link:end --> にある。

!!! example "判断例：全部通った 20 件のテストをどこまで確かめるか"
    - **状況**：Claude が決済の計算関数に 20 件のテストを足した。すべて通り、カバレッジも上がった。
    - **迷う候補**：20 件の期待値を人がすべて読む。または、コードを壊して落ちるかを Claude に確かめさせ、期待値を読むのは要の数件にする。
    - **選んだもの**：後者。先に Claude に壊して確かめさせ、落ちなかった壊し方にはテストを足させる。そのうえで、金額の丸めと境界の 3 件だけ、人が期待値を手で計算して読む。
    - **理由**：全件を読む時間は大きく、読んでも「落ちるか」は分からない。壊す確認は機械的にでき、弱いテストの場所を絞れる。要の期待値は実装の写しになりやすいので、人が読む価値がある。

## テストのないコードに足させる {#add-to-untested}

テストのない古いコードに足させるときは、任せる範囲が広く、落とし穴も重なる。古いコードには気づかれていないバグがあるかもしれず、現在の挙動が仕様とは限らないからである。

公式の手順は、テストのない関数を見つけ、雛形を作り、境界値とエラー条件を足し、実行して失敗を直す流れである（Common workflows）。Claude は既存のテストの書き方に合わせられる。

この流れに、落とし穴への備えを足す。足すものは次の 3 つである。

- 期待値の根拠を分けさせる。「仕様から」「呼び出し元から」「コードの出力から」のどれかを、期待値ごとに挙げさせる。「コードの出力から」だけのものは、人に確認させる。
- 今の挙動を記録するだけのテストと、正しさを確かめるテストを区別する。前者は、リファクタリングで挙動が変わっていないことを確かめる安全網としては使える。正しさの証拠としては使わない。名前やコメントで区別させる（この辞典の推奨）。
- 壊して落ちることを、出力つきで見せさせる。通ったことだけの報告で終わらせない。

Before はこう頼む場合である。

> このモジュールにテストを書いて。

After は、同じ依頼に次を足す。既存のテストの書き方に合わせる指定、期待値の根拠の分類、壊して落ちることの確認、元に戻したことの確認、仕様と食い違うときの止まり方、である。頼み方の全体は次の雛形にある。

<!-- gen:begin snippet pitfalls-of-ai-written-tests/add-tests -->
<!-- textlint-disable -->

??? example "雛形：既存のテストに合わせて足させ、壊したコードで落ちることを見せさせる依頼"

    ```text
    次のコードにテストを足す。

    対象：<ファイルまたは関数のパス>
    テストの置き場所：<既存のテストファイルのパス>
    実行コマンド：<リポジトリですでに動くテストの実行コマンド>

    進め方：
    1. 既存のテストを読み、書き方（フレームワーク・命名・アサーションの形）に合わせる。
    2. 対象の挙動を書き出し、期待値の根拠を「仕様から」「呼び出し元から」「コードの出力から」のどれかに分ける。根拠が「コードの出力から」だけのものは、テストにせず、私に確認する。
    3. 境界値とエラー条件を含めてテストを書き、実行して全部通ることを確かめる。
    4. 対象のコードを、作業用のブランチの上でわざと壊す（比較演算子を反転する、境界の値を 1 ずらす、分岐を消す、の 3 か所）。壊すたびにテストを実行し、落ちた出力を貼る。落ちなかった壊し方には、それを落とすテストを足す。
    5. 壊したコードを元に戻し、`git diff` で対象のコードが変わっていないことを見せる。

    変えてはならないもの：対象のコード、既存のテスト。
    止まって報告する条件：コードの挙動が仕様と食い違って見えるとき。テストを挙動に合わせて通さず、止まって食い違いを報告する。
    ```

    動作を確かめていない雛形。

## 何に効くか {#what-it-helps}

このページの手は、原理「確かめる」を、テストの強さに当てはめたものである。Claude 側の原因では「確かめていない」に効く。テストが通ったという報告は、確かめた結果に見える。しかしテストそのものが確かめられていなければ、その緑は何も確かめていない。

- 今の挙動を固めたテストには、期待値を仕様から決めることが効く。
- 通るだけのテストには、壊して落ちるかを見ることが効く。
- 足させたテストが強いかどうかには、根拠の分類と、壊す確認が効く。

効かない場面もある。仕様自体が間違っていれば、仕様どおりのテストも間違いを守る。ミューテーションの確認は、入れた壊し方の範囲でしか強さを示さない。こうした穴は、完了の定義と、人が読む確認で補う。完了の定義の効き方は <!-- link:begin define-done#what-it-helps -->[「完了」を定義して渡す › 何に効くか](define-done.md#what-it-helps)<!-- link:end --> にある。

## 誤解 {#misconceptions}

- 「カバレッジが高ければテストは強い」：カバレッジは、実行された行や分岐の割合である。期待値を検査しているかは測らない。
- 「全部通ったのだからバグはない」：テストが固めた挙動は、正しいとは限らない。期待値が仕様に照らして決められているかを見る。
- 「ミューテーションスコアが高ければ正しい」：スコアは、入れた変異を検出した割合である。仕様の間違いや、変異にない種類の誤りは見つからない。
- 「AI にテストを書かせるのは危ないので、やめたほうがよい」：足させること自体は有効である。落とし穴を知ったうえで、確かめと組み合わせて任せる。
