望む形で書くとは、してほしくないことを禁止で並べる代わりに、代わりにしてほしいことを肯定の文で書くことである。公式の指針も、何をするかを書き、何をしないかは書かない形を勧めている。ただし、例外が 1 つもない禁止は、言葉を重ねても必ず守られる保証にならない。その禁止は、書き方ではなく仕組みで止める。

## 禁止を望む形に書き換える {#rewrite}

禁止を望む形に書き換えるとは、「何を避けるか」の裏返しではなく、「代わりに何をするか」を主語にして書き直すことである。公式の Prompting best practices は、出力の形の指示で、`Do not use markdown` と書くより、滑らかにつながる段落で書くよう求めるほうがよいとしている（2026-10-29 に確認）。Prompting Claude Opus 5 にも、望む文体は正の例で示すほうが「〜するな」より効く、という趣旨の記述がある（2026-10-29 に確認）。

書き換えは 3 つの手順で進める。

1. 禁止の裏にある狙いを一言で書く（読みやすさ、既存の方式に合わせる、など）
2. 狙いを満たす行動を、動詞で書く（「段落でつなげて書く」「実際のデータベースに接続して書く」）
3. 行動が決まらないときは、手本を 1 つ見せる

同じ依頼を、禁止だけの書き方と、望む形の書き方で並べる。

```text
Before（禁止だけ）
README の説明を書いて。markdown の見出しや箇条書きを使わないで。専門用語を使わないで。長くしないで。

After（望む形）
README の冒頭に置く説明を書いて。初めて来た開発者が読む。
段落でつながる文章で、3 文にまとめる。1 文目に「何のためのツールか」を書く。
専門用語は、初めて出る所で 1 文だけ言い換える。
```

もう 1 つ、開発の例を示す。

```text
Before（禁止だけ）
テストでモックを使わないで。console.log を残さないで。

After（望む形）
テストは、`docker compose` で立てる test 用のデータベースに実際に接続して書く（モックだと、移行の不具合を見逃したため）。
作業が終わる前に、デバッグ用に足した出力を消して、消したことを報告に 1 行書く。
```

After で足したものは 3 つある。1 つ目は、代わりにする行動である（段落で書く、実際のデータベースに接続する、デバッグ用の出力を消して報告する）。2 つ目は、行動の具体形である（3 文にまとめる、1 文目に何を書くか、どのデータベースか）。3 つ目は、狙いか理由である（初めて来た開発者が読む、モックだと移行の不具合を見逃した）。理由の書き方は <!-- link:begin give-reasons#what-changes -->[理由を添える › 理由を添えると何が変わるか](give-reasons.md#what-changes)<!-- link:end --> の持ち分で、ここでは繰り返さない。

禁止の形がすべて悪いわけではない。「本番の認証情報を出力に書かない」のような、守りたい境目そのものは、禁止で書いてよい。そのときも、書いた禁止の隣に、代わりの扱い（「伏せ字にして書く」）を並べると、行動が決まる。

## 何が変わるか {#what-changes}

望む形に書き換えると、出力の変わる点が 3 つある。

- **出力が目標に寄る**：「段落で 3 文」と書くと、Claude は何を出せばよいかが分かる。禁止だけの依頼では、避ける形は分かっても、出す形は推測になる。
- **ぎこちなさが減る**：禁止を重ねると、Claude は禁止の全部を避けるために、不自然な言い回しや回りくどい文を選ぶことがある。望む形が決まっていれば、その形に向かって書ける。
- **禁じた語が出にくくなる**：「使うな」と書くと、禁じた語を禁止の文の中に書くことになる。望む形なら、その語を書かずに済む。

変わる程度は、モデルや依頼の長さで違う。どれも経験則の域を出ない（推論・実践例なし）ので、自分の依頼で Before と After を並べて観察する。並べ方は、このページ末尾の「効かない場面とやりすぎ」に書いた。

## なぜ望む形のほうが守られやすいか {#why}

理由は 2 つ考えられる。1 つは、禁止だけでは「代わりに何をするか」が Claude の側から見えないことである。避ける形が分かっても、出す形が決まらないので、残りを推測で埋める。もう 1 つは、禁止の文にも禁じた語が書かれるので、その語が文脈に載ることである。前者は公式の指針が示す方針と整合する。後者は、この辞典の推論で、公式の説明ではない（推論・実践例なし）。

比喩で言えば、道順を聞かれて「右には曲がらないで」とだけ答える形である。聞いた側は、曲がってはいけない方向は分かるが、どこへ行けばよいかは分からない。「次の信号を左へ」と言えば、行く先が決まる。禁止は境目を示し、望む形は行き先を示す。

禁止を足すほど出力がぎこちなくなる症状は、行き先が決まらないまま、境目だけが増えていく形で起きる。強調語を重ねても直らない理由は <!-- link:begin emphasis-words#why-not -->[強調語（IMPORTANT・必ず）の現在 › 強調で直らない二つの理由（長すぎる・例外がない）](emphasis-words.md#why-not)<!-- link:end --> にある。

## 書き換えを任せる雛形 {#templates}

禁止の項目が多いときは、書き換えそのものを Claude に頼める。次の雛形は、禁止を 3 つの区分に振り分けさせる依頼である。3 つ目の区分は、判断を含む規則で、禁止をやめて基準に直す。

<!-- gen:begin snippet say-what-you-want/rewrite-negatives -->
<!-- textlint-disable -->

??? example "雛形：禁止を望む形に書き換えさせる依頼"

    ```markdown
    次の指示文には「〜するな」「〜しない」の形の禁止が並んでいる。1 つずつ次の 3 つに振り分けて、書き直してほしい。

    1. 望む形に書き換えられるもの：代わりにしてほしい行動を主語にして、1 文で書き直す。理由が分かるものは理由を添える。
    2. 例外が 1 つもなく、機械で判定できるもの：書き直さず、「権限のルールかフックで止める候補」として別に並べる。
    3. 判断を含むもの：禁止をやめて、判断の基準と、迷ったときに止まって相談する条件に書き直す。

    書き直した文だけを返し、元の指示文は繰り返さない。

    --- 指示文 ---
    （ここに、今の指示文か CLAUDE.md の禁止の項目を貼る）
    ```

    動作を確かめていない雛形。

<!-- textlint-enable -->
<!-- gen:end snippet say-what-you-want/rewrite-negatives -->

返ってきた文を、そのまま使わずに読む。望む形が、元の禁止の言い換えにすぎないとき（「冗長にしない」を「簡潔にする」と言い換えただけなど）は、動詞と具体形を自分で足す。

## 例外のない禁止は仕組みへ（二層） {#two-layers}

二層とは、禁止を、Claude に読んで判断させる層と、仕組みで必ず止める層に分けることである。プロンプトや CLAUDE.md に書いた禁止は、Claude が読んで判断する「お願い」にとどまる（<!-- link:begin request-vs-lock#two-layers -->[お願いと鍵（決定論的か、非決定論的か） › 二層で書く](../basics/request-vs-lock.md#two-layers)<!-- link:end -->）。望む形に書き換えても、お願いであることは変わらない。書き方で守られやすくなるだけで、必ず守られる保証にはならない。

例外が 1 つもなく、機械で判定できる禁止は、言葉を重ねない。分け方は次のとおりである。

- **仕組み（deny ルールかフック）**：例外を許さない禁止を強制する。書き方は <!-- link:begin permission-rules#minimal -->[権限ルール（allow・ask・deny） › 最小の使い方](../enforce/permission-rules.md#minimal)<!-- link:end --> にある
- **CLAUDE.md**：その禁止の理由と、止まって相談する基準だけを書く。判断を含む規則は、お願いのままにする
- **依頼文**：今回の作業に固有の、望む形の指示を書く

フックが止めるときに返す文は、Claude に届く指示でもある。「禁止された」とだけ返すと、Claude は代わりの手段を推測する。止めた理由と、代わりにしてほしい手段を、望む形で書いて返すと、止められたあとの動きが決まる。

同じ二層の考え方は、触ってよい範囲の指定にも使える（<!-- link:begin state-the-scope#two-layers -->[範囲を伝える（やらないこと） › 例外を許さない範囲は仕組みで縛る（二層）](state-the-scope.md#two-layers)<!-- link:end -->）。このページは禁止の書き方の話で、範囲の話はそちらが持つ。

どの禁止を仕組みへ移すかの判断は、<!-- link:begin when-to-lock#signals -->[お願いを鍵に移す判断 › 鍵に移す合図](../enforce/when-to-lock.md#signals)<!-- link:end --> の合図で見る。同じ注意を 2 回した、強調しても破られた、というときが移す合図になる。

面ごとに、使える手段は違う。

=== "アプリ"
    望む形の指示を、依頼の本文とプロジェクトの指示に書く。アプリで禁止を仕組みで止める手段は、この辞典では未確認である。

=== "Claude Code"
    望む形の指示を、依頼の本文と CLAUDE.md に書く。例外を許さない禁止は、deny ルールかフックで止める。

=== "API"
    望む形の指示を、システムプロンプトと各依頼に書く。ツールを実行するのは自分のコードなので、禁止する操作を拒否する処理は、そのコードの側に置く（推論・実践例なし）。

!!! example "判断例：「デバッグ出力を残すな」をどう書くか"
    - **状況**：開発の依頼のたびに、デバッグ用の出力がコードに残る。CLAUDE.md には「console.log を残さないこと」と書いてある。
    - **迷う候補**：CLAUDE.md を「作業の終わりにデバッグ用の出力を消して、消したことを報告する」という望む形に書き換える。あるいは、フックで残った出力を検査して止める。
    - **選んだもの**：まず前者に書き換え、書き換えたあとも同じ注意を 2 回するようなら、後者を足す。
    - **理由**：残してよい出力（本番のログ）と残してはいけない出力（デバッグ用）の見分けに判断が要るので、最初から機械判定には向かない。書き換えで足りないなら、検査できる形（特定の呼び出しの有無）に絞ってフックへ移す。

## 何に効くか {#effects}

望む形で書くことは、原理の「見せる」と「縛る」に関わり、防ぐ原因は「見えていない」と「縛っていない」である。

- **見せる**：代わりにしてほしい行動と手本を書くのは、Claude の側から見えない行き先を見せる手である。原因の「見えていない」を防ぐ。
- **縛る**：例外を許さない禁止は、書き方を整えても、お願いのままである。deny ルールやフックは、効く範囲と条件の中で毎回必ず効く。原因の「縛っていない」を、仕組みで補う。

出力の形を指定するときは、頼む文の書き方そのものも出力に映る（<!-- link:begin output-shape#mirror -->出力の形と分量を指定する › 頼む文の書き方が出力に映る（準備中）<!-- link:end -->）。禁止を並べた文より、望む形で書いた文のほうが、望む出力の書き方に近い。

## 効かない場面とやりすぎ {#limits}

望む形で書くことにも、効かない場面と、やりすぎの形がある。

- **言い換えただけで終わる**：「冗長にしない」を「簡潔にする」と書き換えても、行き先は決まらない。動詞と具体形（何文で、何を先に）まで書く。
- **例外のない禁止を書き換えで済ませる**：望む形にしても、お願いのままである。破られて困る禁止は、仕組みへ移す。
- **望む形を詰め込みすぎる**：行動の指示を何十も並べると、重要な 1 行が埋もれる。数を絞り、理由で束ねる。
- **手本に引きずられる**：書いた手本の文を、そのままなぞる出力が増える。手本は典型的で多様なものにする（<!-- link:begin show-examples#overfit -->[例を見せる › 例にだけ合う出力に気をつける](show-examples.md#overfit)<!-- link:end -->）。
- **すべての禁止を消そうとする**：守りたい境目は、禁止の形で書いてよい。消すのは、代わりの行動を書けるのに書いていない禁止である。

効いているかは、同じ依頼を Before と After で数回ずつ流し、出力を並べて比べる。差が出なければ、書き換えが言い換えにとどまっていないかを見る。
