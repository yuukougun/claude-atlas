- ユーザーに確かめる点は §3 にまとめ、工程5で示す

## 2. 対応の一覧

### DR-01 未公開のページへの道（R1-01・R2-1・R2-7・R2-30・R3-2・R4-1）

- 生成物（ナビゲーション・分野の入口・一覧・逆引き・用語索引・知識マップ・ロードマップ・比較表・症状の原因別の表・llms.txt）には、stage が draft 以上のページだけを載せる
- ページ下部の前提・次に読む・関連が stub を指すときは、リンクにせず「題名（準備中）」の平文にする
- 本文から、まだ公開していないかもしれないページを指すときは、目印 `<!-- link:begin <id>[#<anchor>] -->` 〜 `<!-- link:end -->` を使う。道具が相手の stage を見て、draft 以上ならリンクを、stub なら「題名（準備中）」を書く。相手を公開したら道具が書き直すので、前のページへ手で戻らない
- 手書きの Markdown のリンクで stub を指すものは、check_pages.py が止める。MkDocs の `--strict` は止めないので頼らない（MkDocs 1.6.1 の実装。R4-1）
- 試作のページは、そのページの波が来るまで公開から外す
- 反映：design §8.4・§8.5・§8.6・§10.1

### DR-02 症状のページの振り分け先 `routes`（R1-02・R3-1・統合 I7-1）

- 症状のページに `routes` を持たせる。形は `routes: [{cause: <prevents か pitfalls の値>, to: [<id[#anchor]>, …]}]`。原因ごとに中心の対処を1〜3件、近い順に書く
- `routes` には段階と優先度の規則を当てない（上の段の対処も、推奨の対処も置ける）
- 症状のページの `prerequisites` は、診断を読むのに要る概念のページだけにする（ふつう basics と start）。level は、その症状に出会う段階で付け直す
- 知識マップ・症状の原因別の表（design §8.3）・第一波の数え方・診断の節の目印は `routes` を読む。症状のページの related は、routes にない近いページだけにする
- 統合の担当 I7 が挙げた案 (b)（README に例外として書く）は採らない。段階と知識マップのゆがみが残るため（R3-1）
- 反映：design §3.3（キーの台帳）・§4.1、catalog/README §3・§4、check_catalog.py（routes の検査と、第一波の数え方の内訳）、symptoms.yaml

### DR-03 第一波の範囲（R1-01・R2-1・R2-5・R2-6・R3-2・R3-3・統合 I7-2）

ユーザーに確かめる（§3 の U1）。目次の直しの後の数で示す。メインの推奨は「核（入口・症状辞典の全ページ・台帳・評価と実験の核・判断と理解の核・日本語の核）と、その前提と、症状のページの原因ごとの最初の振り分け先と、名指しの正本（安全の早見表）」。推奨の症状のページも第一波に入れるなら、それらを必須に上げる（D10「初版は必須」の順と食い違わないようにする）。

### DR-04 規模の上限（R3-4）

試作（工程7）で1ページの使用量を測ったら、第一波の上限（ページ数かトークン）と、超えたときに外す順を決めて design §2.3 に書く。check_catalog.py の第一波の数に内訳（核・前提・routes・正本）を出す。

### DR-05 比例則の読み（R2-2・R1-10・R3-6）

ユーザーに確かめる（§3 の U2）。メインの推奨は、前提を「知らないと読めない」依存に限り、守りのページ（verify・eval・enforce・safety）は関連に持たせ、ロードマップの生成で同じ段の手前に並べる形。要件 §3.3 の目的（生成されるロードマップが任せる幅を広げる順になる）は生成の規則で満たせる。守りを前提にすると前提の鎖が深くなり（深さ6以上が47ページ。R1-10）、具体的な用で来た読者に「先にこれだけ読め」と見える。反映：design §3.1・§7（ロードマップの作り方）・§13 に比べた案として足す。

### DR-06 ユーザーに確かめる場面（R2-3・R4-3・R4-24）

- §10.8 から「試作の出来」「第一波の最初のバッチの出来」「骨格の後のページの追加・統合・削除と id の変更」を外す。出来は別の担当の検証と工程10の「読者の課題から引く」で確かめる
- ページの追加・統合・削除は decisions.md に記録し、事後に一覧で知らせる。公開済みの URL を変えるときだけ確かめる
- 作者への頼みは5つにまとめる：工程5、工程7の終わり（使用量と期間の見込み・方針の文の承認・この環境で試せない確認・口座の状態の確認を1回で）、鮮度の点検で推奨・安全の既定・台帳の状態が変わる更新（点検ごとにまとめて）、使用量が見込みを大きく超えるとき、Zensical への移行

### DR-07 雛形の確認（R4-2・R4-5〜R4-9・R4-31・R2-15・R2-27）

- **対照**：期待ごとに「雛形あり」と「雛形なし（同じフォルダ・同じモード・同じ依頼）」を流し、結果が期待どおりに違うことを合格の条件にする。雛形が読まれたことを `claude doctor` の出力でも確かめる。対照の結果も verified.yaml に残す
- **切り離し**：子の環境は許す一覧から作る（偽のホームの HOME・PATH・LANG・CLAUDE_CONFIG_DIR と認証の token だけ）。偽の秘密は偽のホームに置く。`--strict-mcp-config` と、claude.ai のコネクタと自動メモリを読まない設定を付ける（research/28 #26・#35）。API キーやクラウドの事業者の認証の変数が親にあれば止めて知らせる（research/28 #33）。使い捨てのフォルダは、上のどこにも CLAUDE.md のない場所（/tmp の下）に作る。モデルと版を固定して記録する。ログインは setup-token の token を勧める
- **読者の条件に合わせる**：雛形ごとの置き場所（user・project・local）と条件を expect.yaml に書き、道具が合わせる（使い捨てのフォルダを専用の設定で信頼させる。defaultMode を決める雛形ではモードを渡さない。research/28 #30）
- **種類ごとの確認**：settings・hook・skill・subagent・claude-md は静的な検査と実機（対照つき）。prompt は実機で数回流した観察を検証ノートの形で添える（合否にしない）。other（点検表・記録表）は静的な検査だけ。安全とデータの雛形（safety: true）だけは、確認を通るまで載せない（方針 B2）。ほかは確認の前でも下書きで出してよい
- **この環境で試せない雛形**（使い捨てのコンテナ・/etc に書く管理設定・API キーが要る `--bare`・GitHub Actions）：既定では雛形を載せず、条件と概念だけを書く（方針 B2 の「写して使う部分だけを止める」）。作者に頼むかは工程7の終わりの頼みに入れて聞く
- **WSL2 の sandbox**：sandbox の雛形に `failIfUnavailable: true` を入れ、Windows の実行ファイルの経路を期待に足す。seccomp のフィルタを制作の環境に入れて確かめ、版を記録する（research/28 #36・#37）
- **静的な検査**：SchemaStore のスキーマの写しを schema/ に置き（写した日と相当の版）、雛形が使うキーの許す一覧を自前で持って CI で誤りにする。skill と subagent は手元で `claude plugin validate --strict` も流す
- 確かめた版の系列（latest・stable）を verified.yaml と verified_with に書く。雛形が要る最低の版は、facts の「入った版」から道具が書く
- 検証ノートには、制作の環境で試したか、作者に頼んだかを書く
- 反映：design §6.9・§6.10・§8.6・§8.7

### DR-08 hooks と permissions（R4-16・R4-20〜R4-23・R4-33・R4-37・R2-25・R2-26）

- **H1**：強制は `.claude/settings.json` の deny（`WebFetch(domain:<ドメイン>)` と `WebFetch(domain:*.<ドメイン>)`）で行う。hook は理由の文と記録だけを受け持つ。Bash は、取得の道具（curl・wget など）の URL の引数のホストがそのドメインのときだけ照らす（ドメインの文字列では照らさない。grep や check_noai.py を止めないため）。sources で断るドメインがすべて deny にあるかを検査で確かめる
- **H2**：deny と同じ範囲に当たる PreToolUse の hook を1つ置き、理由と代わり（`gen_site.py` で作り直す）を返す。止めた操作は `state/blocks.log` に1行ずつ記録し、バッチの報告に「止められた操作」の欄を足す
- **H3**：担当に許す git を、読むだけのもの（status・diff・log・show）に絞る（巻き戻しの操作はほかの担当の変更を消すため）。gh の書き込みも止める。担当が目印を埋めるときは、自分のページだけを書く `gen_site.py --page <id>` を使う。ワークフローの担当で hook が効かなかったときの代わりに、バッチの始めと終わりの HEAD を state/ で比べる
- **制作にだけ要る縛り**（H3・H4）は、追跡しない印（`state/production`）があるときだけ働き、ないときは何もしないで終わる。読者がリポジトリを開いたときは動かない
- **H4**：API キーの確かめは check_templates.py の中の必須の確かめ（あれば止める）に移す。hook は印のあるときに知らせるだけ
- README には、どんな hooks と permissions が入っていて何をするか、読者の環境で何が動き何が動かないか、依存が欠けたときにどうなるかを書く
- §11 と CLAUDE.md の「生成と commit は H2・H3」を実際に合わせる（commit は H3、生成は CLAUDE.md と指示）
- 制作の権限モードと、`.claude/` への書き込みで確認が出るか（ワークフローのスクリプトの置き場所）は、土台作りで決める
- 反映：design §10.5・§11

### DR-09 工程（R2-6・R4-13・R4-14・R4-17・R4-18・R4-34・R4-35・R3-21）

- 8b を「第一波（終わり：第一波の公開）」と「残りの必須（終わり：初版の公開）」に分ける。推奨は、工程11の運用で Issue と需要の見立てから選んで足す
- 骨格（8a）を試作の前（土台作りの終わり）に移す。試作で、stub を含めた試しのビルド（公開しない）で、ナビゲーション・検索・知識マップの規模と、DR-01 の目印を確かめる
- 試作の型に recipe と guide を足し、prompting の技法の concept も1ページ入れる
- 工程7の終わりの条件に「型ごとの手引き・チェックリスト・見本を確定し、試作で分かった設計の直しを反映した」を足す
- 鮮度の点検の skill（少なくとも点検の手順の1・2・5）は、第一波の公開の前に仕上げる
- 工程6の後半（試作の前）に「data の初版」を足す。担当が research/22〜28 と公式の文書から facts・features・outdated-advice・sources を作り、別の担当が出典と照らす。終わりの条件は「第一波のページが tracks・outdated_advice・sources で指す id がすべてある」
- 工程4の終わりの条件に「反映の後、別の担当が design-review.md と第2版の差分を確かめ、check_catalog.py が通る」を足し、見直しの担当を4つに直す
- 反映：design §10.1

### DR-10 段階の移り方と「完成」の意味（R2-9・R2-10・R4-11）

- 執筆者が draft にする（verified なし。帯は「下書き・未検証」）→ 検証役が、指摘0件か、直しの差分を確かめ直して reviewed にし、verified を書く → メインが、検査0件と未解決の指摘がないことを確かめて done にする
- キーの台帳の verified の「必須」は reviewed 以降にする。数値の確認日は目印の中に持つ
- 「完成（done）」は、作者がすべてを確かめた意味ではない。サイトでの言い方は出典と AI 利用の方針のページに書き、作者の承認に入れる
- 反映：design §3.3・§8.5・§10.2

### DR-11 鮮度（R4-10・R4-12）

- facts の各項目に volatility を持たせる（既定は高）。道具が、ページごとに期限の日（ページの確認日＋ページの期限と、各数値の確認日＋数値の期限のうち早いもの）を計算して data 属性に出す。ブラウザは今日と比べるだけにする（生成物は決定的なまま）
- 点検で影響がないと確かめた日は `checked` に書いて期限の計算に使う。verified は出典を読み直したときだけ進める
- features の項目に、CHANGELOG とリリースノートで照らす英語の語を持たせる。前回の点検の版と日付を data に持つ（追跡する）
- 月の点検の量と使用量は試作で見積もる（いまの volatility では、全部を公開した後に月に約130ページが期限を迎える。R4-12）
- 反映：design §8.5・§9.1・§9.2・§9.4・§10.7

### DR-12 執筆の受け渡し（R4-15・R2-33・R2-14・R4-32）

- 出典は、ページごとのファイル（`data/sources.d/<id>.yml`。執筆者が書いてよい）に足し、道具が1つにまとめて URL の重なりを検査する
- 新しい数値の id は提案のファイルに書かせ、検証役がそれも照らす
- front matter の直しの提案は、決まった形の YAML（id・キー・前・後・理由）で報告させ、メインが承認したら道具が当てる
- 執筆には、手引きが写す設計書の節を名指しして渡す。手引きとチェックリストは format-and-operations F16 の3点（今有効な規則だけを置き決定のたびに書き換える、機械で検査できる規則に検査の名前を添える、チェックリストを検証の4つの観点に合わせる）で作る
- 止まった担当の半端な変更は、既定では最後の commit に戻してから流し直す
- 反映：design §3.3・§10.2・§10.3

### DR-13 使用量とモデル（R4-19・R3-4）

- 役割ごとのモデルと effort の初めの案（執筆と事実の検証は上位のモデル、形の検査に近い検証は軽いモデル）を書き、試作で測って決める
- 工程5の一覧に概算を入れる：kyopro-atlas の1ページ35〜45万トークンを当てると、第一波（125ページの場合）で約4,400万〜5,600万、必須で約6,100万〜7,800万、全部で約1.3億〜1.6億。設計書は、検証の観点が多いのでこれより重くなると見込む
- 新しい段を起動しない条件を、週の使用量でも決める。口座の状態（5時間の上限がない確認済みか）は、工程7の終わりの頼みで作者に確かめる
- 反映：design §10.2・§10.3・§10.7・§12

### DR-14 表示（R1-09・R2-8・R4-4・R4-30）

- サイトのトップ（docs/index.md。手書き）を横断のページに足す：非公式の教材であること、三つの入口（困りごと・やりたいこと・名前）、検索、症状辞典と台帳への道
- ナビゲーションの分野の並びは requirements §4.1 のままにし、トップと start から症状辞典を直接指す（並びを変えるのは要件の変更になるため）
- 全ページの冒頭とフッターに非公式の文、フッターに「© 2026 yuukougun」とライセンス。Anthropic のロゴと意匠をまねない。mkdocs.yml に site_url。冒頭とフッターの文は公開の約束なので作者の承認に入れる
- `theme.font: false`（端末のフォント）にし、Mermaid は写しを置いて読む（外のサイトから読まない。読者の情報を集めない決定の趣旨）
- 描画の検査は、push と pull request で変えたページ、週1回は全ページ、手元でも同じコマンドで回す。土台作りで、手元の Chrome と日本語のフォントを決めて記録する
- 反映：design §7・§8.5・§8.6・§8.8・§12

### DR-15 逆引きと用語索引の作り方（R1-03・R1-06・R1-08）

- 逆引きの困りごとの節は、症状辞典の章で分ける。対処のページの困りごとは、振り分け先の症状のページの章に入れる（分野から章への対応表を作る層の設定に持つ）。やりたいことの節は場面か分野で分ける
- 同じ文の sign は1行に束ね、行き先に面や型の短い印（アプリ・Claude Code、考え方・手順）を付ける。わざと1つの問いにまとめる goal は同じ文にそろえ、まとめないものは場面を書き分ける
- 試作で逆引きを生成し、R1 の読者の課題で引いて確かめる（工程10まで待たない）
- 用語索引は、機能ごとに主のページを決め（features.yaml の page）、主を先に出し、ほかのページを短い印付きで並べる。ほかのページの題名と同じ別名は外す
- 反映：design §7、features.yaml

### DR-16 技術の細部（R4-25〜R4-29・R4-36）

- 道具は `uv run`（Python 3.12）で動かし、PyYAML などは pyproject の依存にする。hooks は、標準のライブラリだけの `python3` で動く形にする
- 前提と関連の規則は検査の層の関数にし、catalog と front matter の両方に当てる（check_catalog.py は骨格の後に退く）。page.schema.json は site.yml とキーの台帳から作る。search.boost を使うならキーの台帳に足す
- 目印の外に数値ファイルの値を手で書いた警告は、照合の型（単位や前後の語）を持つ項目だけを照らす
- 雛形の本文への写しも、目印（`<!-- gen:begin snippet <id>/<名前> -->`）の間に道具が書き、`--check` で snippets/ との一致を確かめる
- Zensical の評価の基準を決める（stub が出ない・描画の検査0件・日本語の検索・overrides・リンクの検査）。試験ビルドの版を固定する。stub を docs/ の外に置き、draft にするときに docs/ へ移す形も土台作りで比べる。Material 9.8 の保守の終わり（2027-05-05）に移れないときは、使い続けて依存の脆弱性を見張る案を作者に知らせる
- CI と同じ検査の組を流す入口（`tools/check_all.py`）を作り、commit の前に流すと CLAUDE.md に書く。デプロイの job は必須の検査の後に置く
- 反映：design §8.1・§8.3・§8.4・§8.6・§8.8

### DR-17 編集方針に足すもの（R2-11〜R2-13・R2-17〜R2-24・R2-27・R2-29・R2-31・R2-32・R3-21〜R3-23）

- 公式の文書を訳して載せない。ほかの記事の文を転載しない。参考にした資料は出典に残す。検証（事実・出典）のチェックリストに「出典の文と長く一致する箇所がないか」を入れる（R2-11）
- 方針 B1（文書にない回避方法は公開より先に Anthropic に報告する）の手順：見つけたら、その記述と雛形の公開を止め、記録は追跡しない state/ に置き、報告を作者に頼む。報告が済むまで公開しない（R2-12。§3 の U4 で確かめる）
- 見せ方（注釈付きのセッション記録・検証ノート・Before/After）：目次の notes に「見せ方」を書く。試作の前に、メインが制作の記録から作れる題材と、繰り返して確かめる検証ノートの数件を名指しした一覧を作る（R2-13）
- AI Fluency（4D）は参考文献に挙げるだけにする。公式の教材（Academy・docs）は案内する。第三者のツールには成熟度と確認日を付ける（R2-17・R2-18・R2-21）
- コンテスト：七つの形式を同じ厚さで扱う、例は AtCoder の ABC・AHC から多く取る、作者の参加の記録は使わない、競技の練習法と AtCoder の規則の細部は kyopro-atlas へリンクする（境界の表に足す）、大会の規則の版は作者に確かめを頼まない（R2-19）
- 演習は作らず、演習の形の論点を判断の例・検証ノート・振り返りのチェックリストにする（D7。R2-20）
- scenes にコンテストを持つページを、contest の分野の入口（生成）で一覧にする（R2-22）
- §12 の10を決定の言い方にする（教材の推奨・安全の既定・台帳の状態が変わる更新）（R2-24）
- 守れない約束を書かない。how-to-use の report・freshness の節も、作者に見せる文に入れる（R2-31）
- 安全の既定の正本の中身として、決定の段階ごとの中身（任せる段階からは sandbox と秘密の読み取りの禁止、無人の実行は使い捨ての環境、預かったデータは契約のある面だけ）を §6.6 に書く（R2-32）
- §2.2：本体を生成するページも hub・ledger の型を持ち、生成の部分は目印で作る。型を持たないのは分野の入口（index.md）と lists/ だけ（R2-23・R3-23）
- concept の定義に技法（どう頼むと何が変わり、なぜか）を足し、§6.3 に目安の流れを足す（R3-21）
- summary の1文目は「何ができるか、または答えそのもの」にする（R3-22）
- 動く図「コンテキストの埋まり方」：公式の対話の図へのリンクを主にし、自作は公式にない点（毎回全部を読み直すこと・圧縮）だけの図にする。動く図にするのは、公式で足りないと試作で分かったときだけ（R2-29。統合のときの M8 を改める）
- 反映：design §2.2・§4.2・§5.3・§6

### DR-18 名称と台帳の分担（R3-13）

名前と画面の変更の事実（旧名・今の名前・変わった時期）は、数値ファイルの名称の表を正にする。台帳の行は名称の id を指して時期をそこから引く（二か所に持たない）。台帳の行は消さない。古い記事の手順が通じない読者の入口になるため（例：`/fork` は改名され、今の `/fork` は別の機能）。反映：design §9.1。

## 3. ユーザーに確かめる点（工程5）

- **U1 第一波の範囲**（DR-03）と、推奨の症状のページを第一波に入れるなら必須に上げるか
- **U2 比例則の読み**（DR-05）：要件の「守りのページを前提に持たせる」に戻すか、前提は「知らないと読めない」依存に限り守りは関連とロードマップの生成で示すか
- **U3 事例の記録の skill**（R2-16）：要件 §8 の使い道（検証ノートと注釈付きのセッション記録の素材）は、決定（方針 A6「作者の手元の記録は使わない」と「検証ノートは制作の環境で」）で閉じた。作らないか、使い道を変えるか。メインの推奨は、作らずに、作者が出会った困りごとは Issue のテンプレート（ページや症状の提案）で受けること
- **U4 文書にない回避方法を見つけたとき**（DR-17）：報告は作者が行い、報告が済むまで該当の記述と雛形を公開しない、でよいか
- **U5 公式で表記が割れている3語**：plan モード・effort・許可ルール／確認ルール／拒否ルール（仮。Claude Code の日本語版の多数派）
- 知らせるだけのもの：使用量の概算（DR-13）、ユーザーに確かめる場面を決定に合わせたこと（DR-06）、この環境で試せない雛形の既定（DR-07）、kyopro-atlas の AtCoder の規則の書き方と claude-atlas の「未確認」の食い違い（kyopro-atlas は変えていない）
