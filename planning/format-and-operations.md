## 2. 案の要点

1. 形式の骨組みは kyopro-atlas から引き継ぐ：Markdown と front matter から一覧・索引・逆引きを生成する、catalog → 骨格 → 本文 → 検証の段階、独立スクリプト、textlint
2. 変わりやすい値（数値・既定値・名称・成熟度）は `data/` に集め、本文とバッジには道具が書き込む。手では書かない（L4）
3. 確認日は「主張」と「ページ」の二段で持ち、期限切れはブラウザで日数を計算して出す（L5・L18）
4. 描画の検査と書き方の検査は土台作りで用意し、試作のページで0件にしてから本制作に進む（L1〜L3）
5. 道具は層に分けて作り直す。汎用の部品（描画の検査・noai の確認など）は kyopro-atlas から写して直す（L6）
6. 制作は、共通の指示と差分、報告の固定の形（「確かめていないこと」の欄）、状態ファイル（追跡外）、ワークフローのスクリプトと args の保存で回す。止まっても機械的に再開できるようにする（L9〜L12）
7. 公開の約束・方針・ライセンスに関わる文は、作者が承認してから出す。メインが書いた直しも、別の担当が検証する（L13・L15）
8. claude.ai での相談の仕組みは作らない（decisions 2026-11-03）

- hooks や permissions の置き場所は Q2 で決める

### F2 front matter と schema（案）

- JSON Schema（`schema/page.schema.json`）と、それを当てる検査は引き継ぐ
- **キーの台帳**を設計で作る。キーごとに「型・誰が書くか（執筆者・検証役・道具・メイン）・どこに写るか（表示・一覧・逆引き・`llms.txt`）・書式（平文か Markdown か）・検査」を決める（L7）。型を検査できないキーは作らない
- 執筆者が書くキーを絞る。`verified`・`verified_with` は検証役か点検の道具が書き、`maturity` などの変わりやすい値はキーに手で書かず、`tracks` から `data/facts.yml` を引いて道具が出す（L4・L7）。執筆の指示には「書かないキー」を明記する
- 1つのキーを2つの表示の役に使わない（kyopro-atlas の `nav_title` の不具合 #91）

### F3 段階と正本（案）

- catalog（目次）から骨格を作った時点で、front matter を正にし、catalog は凍結して執筆の指示にだけ使う（kyopro-atlas と同じ。回答 B1 も同じ意見）
- 骨格の後は id と URL を変えない。ページを足すときは decisions.md に「新しいページ（id と URL）」を記録する（工程11 の運用）
- 段階は stub → draft → reviewed → done を引き継ぐ。done（完成）と鮮度（確認日の期限）は別の軸にする

### F4 要点と、公開する段階（要点は案。公開の段階は Q4）

- 全ページの本文の最初に要点の囲みを置く（kyopro-atlas と同じ）。項目は requirements §5.3 のとおり
- どの段階のページを公開するか（準備中・下書きを出すか）は Q4

### F5 数値ファイルと、本文からの参照（案）

- 料金・上限・既定値・名称・成熟度・大会の規則と成績を `data/facts.yml` に集め、項目ごとに出典の id と確認日を持たせる（D11）
- 本文への参照は、目印（例：`<!-- fact:begin 名前 -->`〜`<!-- fact:end -->`）の間に、道具が値・数値を含む決まった文・確認日を書き込む。CI の `--check` で、データとの食い違いを止める（L4。回答 C4 の (a)）
- mkdocs-macros で変数名だけを書く方式は採らない。リポジトリや `llms.txt` から Markdown を読む人や AI に値が見えず、Zensical にも移りにくい
- 目印の中に、毎回変わる値（ハッシュなど）を書かない（L5）

### F6 確認日・変わりやすさ・期限切れ（案）

回答 I2 の「最初に決めるべき4つ」に沿って決める。

1. **確認日の単位**：主張（`data/facts.yml` の項目）と、ページ（本文の主張全体）の二段で持つ。ページには、含む主張の確認日のうち最も古いものを、道具が計算して添える
2. **期限**：`volatility` が低なら365日、中なら90日、高なら30日（requirements §7 の目安）
3. **期限切れの見せ方**：ページに確認日と版を出し、期限切れの注意書きは、ブラウザがその日付から日数を計算して出す。ビルドした日で変わる値を生成物に入れない（L5。requirements §7 の「ビルド時に出す」を改める案）。CI でも期限切れを警告するが、日によって結果が変わるので失敗にはしない
4. **点検の担当と手順**：鮮度の点検の skill（F23）が、前回の確認より後の CHANGELOG とリリースノートの差分を `tracks`・`aliases` と照らし、影響のあるページの一覧を出す。更新は人が承認する（D18）。GitHub のリポジトリを作った後は、点検の結果を Issue にして回す

### F7 出典の記録（案）

- 出典を `data/sources.yml` の1か所に持つ（id・URL・題名・種類（公式文書・公式ブログ・CHANGELOG・実践者・研究）・確認日・AI の利用の指定を確かめた日と結果）。ページの front matter からは id で参照し、ページ末尾の「参考」は道具が作る（L4）
- 新しいドメインは、資料にする前に AI の利用を断る指定を確かめる（`check_noai.py` を写して使う）。kyopro-atlas の手引き付録 B にあった記録は、このデータに入れる

### F8 図（案）

- 静的な SVG と Mermaid を基本にし、動く図は、動かすことで分かりやすくなる数個に絞る（requirements §2）
- 描画の検査（kyopro-atlas の `render_pages.py` を写して直す）を土台作りで用意し、pull request では変えたページだけ、週1回は全ページを流す（回答 H3）

### F9 技術基盤（書き方の制約は案。道具の選択は Q5）

- 2026-11-03 に確かめた事実：Material for MkDocs の最新は 9.8.0（2026-10-24。主にセキュリティの修正で、Python 3.11 以上が必要）で、保守は 2027-05-05 に終わると告知している。Zensical の最新は 0.0.74（2026-10-30）で、まだ alpha。11-05 に変更の予告がある（中身は未確認）。kyopro-atlas の記録の「0.1.0 は 2026-11-05 の予定」は 10-21 時点の情報である
- どちらで作る場合も、MkDocs の hooks・macros・自作プラグインを使わず、生成は独立スクリプトで行う（requirements §2。kyopro-atlas と同じ）。この制約は今決めてよいと考える
- どちらで作るかは Q5

### F10 生成スクリプト（案）

- 写して直すのではなく、層に分けて作り直す。(1) front matter・data を読んでモデルにする層、(2) 生成の層（生成物の種類ごとに1つ）、(3) 検査の層（検査1つを関数1つにして登録し、試験も検査ごとに書く）。分野・段階・type などの語彙は設定ファイル（`schema/` に置く）に出す（L6。回答 C1）
- kyopro-atlas から写して直すもの：`render_pages.py`（描画の検査）・`check_noai.py`・`check_svg.py`・`textlint_targets.py`。`gen_site.py`・`check_pages.py`・`make_skeleton.py` は考え方を引き継ぐ
- 生成するもの：ナビゲーション・分野の入口・一覧・逆引き（`signs` の symptom・goal・situation から）・比較表（`enforcement` などの属性から）・ロードマップと知識マップ（level と `prerequisites` から）・古くなった助言の台帳への逆リンク・`llms.txt`（Q7）
- 生成物はコミットし、CI で `--check`。マージの後は生成し直す手順を最初に決める。生成物に内容のハッシュなど毎回変わる版を入れない（L5）

### F11 検査スクリプト（案）

土台作り（工程6）で、試作の前に次を用意する（L3）。

1. front matter の schema とキーの台帳
2. 参照・循環・前提のレベル（委任の段階）のつながり
3. リンクと anchor（`mkdocs build --strict` を含む）
4. 生成物の `--check`（数値・出典・バッジ・一覧）
5. 確認日と期限（警告）、版に依存する記述の確認日
6. 書き方（textlint と、試作で決める型ごとの規則。例：節の並び、平文の欄に記法を書かない）
7. 描画（ヘッドレスの Chrome。pull request では変えたページだけ、週1回は全ページ）
8. 雛形の静的な検査（F12）

全体の検証（工程10）には、ページの正しさとは別に「読者の課題から引いてみる」観点を足す。逆引きの項目（requirements §1 の困りごとや `00` §4 の73項目）から20ほどを選び、目的の節に何回のクリックで着くかを試す（L2）。

### F12 設定・雛形の動作確認（形は案。どこで試すかは Q6）

- `snippets/<id>/` に雛形のファイルと期待の設定を置く。期待は「出力の完全一致」ではなく、「この操作が止められる」「この行が出る・出ない」の形にする（回答 C5）
- 二段で確かめる。静的な検査（JSON と YAML の形、settings の schema、skill と subagent の front matter）は CI で毎回。実際に動かす確認（使い捨てのフォルダで `claude -p` を動かす）は手元だけで行い、確かめた版・OS・日付を記録する
- 鮮度の点検で、「確かめた版」と「今の版」の差を出せるようにする（回答 C5）
- 実際に動かす確認は、作者のプランの使用量を使う

### F13 textlint と prh（案）

- kyopro-atlas の設定（preset-ja-technical-writing・prh・全角と半角の間の空白、警告は残してよい）を引き継ぐ

### F14 サブエージェントへの分担（案）

- 執筆 → 検証（別の担当）→ 直し（書いた担当に戻す。回答 D2 で問題がなかった）
- 執筆者が書いてよいのは、担当のページ・そのページの雛形と図だけ。共有のファイル（用語集・prh・data・catalog・手引き）への変更は、報告に「提案」として書き、メインがバッチの終わりに反映する。指示には front matter の中で触ってよいキーを名指しで書く（L13）
- 検証の観点は4つに組み直す。(1) 事実・出典・鮮度（数値ファイルを経由しているか、確認日、根拠の強さ、版に依存する記述）、(2) 雛形の動作、(3) 分かりやすさ（冒頭で用が足りるか、断片で読んで通じるか）、(4) 図と描画（描画した結果を見る。L16）
- 担当の外への波及（並べ替えた後の「上の節」など）は、メインと道具の検査で見る（L16）
- メインが書いた直しも、書いた本人ではない担当か、機械の検査に加えて別の担当が確かめる（L13）

### F15 バッチの回し方（再開の決まりは案。ワークフローの使用と規模は Q1）

- 共通の指示を1ファイルにし、担当には差分だけを渡す（L9）
- 報告の形を固定する：書いたファイル・直したこと・範囲を越えたこと・メインに判断してほしいこと・検査の結果・**確かめていないこと**・使用量（L9）
- 各担当は、報告をファイルに書いてから終える。再開は「報告のないものだけを流し直す」（L11）
- ワークフローのスクリプトは `.claude/workflows/` に、起動したときの args は `state/` に残す（L11）
- ページの一覧は、必ずファイルから機械的に渡す（kyopro-atlas b1 の反省）
- 上限の窓の終わりには新しい段を起動しない。ワークフローの「完了」は、報告のファイルと作業ツリーで確かめる（L12）
- 並列の数は、試作で測ってから決める

### F16 執筆の手引きとチェックリスト（案）

## 4. 調査資料と要件の中で気づいた点

調査資料は AI が書いたもので、根拠が弱いのに断定している箇所や、要件・手本と食い違う箇所がある。形式と運用に関わるものを挙げる（v0 から引き継ぎ、判断を反映した）。

1. **catalog を唯一の正本にする案**（00 §6「planning/catalog は、ページの一覧と front matter の唯一の正本にし、雛形はそこから生成する」）：kyopro-atlas は骨格の後に catalog を凍結し、front matter を正にした（二重管理を避けるため。design-review T10）。回答 B1 も、骨格の時点で front matter に正を移す意見だった。F3 で採らない
2. **数値を mkdocs-macros で参照する案**（00 §6「本文からは mkdocs-macros などで参照する」）：requirements §2 の「MkDocs を import しない独立スクリプト」と、kyopro-atlas の「Zensical に移りやすくするため macros を使わない」（design §8.1）と食い違う。リポジトリの Markdown を読む人や AI に値が見えない。F5 で採らない
3. **「スクリプトの多くは AtCoder 固有なので作り直す前提」**（00 §7）：言い過ぎである。大きな2本で、AtCoder・問題・台帳・ACL・出題頻度・コード片・KaTeX に触れる行は、`gen_site.py` が1536行中134行、`check_pages.py` が2477行中136行で、どちらも1割に満たない。`render_pages.py`・`check_svg.py`・`check_noai.py` などはほぼ汎用である。ただし回答 C1 によると、`gen_site.py` と `check_pages.py` は分野・段階の名前などがコードに直書きで絡み合っているので、F10 では「層に分けて作り直し、汎用の部品は写す」とした
4. **「用語集は、MkDocs Material の略語ツールチップで本文中の語に自動で付ける」**（00 §6）：日本語の語には効かない。Python-Markdown 3.11.2 の abbr で確かめると、前後が英数字でない語にだけ当たった。「subagent を」には付いたが、「subagentを」「サブエージェントを」「お願いと鍵を」には付かなかった（2026-11-03、kyopro-atlas の .venv の Python-Markdown で確認）
5. **期限切れの注意書きを「ビルド時に」出す**（requirements §7）：生成物を決定的にして `--check` で確かめる方式と合わない。また push がない間は日数が古いままになる。F6 で、ブラウザで日数を計算する案にした
6. **claude.ai の Projects の種類**（requirements §8）：従来の Projects か、新しい Projects（claude.ai/code）かが書かれていなかった。相談の仕組みそのものを作らないことになったので（decisions 2026-11-03）、この点は解消した
7. **front matter の例の食い違い**（00 §6 の例）：`level: L3`・`priority: 必須`・`summary: {can, when, prereq}` の形で、requirements §3.3（level は「使う」〜「回す」の名前）・§5.2（kyopro-atlas のキーを引き継ぐ。summary は1文）と、00 自身の §7（summary は1文のまま）とも違う。requirements の形を正とする
