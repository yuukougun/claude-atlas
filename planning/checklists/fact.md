# 事実・出典・鮮度のチェックリスト

- 版：2026-11-04 第1版（工程6a。試作〔工程7〕で確かめて確定する）
- 検証の共通の決まり（common.md）と一緒に使う。照らす規則は、共通の手引きの §8・§9・§11・§14〜§17 と型の手引き
- 渡されるもの：ページ、data（facts・sources・outdated-advice）、出典、数値の提案のファイル

## F1 主張と出典の照合

元：design §10.2・§6.8、requirements §11

- **見るもの**：機能の挙動・既定値・規則・研究の結果を述べる文と、`sources` の出典
- **確かめ方**：出典を開いて読み直し、主張が出典に書かれているか（言い過ぎていないか、条件を落としていないか）を見る。調査資料の要約でなく、今の公式の文書で確かめる。工程2の訂正・注記（research/22〜28）の付いた主張が、訂正の前の形で使われていないかを見る
- **よくある失敗**：改稿の前の公式の文書の要約を使う（Claude Code の Best practices は 2026-10 下旬に書き直され、調査資料には前と後の要約が混ざる。research/23）。面ごとに違う既定値を一つに丸める。公式の別々の記事の数値を混ぜる

## F2 変わりやすい値が数値ファイルを経由しているか

元：design §6.7・§8.4

- **見るもの**：本文の数値・既定値・成熟度・名前の変更・版・大会の規則と成績、summary・signs・題名
- **確かめ方**：目印の外に手で書いた値がないかを読んで探す（検査：check_pages.py「目印の外の数値」）。この検査は照合の型を持つ項目しか見ないので、検査の外も読む。目印の id が数値ファイルにあるか（検査：check_pages.py「facts の id」）。目印の中身が数値ファイルと一致するか（検査：gen_site.py --check）。数値の提案のファイルの各項目を、出典で照らす（値・条件・確認日・面とモデルの違い・食い違い）
- **よくある失敗**：段落の中に「既定では N」と手で書く。目印の決まった文を、目印の外で言い換えて値を繰り返す。research preview の機能の名前やモデルの世代の名前を手で書く

## F3 根拠の強さ

元：design §6.6、requirements §6.2・§3.2

- **見るもの**：研究・数値・実践例を根拠にする主張と、その根拠の印
- **確かめ方**：印があるか、出典の種類と印が合うか（共通の手引き §8 の表）を見る（作る予定：check_pages.py「根拠の印」）。この検査は印の形だけを見る。研究の結果に、モデル・世代・標本の大きさがあるか。類推・推論が、強い根拠に見える書き方になっていないか。推論（実践例なし）が必須のページの中心になっていないか。割れる論点が三段（公式の立場・実践者の幅・この教材の推奨）で書かれているか
- **よくある失敗**：旧世代や他社のモデルの研究を、現行の Claude の傾向として書く。五つの落とし穴の根拠を一律に「強」とする（requirements §3.2 の注記）。自己申告の数値を事実として書く

## F4 版に依存する記述と確認日

元：design §6.5・§8.5・§9.2

- **見るもの**：機能の挙動・画面・コマンドの出力など、版で変わる記述
- **確かめ方**：今の版（制作の環境の `claude --version` と、npm の latest・stable）で確かめられるか。版の番号・入った版・最低の版が手で書かれていないか（目印か、道具が書く所か）。Claude Code の記述が WSL・Linux の CLI を基準にし、ほかの OS と IDE の拡張を「未確認」としているか。制作の環境で試せないアプリの機能に、「未確認」か、作者に頼んだ結果の印があるか（検査：check_pages.py「確認日」）
- `verified_with` に書く版と系列（latest・stable）を決めて、報告に書く（共通の決まり §4）

## F5 出典の文と長く一致する箇所

元：design §6.1・§10.2、design-review DR-17

- **見るもの**：出典（特に公式の日本語版の文書）と、同じ話題の段落
- **確かめ方**：出典と本文を並べ、文の並び・言い回し・例が同じ所がないかを見る。公式の文書の訳文になっていないか（合わせてよいのは訳語だけ）
- **よくある失敗**：公式の日本語版の文を、言い回しごと使う。記事の例（数値・題材）をそのまま使う

## F6 出典の記録

元：design §6.8・§9.1・§10.5

- **見るもの**：`sources` の id と、`data/sources.d/<id>.yml` の `sources`・`domains`（形は `schema/sources.schema.json`）
- **確かめ方**：id があるか（検査：check_pages.py「sources の id」）。URL が転送先のものか（開いて確かめる）。題名・発行者・種類・言語・確認日が出典と合うか。出典のドメインの、AI の利用の指定の確認が `domains` に記録されているか（検査：check_noai.py）（検査：check_pages.py「AI の利用の指定」）。同じ URL が重なっていないか（検査：check_pages.py「出典の URL の重なり」）。断るドメインの出典がないか、あれば deny にあるか（検査：check_pages.py「断るドメインと deny」）
- **よくある失敗**：転送の前の URL を記録する（claude.com/blog と anthropic.com/engineering の記事は別の道へ転送される）。記憶で書いた URL

## F7 実在の人物・団体・第三者

元：design §6.12

- **見るもの**：人物・企業・製品・第三者のツール・書籍・講座の名前が出る所
- **確かめ方**：主張が一次資料で確かめられるか。否定的な文脈で名指していないか。自己申告に「自己申告」が添えてあるか。第三者のツールが推薦になっていないか、成熟度と確認日があるか。書籍・講座を評価していないか。AI Fluency（4D）を構成や用語に使っていないか

## F8 書かないもの

元：design §6.11

- **見るもの**：安全・攻撃・断られたとき・回避・近道に触れる所と、AI の文章の扱い
- **確かめ方**：共通の手引き §14 の各項に当たる記述がないか。攻撃の再現が無害か（送信・削除・秘密の読み取りを伴わない）。断られたときの書き方が、公式が案内する手段だけか
- 文書にない回避方法に気づいたら、方法を書かずに、共通の決まり §2 のとおりに指摘する

## F9 安全の既定

元：design §6.6、decisions 2026-11-03「安全の既定の勧め方」

- **見るもの**：段階ごとの安全の既定、サンドボックス・秘密・無人の実行・預かったデータに触れる所
- **確かめ方**：正本の節（`default-safety-settings#by-stage`）と食い違わないか。ほかのページが、段階ごとの既定を書き直していないか（正本を指しているか）。正本の節そのものは、決定（公式の既定〔auto モード〕を基準に限界を書く。任せる段階からはサンドボックスと秘密の読み取りの禁止、無人の実行は使い捨ての環境、預かったデータは契約のある面だけ）と照らす

## F10 大会の規則

元：design §6.13

- **見るもの**：大会の規則・版・AI の成績に触れる所
- **確かめ方**：版・確認日・類型・一次資料へのリンクが数値ファイルを経由しているか。確かめられない版が「未確認」か。条文の要約がないか。「過去問の練習には規則が適用されない」と断定していないか。atcoder.jp・codeforces.com の中身を根拠にしていないか

## F11 front matter と冒頭の食い違い

元：design §3.3・§6.4

- **見るもの**：front matter、要点、別名の行、報告の提案
- **確かめ方**：執筆者が変えたキーが sections・stage・updated・sources だけか（作る予定：check_pages.py「執筆者のキー」）。要点が summary・signs・prerequisites と食い違わないか。別名の行に aliases がすべてあるか（検査：check_pages.py「別名の行」）。front matter の直しの提案が、決まった形（id・key・before・after・reason）か
