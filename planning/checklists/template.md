# 雛形の動作のチェックリスト

- 版：2026-11-04 第1版（工程6a。試作〔工程7〕で確かめて確定する）
- 検証の共通の決まり（common.md）と一緒に使う。照らす規則は、共通の手引きの §7・§12 と、型の手引き
- 渡されるもの：`snippets/<id>/` の雛形と期待（`<名前>.expect.yaml`）、雛形を載せるページ
- 実機の確認の結果は `snippets/<id>/verified.yaml` に書く（版と系列〔latest・stable〕・モデル・OS・日付・対照の結果）。確かめたコマンドと Claude Code の版を報告に書く

## T1 置き場所と形

元：design §6.9・§8.7

- **確かめ方**：`snippets/<id>/<名前>.<拡張子>` と `<名前>.expect.yaml` がそろっているか。種類が `schema/site.yml` の `template_kinds` にあるか。本文が目印で写していて、写しが snippets/ と一致するか（検査：gen_site.py --check）。取り込みの記法（`--8<--`）や、手で写した雛形がないか

## T2 静的な検査

元：design §8.7・§8.6

- **確かめ方**：JSON・YAML の形、settings のスキーマの写し（schema/ にある。写した日と相当の版を見る）と、雛形が使うキーの許す一覧で見る（検査：check_templates.py）。スキルとサブエージェントの front matter の必須の項目を見る。スキルとサブエージェントは、手元で `claude plugin validate --strict` も流す
- **よくある失敗**：スキーマの写しが古く、新しいキーを書いた正しい設定を誤りとして落とす（公式の文書が案内する SchemaStore のスキーマは、新しいキーに遅れる）。許す一覧にないキーを使う

## T3 期待の形

元：design §8.7

- **確かめ方**：期待が「この操作が止められる」「この行が出る・出ない」の形か。置く場所（user・project・local）と条件があるか。本文の主張（何を止める・何を足す）と期待が対応しているか
- **よくある失敗**：出力の完全一致を期待にする。期待が本文より狭い（本文が止めると言う操作の一部しか試していない）

## T4 対照

元：design §8.7

- **確かめ方**：期待ごとに「雛形あり」と「雛形なし（同じフォルダ・同じモード・同じ依頼）」を流し、結果が期待どおりに違うかを見る（作る予定：check_templates.py --live）。雛形が読まれたことを `claude doctor` の出力でも確かめる
- **よくある失敗**：`-p` は承認の要る呼び出しを既定で拒むので、雛形がなくても「止められた」になる。対照のない「止められた」を合格にする

## T5 作者の環境から切り離す

元：design §8.7、decisions 2026-11-03「API キー」「危ない雛形を試す場所」

- **確かめ方**：子の環境が、許す一覧から作られているか（偽のホームの HOME・PATH・LANG・CLAUDE_CONFIG_DIR と、認証の token だけ）。`--strict-mcp-config` と、claude.ai のコネクタと自動メモリを読まない設定が付いているか。使い捨てのフォルダが /tmp の下にあり、上のどこにも CLAUDE.md がないか。Claude Code が 2.1.314 以上で、モデルと版を固定して記録しているか
- 環境に API キーやクラウドの事業者の認証の変数があれば、試さずに止めて報告する
- 偽の秘密と、壊れても困らない操作だけで試す。本物のホームや認証情報に触れる形は動かさない

## T6 読者の条件に合わせる

元：design §8.7

- **確かめ方**：expect.yaml の置き場所と条件に合わせて試したか。使い捨てのフォルダを専用の設定で信頼させたか（`-p` は、信頼していないフォルダの `permissions.allow` を使わない）。defaultMode を決める雛形で、モードを渡していないか

## T7 種類ごとの確認

元：design §8.7

- settings・hook・skill・subagent・claude-md：静的な検査と、対照つきの実機の確認の両方を行う
- prompt：実機で数回流した観察を、検証ノートの形で添える（合否にしない）
- other（点検表・記録表）：静的な検査だけを行う

## T8 安全とデータの雛形と、サンドボックス

元：design §6.9・§8.7、decisions 2026-11-03 方針 B2、2026-11-04「文書にない回避方法」

- **確かめ方**：動作を確かめていない雛形に、確かめていないことの注記がある（道具が書く）。`safety: true` の雛形には、自分の環境で確かめるよう促す一文がある（decisions 2026-11-04「雛形の動作確認」）
- サンドボックスの雛形では、次を見る
  - bubblewrap と socat で確かめたか
  - 雛形に `failIfUnavailable: true` が入っているか
  - WSL2 で Windows の実行ファイルを起動する経路が、期待にあるか
  - seccomp のフィルタを入れて確かめ、版を記録したか
- 回避された仕組みを守りとして勧める雛形は、不合格にする。回避の方法は書かない（共通の決まり §2）

## T9 この環境で試せない雛形

元：design §8.7

- **確かめ方**：使い捨てのコンテナ・/etc に書く管理設定・API キーが要る `--bare`・GitHub Actions の雛形が、本文に載っていないか（条件と概念だけになっているか）

## T10 記録と本文の版

元：design §8.7・§6.9

- **確かめ方**：`verified.yaml` に、版と系列・モデル・OS・日付・対照の結果があるか。本文の版の記述（確かめた版・要る最低の版）が、道具が書いたものか（手で書いていないか）
