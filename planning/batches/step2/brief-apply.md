# 工程2：調査資料への反映の担当への共通の指示

- 版：2026-11-03 v1.1（確かめた担当の指摘を受けて §2 の 6〜8 を足した）
- 担当ごとのファイルの割り当ては [README.md](README.md) の「反映」の表にある

## 1. 背景

工程2の7つの担当（R1〜R7）が、調査資料の主張を一次資料で確かめ、結果を `planning/research/22〜28` に書いた。調査資料（`planning/research/00〜11`）と `planning/requirements.md` は、GitHub の公開のリポジトリに入れる。その前に、確かめた結果を資料に反映する。決まりは `planning/decisions.md` の 2026-11-03「工程2（調査の補完）の結果への回答」にある。

## 2. 反映の決まり

1. **実在の人物・団体についての誤り**（報告で「誤り」「一部誤り」とされたもの）：文を直す。直した文の直後（表なら表の直後）に `> 【2026-11-03 訂正】…` と、何をどう直したかと根拠の報告の番号（例：research/25 の P2）を書く。直した文には、報告の「正しい内容」のうち一次資料で確かめたことだけを書く。人物・団体についての主張で「確かめられない」とされたものは、断定を外す形に直す
2. **否定的な文脈の実名**（古い助言の例・批判のコメント・失敗例・低い評価）：個人の名前（ハンドルを含む）と、その記事・投稿の URL を外し、内容と時期だけを残す（例：「ある個人の記事（2026-03）は…」）。外した所の直後に `> 【2026-11-03 訂正】否定的な文脈の実名を外した（decisions.md 2026-11-03「否定的な文脈の実名」）。` と書く。肯定的・中立の文脈の実名と URL は残す
3. **ほかの誤り**：原文は残す。直後（表なら表の直後）に `> 【2026-11-03 注記】…は誤り（または一部誤り）。正しくは…。research/2N の #M。` と書く。「確かめられない」とされた主張には `> 【2026-11-03 注記】…は一次資料で確かめられなかった（research/2N の #M）。` と書く
4. 「正しい」と確かめられたものには何もしない
5. **AtCoder の規則についての「確認済み」**（11 など）：以前の調査のセッションが atcoder.jp を読んで得たもので、この教材では根拠にしない、と注記する（decisions.md 2026-11-03「大会の規則の版」、research/24）
6. **2026-10-29 より後に古くなった点**（research/22 で「古くなった」とされたもの。旧 Max 20x → Ultra など）にも、`> 【2026-11-03 注記】…は 2026-10-29 より後に変わった。…（research/22 の #M）。` と付ける
7. **工程2で空白を埋めた点**（research/26 などで「空白を埋めた」とされたもの）には、`> 【2026-11-03 注記】…は research/2N の #M で確かめた。` と案内を付ける
8. **否定的な文脈の実名の決まりは、planning/ の公開するすべてのファイルに当てる**（research/21〜28 の報告と、planning/batches/ の報告を含む。decisions.md 2026-11-03「工程2：反映を確かめた後の判断」）。報告の中で確かめた証拠として挙げるときは「ある個人の記事（日付）」の形にし、名前と URL を外す。本人が自分の経験（失敗を含む）を振り返った記事は名前を残してよいが、本人の言葉として紹介し、順位などは「自己申告」と添え、評価の語（「沈み」「終わり」など）を使わない

## 3. 書き方

- 訂正と注記は短く、だ・である調の自分の言葉で書く
- **表の中や表の行の間に注記を挟まない**（表が二つに割れる）。表の直後に置き、行の番号や項目名で指す
- 見出し・節の番号・表の形は変えない。誤りに関係のない文は変えない（体裁の直しや言い換えをしない）
- 1つの誤りが同じファイルの何か所にもあるときは、それぞれに付ける。ただし同じ節の中の繰り返しは、1つの注記にまとめてよい
- 報告の文が分かりにくいとき、報告どうしが食い違うときは、直さずに自分の報告に書く

## 4. 進め方

1. `planning/batches/step2/brief.md` の §1 と、decisions.md の 2026-11-03 の工程2の2つの節（「工程2（調査の補完）の結果への回答」「工程2で確かめた事実（設計の前提）」）を読む
2. `planning/research/22〜28` の各報告の「結果の一覧」と「提案」から、担当のファイルに関わる行を探す（ファイルの番号や名前で検索してよい）。research/25（R4）は注記の文そのものを提案しているので、それを元にする
3. 担当のファイルを直す
4. 自分の報告を書く

## 5. 守ること

- 書いてよいのは、担当のファイルと、自分の報告（`planning/batches/step2/apply-<担当>.md`）だけ。ほかのファイルは変えない
- git の操作（commit など）をしない
- Web を開かない。報告の結果を写すだけにし、新しく調べない

## 6. 報告の形（`planning/batches/step2/apply-<担当>.md`）

1. 直したファイルと件数（訂正・注記・実名を外した、の別に）
2. 訂正と注記の一覧（ファイル・行か節・種類・根拠の報告の番号）
3. 直さなかったもの（理由）
4. 確かめていないこと

最後の返答（メインへの報告）は300字まで。
