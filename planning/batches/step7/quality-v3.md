# 工程7：v3（2人の流し方）のページの質の見比べ

- 日付：2026-11-05。担当：QC（読むだけ）
- 見分け方：pages/<id>/ に review.md だけがあるものが v3（agent-loop・block-with-exit-2・caves-when-pushed・experiment-log）。fix.md と verify-clarity.md があるものが v2（four-specifics を含む残りの10）
- 見たこと：辞書として引いたときに答えに着けるか、例と雛形が使えるか、言葉が分かるか、構成が型に合うか（clarity.md・card.md §11・concept.md §1）。事実と出典は見ていない

## 組ごとの見比べ

### 組1 symptom：instructions-ignored（v2）と caves-when-pushed（v3）
- 冒頭：どちらも要点の3項目で、答えのページかどうかが判断できる。v3 は「答えが変わった理由に新しい根拠があるか」を診断の0番に置いていて、切り分けの入口がはっきりしている
- 診断：v2 は面のタブごとに具体的なコマンド（`/context all`・`/doctor` など）まであり、とても厚い。v3 は原因が2つ（prevents と pitfalls）で、どの項目も「何を見るか・どう確かめるか」を持つ。症状の型の決まりは満たしている
- 弱み（v3）：「よくある形」の後半2段落が研究の要旨（迎合の仕組み、押し方による差）になっている。症状のページの節としては脇道で、仕組みは前提のページ（sycophancy）が持つ内容
- 判断例・雛形：どちらも4行の形を守り、雛形はそのまま使える。見劣りはない

### 組2 concept（原理）：request-vs-lock（v2）と agent-loop（v3）
- 冒頭と例：どちらも「何が分かるか」から入る。v3 の Before/After には足したものの注記があり、雛形もそのまま使える。判断例は2つで、どちらの候補も筋が通る
- 構成：v2 は「なぜ（比喩付きの図：扉の紙と錠）→ 何に効くか（原理の『縛る』・原因の『縛っていない』を名指す）」を持つ。v3 には「何に効くか」の節がない。本文は front matter の `principle: 確かめる`・`prevents: 確かめていない` を名指していない。concept.md §1 が「必ず持つもの」とする要素が欠けている
- v3 の図はループの図で、比喩はコンテキストの「広い机」だけ。ループそのものの比喩はない
- 誤解の節：v3 も4つの誤解を持ち、使える。ただし「台帳に行がある」で終わり、台帳を指していない

### 組3 recipe：keep-replies-in-japanese（v2）と experiment-log（v3）
- 分量：v2 は約44KB で、場面・設定・指示・フック・届かない所・測り方まで網羅していて、辞書としては長い。v3 は約26KB で、引いた人が手順と雛形に早く着ける
- 構成：v3 は「実験1件の流れ（各段の終わりの状態）→ 項目の表 → 雛形2つ → 確かめ方 → 繰り返すとき」で、レシピの型に合う。ただし手順の節は、執筆の段では抜けていた。検証の担当が「直す」として足している（review.md の1）
- 雛形：v3 の台帳の1件分と、依頼の雛形は、埋めればそのまま使える。v2 の Stop フックの雛形と比べても見劣りはない
- v3 の「先に整える守り」は、独立した節ではなく導入の2段落に入っている。読めば分かるので、軽い

| 中 | experiment-log（手順の節） | 執筆の段で、レシピの型の芯（手順）が抜けていた。検証が拾ったので、公開する版には残っていない | 上と同じ根から来ている。2ページに1つの割合で書き手が型の必須を落とし、検証が拾ったのは2件のうち1件。検証の担当が1人だと、漏れがそのまま残る |
| 小 | caves-when-pushed「よくある形」の後半 | 症状のページに、研究の要旨（仕組みの説明）が入り込んでいる | 束の材料の抜き出しに研究の要旨が多く、書き手が使い切ろうとした。カードに「症状のページは仕組みを持たない（前提のページを指す）」の一文がない（§11 の symptom の項には対処の本体を書かないとだけある） |

全体として、冒頭で答えに着けるか、判断例の4行、雛形がそのまま使えるか、言葉の定義、節を単独で読んで通じるかについては、v3 は v2 に見劣りしない。見劣りが出るのは「型が必ず持つもの」の漏れの1点で、これは流し方の作りから来ている。

## 流し方の直しの案（効きそうな順）

1. **束に、型の「必ず持つもの」と構成の目安を写す（使用量はほぼ増えない）**：束を作る道具が、`planning/guides/<型>.md` の §1（必ず持つもの）と §2（構成の目安）を、束の「1. ページ」の直後に数行で写す。書き手と検証の担当が、型の手引きを読まずに必須を見られるようになる
2. **write.md と review.md に「必ず持つものの対応」の欄を足す（brief を数行直す）**：write.md には、必ず持つものの1項目ごとに、それを持つ節の anchor を1行で書かせる。review.md には U6 の行を必ず置かせ、その対応が本文と合うかを確かめさせる。書いたものと突き合わせる形にすると、medium の1回の検証でも漏れを拾いやすい
3. **カード §11 の型の項に、一文ずつ足す（カードがわずかに増えるだけ）**：symptom には「仕組みや研究の要旨は前提のページを指し、症状のページには書かない」を足す。concept・feature には「台帳の行に触れたら、ledger を目印で指す」を足す。concept の「`principle`・`prevents` を本文で名指す」は、「何に効くか」の節に置く、まで書く

担当の数と effort は、今のまま（執筆 high・検証 medium の2人）でよいと見る。漏れは effort の不足からではなく、必須の項目が目に入る形で渡されていないことから来ている。

## 結論

- v3 で第一波を書いてよい。ただし、直しの案1と2を当ててから始めるのがよい。どちらも束の道具と brief の小さな直しで済み、1ページあたりの使用量はほとんど増えない。案3は、同じバッチでカードを直すときに一緒に入れればよい
- すでに書いた v3 の agent-loop には、「何に効くか」の節がない。ここはメインの判断で直す（このページの直しは、この報告の範囲の外）
