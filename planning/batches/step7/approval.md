案 A（節 freshness「確認日と期限切れの注意書き」）

> 確認日と期限切れの注意書きは、ページの情報がいつ時点のものかを示す。
>
> ページ上部の確認日のバッジは、出典を読み直した日と、そのとき使った版を示す。点検で影響がないと確かめた日があれば、バッジにポインタを置くと「点検」の日として出る。下書きのページには確認日がなく、「未検証」と出る。
>
> ページごとに期限の日がある。ページの確認日（読み直した日と点検の日の新しいほう）にページの期限を足した日と、ページが含む各数値の確認日に数値の期限を足した日のうち、早いほうを、道具が計算する。変わりやすさが高いほど、期限は短い。
>

## 2. 作者に決めてほしいこと

### 2-1 段階 reviewed・done と、確認日・「未検証」の意味

問い：2026-11-04 に「事実と出典の検証の担当を置かない」と決めたが、設計とすでにある文は、検証の担当を前提にしている。どの段階の名を、どの意味で使うか。

食い違いの所

- design §10.2：reviewed は「検証役が指摘0件か直しの差分を確かめ、`verified`（出典を読み直した日）を書く」。common §19 も同じ
- `tools/gen/config.yml`：reviewed の表示名は「検証済み」。how-to-use の節 stage の表も「出典を読み直して確かめ、確認日と版を書いた」と書いている
- いま行っている確かめ（2026-11-05 の決定）は、別の担当による分かりやすさの確認と直し、メインによる機械の検査だけ。出典を読み直す担当はいない。だから reviewed に上げる担当も、`verified` を書く担当もいない
- 「完成」の意味（design §10.2）は、メインが検査0件・未解決の指摘なしを確かめた段階で、事実の検証を含まない

案

- 案1（推す）：reviewed を残し、意味を「書いた担当とは別の担当が、分かりやすさを確かめ直した」に改める。表示名「検証済み」は事実の検証と読まれるので、「分かりやすさ確認済み」のような名に替える。`verified`（確認日）は、出典を読み直した日にだけ使う（鮮度の点検で読み直したページ）。理由：実際にしたことだけを段階の名にでき、読者に「事実を確かめた」と読ませない。完成のページにも「未検証」のバッジが出うるが、それは正確である。直す所：config.yml の表示名・design §10.2・common §19・how-to-use の表・ai-and-sources の done の表
- 案2：reviewed を使わず、draft → done の2段にする。理由：段が減って説明が簡単になる。ただし、分かりやすさを別の担当が確かめたかが画面に出ない。語彙（schema/site.yml）と配りの規則を広く直す

決まるまで、方針のページは reviewed の行を「準備中」にしてある。

### 2-2 「返事と直す時期は約束しない」と書くか

問い：誤りの報告の節（ai-and-sources の contact と、how-to-use の案 B）に、返事と直す時期を約束しないと明記するか。

- 案1（推す）：書く（今の下書きはこれ）。理由：守れない約束を書かない決まりに沿い、読者の期待もそろう
- 案2：何も書かない（窓口と書いてほしいことだけ）。理由：「約束しない」という言い方が冷たく見えうる。ただし何も書かないと、返事を期待させる

### 2-3 競技の規則のページで「読ませてよいか」に触れるか

問い：competition-rules は、読者が規則のページを自分の Claude に読ませてよいかに触れるか。

- 案1（推す）：触れない。事実の限界（1-4）だけを残し、「読ませてよいか」は ai-and-sources の noai の1文（「各サイトの規約に従う。この辞典は、その可否を判断しない」）に集約する。理由：方針の文を1か所に置けば、承認が1回で済み、食い違わない
- 案2：competition-rules にも書く。理由：読者が規則のページを開く場面で目に入る。ただし方針の文が2か所になる

### 2-4 台帳の「載っていない小技は有効とは限らない」（1-5 の (a)）

- 案1（推す）：残す。理由：使い方の案内で、約束でも保証でもない
- 案2：削る。理由：方針の文と見るなら、承認の範囲を狭くできる

### 2-5 免責の範囲

問い：ai-and-sources の別名に「免責」がある。本文は決まっている2文（安全を保証しない・法的な助言でない）と雛形の注意だけで、損害への責任を限る文は決まっていない。
