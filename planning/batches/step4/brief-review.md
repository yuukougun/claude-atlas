いまは工程3（設計）が終わったところで、設計書（`planning/design.md`）と目次（`planning/catalog/`。23分野・約360ページ）ができている。設計書はメインが書き、目次は12人の担当が分野ごとに書き、7人の担当が担当どうしの提案を統合した。この後、メインがあなたたちの指摘への対応を決めて第2版にし、ユーザーに決定の一覧を示して承認を得る。承認の後は土台作り（サイトと道具）と執筆に進み、目次は各ページの front matter の元になる。

あなたの仕事は、設計書と目次を**批判的に**読み、直すべき点を見つけることである。作った側は自分の誤りに気づきにくい。メインの判断や担当の判断を、そのまま正しいと受け取らないこと。設計書に理由が書いてあっても、その理由が要件・決定・材料に照らして成り立つかを確かめる。

## 3. 指摘の書き方

- 1つの指摘に1つの問題。どこが（ファイルと節、またはページの id）、何が問題か、なぜ問題か（要件・決定・材料の該当の箇所を示す）、どう直すか（案）を書く
- 重さを3段で付ける：**重大**（このまま進むと作り直しになる・要件や決定に反する・読者が目的のページに着けない）、**中**（品質や手間に効くが、後で直せる）、**軽**（表現や小さな不整合）
- 根拠のない印象は書かない。数えられるものは数える（道具で数えた方法も書く）
- 「確かめていないこと」を必ず書く（読んでいない範囲、道具で数えずに見当で書いたこと）
- 良い点を並べる必要はない。直さなくてよいと判断した論点を短く書くのはよい（ほかの担当と重なりを見分けやすくなる）
- ユーザーに判断してもらうべき点（要件や決定を変える提案）は、別の節に分けて書く

## 4. 観点

### R1 読者の立場

読者になったつもりで、目次から目的のページに着けるかを確かめる。

- 読者の課題を20以上つくる。場面（開発・文章・調べもの・データ分析・学習・コンテスト・チーム）と、段階（使う〜回す）と、面（アプリ・Claude Code・API）を散らす。`planning/research/00-content-report.md` §4（逆引きの73項目）から10ほど、それ以外を自分で10以上。自分でつくる課題は、開発の経験がある人が実際に困りそうなものにする
- 課題ごとに：読者が打ちそうな言葉 → 入口（逆引きの signs・題名・aliases・分野の並び）→ 着くページ → そのページの summary で用が足りそうか → 前提をいくつたどるか、を目次で追う。着けない・迷う・同じ問いに答えるページが複数ある・前提が深すぎる、を指摘にする
- 目次にない、読者が引きそうな題目（欠け）を探す。逆に、読者が引かなそうなページ（機能の紹介だけ・研究の紹介だけ）を探す
- 題名・aliases・signs が読者の言葉になっているか（機能名を知らない人も引けるか）
- 材料：`planning/catalog/*.yaml`（特に start・symptoms）、`planning/research/00-content-report.md` §4、`planning/research/04-community-japanese.md`、`planning/research/03-community-english.md`

### R2 要件と決定との照合

設計書と目次が、要件（requirements.md）とユーザーの決定（decisions.md）に合っているかを照らす。

- requirements の §1〜§11 と D1〜D20、decisions の各節の決定を一つずつ、設計書のどこで扱われているかに照らす。扱われていない・食い違う・決定より強く／弱く書かれているものを指摘にする
- 設計書の中の食い違い（節と節、設計書と catalog/README・schema/site.yml）と、設計書と目次の食い違い（例：境界の表と、実際のページの置き場所）
- decisions の「書き方の方針」（A1〜A7・B1〜B7）、「読者の前提」「安全の既定の勧め方」「鮮度の更新の承認」「実名」「断られたときの頼み直し」などが、目次の summary・notes・templates に反映されているか
- 材料：`planning/format-and-operations.md`（工程1の提案と決定の記録。design.md に引き継がれたはずのもの）、`planning/research/20-kyopro-atlas-retrospective.md`、`planning/research/21-step1-findings.md`

### R3 目次の質

目次そのものの構造と中身の質を見る。

- 粒度：重なるページ（分野をまたいで同じ問いに答えるもの）、薄すぎるページ（1節で足りるもの）、大きすぎるページ（分けるべきもの）。design §4.1 の規則に照らす
- 境界：design §4.2 の表と、実際の置き場所
- レベル：`level_evidence` が成り立つか。前提の段階の並び。「使う」が少なく短いか
- 優先度と第一波：必須の数と割合、第一波の数と中身が D10 と decisions（第一波に足すもの）に合うか、初版と第一波の規模が執筆の手間に見合うか
- 前提と関連：前提の鎖の深さ、関連の質（近いものから並んでいるか）、入ってくる道
- 文：summary が「何ができるか（何が分かるか）」を1文目に言えているか、変わりやすい値が summary・signs・title に入っていないか、題名の表記の揃い（design §6.2）
- 症状辞典：症状のページが「振り分け」になっているか（対処の本体を自分で抱えていないか）、signs が読者の言葉か
- 台帳：`outdated_advice` の逆リンク、台帳の行の過不足
- 材料：`planning/catalog/*.yaml`、`planning/catalog/registry.yaml`・`features.yaml`、`planning/batches/step3/` の担当の報告（catalog-C*.md・integrate-I*.md）

### R4 技術と進め方

設計書の §8〜§11（技術構成・鮮度・制作の進め方・リスク）が、実際に回るかを見る。

- 版と依存（Material 9.8 系・MkDocs 1.6.1・Python 3.12・Zensical の試験ビルド）、生成物と目印、骨格をビルドから外す方法、期限切れの表示、llms.txt
- 雛形の動作確認（静的な検査と実機の確認、専用の設定の置き場所と `--setting-sources`、API キーを使わないこと、無害な形、sandbox の道具）
- hooks と permissions（H1〜H4 と5つの決まり）。ユーザーの注意「過去に入れた縛りによって柔軟な対応が出来ず不適切な対処をすることも多いからそれを気をつけて」に照らして、縛りが強すぎないか、逆に抜けていないか
- 工程の順と終わりの条件、サブエージェントの使い方、バッチと再開、記録、commit と PR、使用量の見込み、ユーザーに確かめる場面（ユーザーは「確認が面倒くさいから俺が直接試すのは必要最低限にしたい」と言っている）
- 材料：`planning/research/28-tech-check.md`、`planning/research/20-kyopro-atlas-retrospective.md`、`planning/format-and-operations.md`、`tools/check_catalog.py`（目次の検査の道具）

## 5. 守ること

- 書いてよいのは自分の報告（`planning/batches/step4/review-<担当>.md`）だけ。ほかのファイルは読むだけにする
- git の操作をしない。Web を開かない（材料は調査資料と工程2の報告。事実の確かめが要る指摘は「確かめていないこと」に書く）
- `../kyopro-atlas` は読まない（工程1の振り返りは research/20 にある）
- 第三者を否定的な文脈で名指ししない（個人の名前を書かない）

## 6. 報告の形（`planning/batches/step4/review-<担当>.md`）

1. 見た範囲と方法（読んだもの、数えた方法）
2. 指摘の一覧（表：番号｜重さ｜場所｜問題｜根拠｜直し方の案）。重大から並べる。多くて40件
3. ユーザーに判断してもらうべき点（要件や決定を変える提案）
4. 直さなくてよいと判断した論点（短く）
5. 確かめていないこと

最後の返答（メインへの報告）は300字まで。重大・中・軽の件数を書く。
