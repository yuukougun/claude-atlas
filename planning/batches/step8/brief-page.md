## 1. 背景

claude-atlas は、Claude 全般を使いこなすための、辞書として引く日本語の教材である。リポジトリは `/home/yuuki/projects/kyopro2/claude-atlas`。いまは本制作（工程8）で、目次のページ（第一波と、残りの必須）を書き、確かめ、直す。

**使用量を抑える**：使用量は「道具の呼び出しの回数 × その時点の文脈の大きさ」で決まる。読むのは §2 の2つだけにし、ほかのファイルを探して小分けに読まない。細かい Edit を重ねず、検査を何度も流さない。

## 2. 読むもの（2つだけ）

1. そのページの材料の束：`state/packets/<id>.md`（冒頭にも「読むのはこの束とカードだけ」と書いてある。ページの front matter・つながるページの題名と要約と指せる節〔`id#anchor`〕・目次の materials と notes・data の該当の項目・出典の一覧・調査資料の該当の節の写し）
2. 執筆カード：`planning/guides/card.md`（書くときに要る決まりの要点を1枚にしたもの。目印の一覧・雛形と expect の形・型ごとの構成・報告の形も入っている）

手引きの全文（`common.md`・型の手引き）は、カードで決めきれないときだけ、カードの（common §N）が指す節を引く。束にないこと、変わりやすい値を数値の提案にするときだけ、一次資料を開く。**Web の取得は1ページで3回まで**。開く前に、新しいドメインは `uv run python tools/check_noai.py <URL>` で確かめる（`.claude/settings.json` の deny にあるドメインは開かない）。

## 3. 置き場所（ページの id を <id>、分野を <field> とする）

- ページ：執筆の担当が `stubs/<field>/<id>.md` を `docs/<field>/<id>.md` へ移し（`mv`。git は使わない）、stage を draft にして書く。書いたページは、メインがバッチの終わりに生成して、下書きの印付きで公開する
- 雛形：`snippets/<id>/<名前>.<拡張子>` と `<名前>.expect.yaml`（形はカード §10）。本文には `<!-- gen:begin snippet <id>/<名前> -->` 〜 `<!-- gen:end snippet <id>/<名前> -->` を置く。動作を確かめていなくても雛形は載せる。目次の templates の案を基本に、分かりやすさのために要る雛形は足してよい
- 図：`docs/img/<id>/`。ページごとの出典：`data/sources.d/<id>.yml`
- 報告：`planning/batches/step8/pages/<id>/` の下に `write.md`（執筆）と `review.md`（検証と直し）。数値の提案は `facts-proposal.yml`（カード §7 の形）

## 4. 役割（1ページに2人）

### 4.1 執筆（Sonnet 5.5・high）

1. 束とカードを読む（これ以外を探して読まない）
2. ページ、雛形、出典のファイルを書く。**ページは1回の Write で全文を書く**（細かい Edit を重ねない）。雛形は1つずつ Write する。目印の組は空で置く
3. 検査を流す：`uv run python tools/check_page.py <id>`（生成・参照の検査・書き方の検査をまとめて流し、指摘だけを出す）。指摘があれば直し、直した後にもう一度だけ流す。エラーを0にする
4. `write.md` を書く（§5）。「必ず持つものの対応」に、束の「型の必ず持つもの」の1項目ごとに、それを持つ節の anchor を1行で書く（持たないなら理由）

### 4.2 分かりやすさの検証と直し（Sonnet 5.5・medium。書いた本人とは別の担当）

1. 束とカードを読み、書かれたページと `write.md` を読む
2. `planning/checklists/clarity.md` でページを確かめる。U6（型の目安と、必ず持つもの）は必ず見て、write.md の「必ず持つものの対応」が本文と合うかを1項目ずつ突き合わせる（事実の正しさは確かめなくてよい。事実と出典の検証は置かない）。指摘を、重さ〔直す・直したほうがよい・軽い〕と場所と直し方で、頭の中か `review.md` の下書きに並べる
3. 「直す」と「直したほうがよい」の指摘を、ページに直す。**まとめて直し**（同じ節の指摘は1回の Edit にまとめる。節の大半を直すなら Write でその節を含む全体を書き直す）
4. 検査を流す：`uv run python tools/check_page.py <id>`。エラーを0にする。直した後に流すのはこの1回
5. 段階：指摘が0件（「直す」「直したほうがよい」が0）なら、ページの stage を reviewed にする。直したなら draft のままにする（直しの差分を別の担当が確かめていないため。decisions 2026-11-05「段階 reviewed の付け方」）
6. `review.md` を書く（§5）

描画・書き方・参照の検査は、2人が `check_page.py` で流すほか、メインがまとめて流す。

## 5. 報告の形（短く）

- `write.md`（執筆）：見出しは「書いたファイル」「必ず持つものの対応」「メインに判断してほしいこと」「提案」「検査の結果」「確かめていないこと」「使用量」。書くことのあるものだけを、1項目1〜3行で。「確かめていないこと」は空にしない。front matter のほかのキーの直しと、用語集などへの提案は、カード §10 の YAML の形で書く
- `review.md`（検証と直し）：指摘の表（番号｜重さ｜場所｜問題｜直したこと〔直さなかったなら理由〕。U6 の行を必ず置く）、検査の結果、「メインに判断してほしいこと」、使用量。1行ずつ短く
- 使用量は、道具の呼び出しの数と Web の取得の数を書く（分かれば）
- 最後の返答は100字までの日本語で、報告のファイルの場所と結果の要点だけを書く（報告の中身は返答に書かない）。ページと報告は Write で書く（Bash で書かない）。ページや報告のファイルの Write が道具に止められたら（「Subagents should return findings as text」など）、回り込まず、止められたことと、そのファイルの中身を最後の返答に書く（このときは100字の決まりより優先する）。メインが返答からファイルを作る

## 6. 守ること

- 書いてよいのは §3 の置き場所の、自分のページのものと、自分の報告だけ。共有のファイル（用語集・prh.yml・data/ の3つのファイル・catalog・手引き・チェックリスト・schema・tools）は直さず、報告の「提案」に書く
- git と gh の操作をしない（制作の印があるので、書き込みは止められる）
- 変わりやすい値を本文に手で書かない（数値の目印と、数値の提案を使う）。事実を記憶で書かず、束の材料か一次資料に基づいて書く
- 公開の約束・方針・ライセンスに関わる文は、作者の承認が要る（カード §13）。案を報告の「メインに判断してほしいこと」に書く
- 第三者を否定的な文脈で名指ししない
- 書かない・軽く扱うものはカード §12 に従う
