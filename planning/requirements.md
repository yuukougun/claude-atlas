## 1. 目的と前提

Claude 全般を使いこなすための、**辞書として引く**教材を作る。対象は claude.ai アプリ（Web・Desktop・Mobile）、Claude Code、モデルと effort、頼み方、API と SDK の概念、安全とデータ、組織での運用まで含む。

- **読者**：Claude や Claude Code をかなり使っているが、知識が足りず使いこなせていない人。リポジトリは public で公開し、いろいろな人が読む前提で書く
- **使われ方**：うまくいかなかった場面や、やりたいことをきっかけに引く。読み通す本ではない。症状や目的から逆引きでページに着き、冒頭の要点で用が足り、必要なら原理へさかのぼれる
- **重心**：機能の紹介ではなく判断を教える。「なぜうまくいかないか」「次に何を足し、どう確かめるか」「どこまで任せ、何を人が握るか」。評価リテラシー（何をもって良しとするかを定め、確かめ、守る力）寄りでよい
- **範囲の濃淡**：インストールや基本設定は詳しく書かず、公式へのリンクで済ませる。全コマンドや全設定キーの網羅もしない（公式リファレンスに任せる）
- **演習は作らない**：代わりに、例・図・比較表・Before/After・判断例・注釈付きのセッション記録・作者が試した検証ノートで分からせる（§6.6）
- **コンテスト**：コンテストでの使いこなしも扱うが、教材はコンテストに限らず AI エージェント全般に通用するものにする。コンテストは題材の一つとして置く（§4.3）
- **非公式であること**：Anthropic の公式の教材ではないことを、サイトの冒頭とフッターに明記する。Anthropic のロゴや公式の意匠は使わない

### 既存の教材との違い（調査で見つかった空白）

既存の書籍・講座・記事は、ほぼすべてが「導入 → CLAUDE.md → コンテキスト → 計画 → MCP・subagent・hooks・skills → CI」という機能順の一本道である。次の四つはほぼ空白で、ここをこの教材の核にする（根拠は `00` §1、`06`）。

1. **症状から引く索引**：「指示が守られない」「完了と言うが終わっていない」から原因と対処へ
2. **確かめ方と評価**：完了を証拠で決める、検証器を作って守る、偽の成功を見抜く、無人実行を信頼する条件
3. **日本語の出力品質**：英語に戻る、文体と表記の揺れを、お願いではなく仕組みで揃える
4. **古くなった助言の台帳**：撤回・置換された助言を、確認日と版付きで記録する

## 2. 形式と技術構成

形式は kyopro-atlas と同じにする。制作セッションは、まず https://github.com/yuukougun/kyopro-atlas を clone し、次を読んでから設計に入ること。

- `planning/requirements.md`・`planning/design.md`・`planning/decisions.md`・`planning/research/10-tech.md`（技術構成の調査）
- `schema/page.schema.json`（front matter の規則）
- `tools/README.md` と各スクリプト（骨格の生成、索引・逆引き・知識マップの生成、ページの検査）
- `mkdocs.yml`・`overrides/`・`CLAUDE.md`・`claude/`（claude.ai で教材を引かせる指示）
- `planning/catalog/`・`planning/checklists/`・`planning/style-guide.md`

引き継ぐもの：

- Material for MkDocs で静的サイトにし、GitHub Pages で公開する。スマホでも読める
- 本文は Markdown。ページごとの front matter（メタデータ）から、逆引き辞典・用語索引・知識マップ・ロードマップ・一覧・Claude 用の索引（`llms.txt`）を自動生成する
- 目次（catalog）→ 骨格（stub）→ 本文（draft）→ 検証（reviewed）→ 完成（done）の段階を持つ
- 生成と検査のスクリプトは MkDocs を import しない独立スクリプトにする
- 本文の表記を textlint（と prh）で検査する
- 出典にする前に、サイトが AI の利用を断っていないか（noai の指定）を確かめる

引き継がないもの（AtCoder 固有）：

- 問題の台帳、AtCoder Problems の参照、difficulty と frequency の計算、C++ のコード片のコンパイル検査

代わりに要るもの：

- **設定や雛形の動作確認**：本文に載せる settings.json・hook・skill・subagent の定義・CLAUDE.md の例は、可能な限り実際に動かして確かめる（kyopro-atlas のコード片のコンパイルに当たる）。確かめた版を記録する
- **鮮度の仕組み**：確認日と版のメタデータ、数値を集めたファイル、点検の手順（§7）

ページの長さに上限は設けない。図は静的な SVG か Mermaid を基本とし、動く図はコンテキストの埋まり方のように、動かすことで分かりやすくなる箇所に限る。

## 3. 背骨：全ページに通す考え方

### 3.1 四つの原理と一つの比例則

| 原理 | 一文で | 例 |
| --- | --- | --- |
| **見せる** | 必要なものを見せ、余計なものは片付ける | 具体的な依頼、資料、CLAUDE.md、/clear、handoff 文書、subagent での隔離 |
| **確かめる** | 完了は自己申告でなく証拠で決める | テスト、画面での確認、独立したレビュー、引用の照合、検証器、/goal、Stop hook |
| **縛る** | 例外を許さないものは仕組みに任せる | hooks、permissions の deny、sandbox、managed settings、textlint |
| **握る** | 何を良しとするか・採るか・やめるか・中核の理解は人が持ち続ける | 評価の定義、採否と撤退の判断、説明できないものは採らない、規則の確認 |

**比例則**：任せる幅を広げるほど、確かめる仕組みと封じ込めを強める。どの段階でも、握るものは手放さない。

最初の三つは、Claude Code の公式 Best practices の考え方（失敗の四分類、指示を「判断されるもの」と「必ず実行されるもの」に分けること）を整理し直したものである（`00` §1〜2）。四つ目の「握る」は、コンテストの補完調査（`10` 第4章・第5部）から加えた。AI が置かれたループを何でも加速するので、評価が誤っていれば誤りも同じ速さで増幅される、という観察が根拠である。

用語は独自の言葉を見出しにし、公式の言葉を併記する（例：「お願いと鍵」＝非決定論的な指示と決定論的な制御）。Anthropic の AI Fluency（4D）は CC BY-NC-ND なので、参考文献として触れるだけにし、構成や共通言語には使わない。

### 3.2 失敗の原因は二つの軸で持つ

**Claude の側：六つの「ない」**（`00` §2）。症状ページはこの順に、安く確かめられるものから問う。

| | 原因 | 典型的な症状 |
| --- | --- | --- |
| ① | 見えていない（情報不足） | 意図と違う、古い情報、存在しない API |
| ② | 散らかっている（情報過多・失敗の残骸） | 長い会話で忘れる、堂々巡り、圧縮後に約束を忘れる |
| ③ | 確かめていない | 完了の偽装、テストの改ざん、引用の誤り |
| ④ | 縛っていない | CLAUDE.md の無視、英語への回帰、破壊的な操作 |
| ⑤ | 合っていない（モデル・effort・面・プラン） | すぐ上限、止まりすぎ・やりすぎ、遅い |
| ⑥ | 境界がない | 秘密の流出、悪意ある入力に従う |

**人の側：五つの落とし穴**（`10` 第3章・第5部）。原因の性質が違うので、①〜⑥に⑦として足さず、別の軸にする。

| | 落とし穴 | 一言で |
| --- | --- | --- |
| ア | 預けすぎる（過度依存） | 判断まで AI に任せ、確かめなくなる |
| イ | 同意を根拠にする（迎合の受け取り方） | AI が賛成したことを正しさの証拠にする |
| ウ | やめられない（サンクコスト） | 費やした分だけ方針を捨てにくくなる |
| エ | 体感を信じる | 速くなった・良くなったという感覚が実測とずれる |
| オ | みんなの案になる（均質化） | AI の案を起点にすると発想が似通う |

五つの現象は、それぞれ隣接分野の研究で確認されている（根拠：強）。ただし「AI に頼って負けた経験の大半がこの重なりで説明できる」という統合の主張は誰も検証していない（根拠：弱）。総論のページではこの区別を書く。

### 3.3 レベルは「委任の段階」

レベルは機能の難しさでも使用期間でもなく、どこまで任せられるかで定義する。kyopro-atlas の level が名前の列挙なので、名前で持たせる。

| level | この段階の読者 | 上がる条件（ロードマップの節目） |
| --- | --- | --- |
| 使う | 対話で頼み、返答を読んで使う | 期待外れの原因を「見えていない／散らかっている」と言い分けられる |
| 整える | 頼み方・資料・会話の長さを整え、結果を確かめて直す | 完了の条件と確かめ方を、依頼に含めて渡せる |
| 任せる | 計画させてから任せ、長い作業を途中で舵取りする | 二回同じ注意をしたら、仕組みに移すと判断できる |
| 仕組みにする | CLAUDE.md・skills・hooks・permissions・MCP・plugins で常設化し、共有する | 無人で動かす前の五つの問いに答えられ、検証器を自分で確かめられる |
| 回す | 並列・無人・定期・プログラムから動かす | ― |

- 読者層から、「使う」のページは少なく短く、「整える」〜「仕組みにする」を厚くする
- 比例則に従い、上の段のページには対応する「確かめる」「縛る」のページを前提（prerequisites）として持たせる。生成されるロードマップが「任せる幅を広げる順」になる
- 「どの段階でも人が握るもの」の一覧を、ロードマップの冒頭に置く
- 補完調査の第25章にある「ゲートつきで任せる範囲を広げる」考え方は、この「上がる条件」に取り込む（カリキュラムとしては作らない）

## 4. 分野の構成（初期案）

### 4.1 切り方

分野は製品ごと（アプリ編・Claude Code 編・API 編）ではなく、**活動ごと**（頼む・整える・確かめる・評価する・縛る・任せる・握る・払う）に切る。製品ごとに切ると「上限に当たる」「事実を確かめる」のような共通の話が三か所に散るからである。面ごとに手段が違う話は、ページの中のタブ（アプリ／Claude Code／API）で並べる。面に固有の操作だけを面別の分野に置く。

並び順は、補完調査の「評価と実験を、エージェントの運用より先に教える」という考えを取り入れ、確かめる・評価する・縛るを、任せるより前に置く。人の側の分野は、任せるの後に置く（使い込むほど問題になるため）。

### 4.3 新しく立てる3分野と、分けた分野のページ候補

**10 eval 評価と実験**（補完調査 第3部。「確かめる」を一段深くする）

- 検証器が問題を定義する（総論：Claude は置かれたループを何でも加速する）
- 検証器の三条件（正しい・書き換えられない・本番を代表する）
- 検証器そのものを確かめる（red/green、手で計算したケース）
- 評価指標そのものを確かめる
- 答えの分かる遅い解と比べる（差分テスト・オラクル）
- 選択圧：良かった版を選び続ける罠
- ロックボックスと hold-out（人だけが持つ検証用データ）
- 実験台帳（仮説を先に書く・提案者・分母・評価器の版）
- 平均ではなく層別と最悪ケースで見る
- 上界を測って「限界です」を反証する
- 変更が効いたかを測る（小さな eval）※ `00` 分野09 から移す
- 体感と実測 ※同上
- /insights と /usage で振り返る ※同上

**09 verify 確かめる** に足すページ：見た目は品質の証拠ではない／AI に書かせたテストの落とし穴／別のモデルに第二の意見を求める（一致は証拠にならない）／良すぎる結果を疑う

**14 judgment 判断と理解を守る**（補完調査 第3章・第5部）

- 人の側の五つの落とし穴（総論。根拠の強さの区別を書く）
- 判断を預けすぎる（過度依存）：検証が安いほど依存が減る理由
- 迎合させない聞き方（好みを伏せる・並べて比べる・新しい文脈で批評させる）
- 同意は根拠に数えない（AI レビュアーの一致を含む）
- やめどきを先に決める（撤退基準を着手前に数値で書き、実装者以外が判定する）
- AI の案は「みんなの案」（均質化）
- 頼む前に自分で考える（AI には問い・反論・道具を頼む）
- AI で新しい技術を学ぶ（生成させた後に理解を確かめる）
- どこまで理解を手放してよいか（中核と周辺）
- 振り返りで AI に評価させない（集計係にとどめる）
- 失敗を仕組みに戻す（ポストモーテム）

**20 contest コンテストで使う**（題材別。kyopro-atlas の「題材別」ページと同じ位置づけ）

- AI はコンテストでどこまで来たか（確認日付きの囲み）
- 規則はなぜ割れるか：禁止・部門分け・開示の三類型と、規則の確認表
- 形式と AI の効き方（検証器の速さと信頼性・典型度・テキストで完結するか・環境の制約・期間）
- 形式別の早見表（短時間のアルゴリズム／長期ヒューリスティック／性能改善型／CTF／データ分析型／ハッカソン／対戦型・長期チーム戦）
- 練習と本番の使い分け（AI を禁止する大会に向けた練習を含む）
- 考察の型（観察 → 仮説 → 小さな実験）
- 形式別の評価器（テスタ・ベンチマーカー・CV・flag・対戦場）
- 実験の回し方（ケース数・集計・パラメータ・勝率に必要な試合数）
- 探索コードと高速化の点検表
- 本番の運用（開始直後に検証器を立てる・終盤は凍結する・AI なしでも提出できる状態を保つ）
- チーム戦の運用（長期・対戦型）
- 振り返りと上位解法の読み方

コンテスト編の置き方の理由：

1. 補完調査の論点の約3分の2はコンテスト以外でもそのまま使える。独立した部にすると、一般の読者が評価や判断の中心の内容をコンテストの章で読むことになる。一般化できるものは各分野に分けて置く
2. 規則や成績は月単位で古くなる。1分野に集めると、確認日の管理もそこに集中でき、原則のページを古くなる情報から切り離せる
3. 「AHC で…」と引く読者には、この分野が入口になり、評価や判断のページへリンクでたどれる
4. 練習と本番の使い分けは、各章に散らすと見落とされる

あわせて、各分野の例にコンテストの場面を混ぜる。front matter の `scenes`（§5.2）に「コンテスト」を持つページを、この分野から一覧で引けるようにする。対戦型や数か月のチーム戦に関する内容は、直接の研究がなく隣接分野からの類推なので、本文で「類推」と明記する。

### 4.4 ほかの分野に足すもの（主なもの）

`11` 第1節に全件がある。主なものだけを挙げる。

- **13 delegate**：任せないもの（評価・採否・撤退・中核の理解）／そのタスクは AI に向いているか（五つの軸）／開いた改善ループの罠／伴走と委託／長時間ジョブの進捗ログを設計する／仮説ごとに並べて、同じ物差しで比べる
- **18 recipes**：仕様を自分で読み、AI に誤読を指摘させる／観察の道具を作らせる／検証環境・テスト基盤を作らせる／プロパティテストを書かせる／失敗する入力を縮めるスクリプトを書かせる／退行の原因を git bisect で探させる／性能改善を頼む（プロファイルが先・出力の一致と実測）
- **19 team**：役割を分ける（書く人・承認する人・疑う人）／リスク段階別の承認（AI の承認を人の承認に数えない）／案出しは独立に、突き合わせは AI に／決定を文書に残す／チームで迎合と過信を防ぐ／レビューの観点を育てる
- **12 safety**：AI 利用の開示と出所の記録／課題資料・問題文に仕込まれた指示／預かったデータ・規約付きのデータを AI に渡してよいか
- **21 symptoms**：評価のおかしさに自分からは気づかない／同じ確認のループにはまる／環境や道具が壊れたと言い出す／誤りを認めずに言い張る／直し続けて方針を疑わない（またはすぐ撤退を勧める）
- **11 enforce**：評価資産を凍結し、触れる範囲を絞る／判断を決定論的なスクリプトに移す
- **16 cost**：課金経路を確かめる（API キーとサブスクリプション）／AI が使えないときの備え（障害・上限）

## 5. ページの型とメタデータ（初期案）

### 5.1 ページの型

| type | 用途 | 例 |
| --- | --- | --- |
| concept | なぜそうなるか | コンテキストウィンドウと注意の予算 |
| feature | 機能の使いどころと注意点 | Stop hook で「終わらせない」 |
| symptom | 症状 → 原因 → 対処 | CLAUDE.md や指示が守られない |
| comparison | 似たものの使い分け | Skill と Subagent の違い |
| recipe | 用途別の進め方 | バグを直す |
| judgment | 人の側の判断を守る | やめどきを先に決める |
| ledger | 台帳・年表・対応表 | 古くなった助言台帳 |
| guide / hub | 入口、案内、題材の一覧 | この辞典の引き方 |

ページの構成は固定のテンプレートにしない。全ページ共通なのはメタデータと冒頭の要点だけにする（kyopro-atlas と同じ方針）。

### 5.2 front matter

kyopro-atlas のキー（`id`・`title`・`type`・`field`・`order`・`level`・`prerequisites`・`related`・`summary`・`signs`・`aliases`・`sections`・`stage`・`updated`）を引き継ぎ、次を足す案である。最終的な形は制作セッションが schema として決める。

| キー | 例 | 目的 |
| --- | --- | --- |
| `signs` | `{type: symptom / goal / situation, text}` | 逆引き辞典の生成。症状・やりたいこと・状況の三種 |
| `surfaces` | `[app, claude-code, api]` | 面のタグ。タブ表示と一覧 |
| `principle` | `[見せる, 確かめる, 縛る, 握る]` | 原理への逆リンク |
| `prevents` | `[①, ④]` | Claude 側の原因。症状ページの診断と逆引き |
| `pitfalls` | `[イ, ウ]` | 人の側の落とし穴 |
| `scenes` | `[業務, 学習, 文章, コンテスト]` | 例がどの場面のものか。題材別の一覧 |
| `enforcement` | お願い／鍵 | 機能ページ。比較表の自動生成 |
| `context_cost` / `load_timing` / `survives_compaction` | 常駐／使うときだけ、など | 機能ページ。公式の比較表と同じ列 |
| `maturity` | GA／beta／research preview／experimental | 成熟度のバッジ |
| `volatility` | 低／中／高 | 点検の周期（§7） |
| `verified` / `verified_with` | `2026-10-29` / `{claude_code: 2.1.312, models: [...]}` | 確認日と、確かめた版 |
| `tracks` | `[/goal, permissions.defaultMode]` | 依存するコマンド・設定・機能名。変更の検知 |
| `outdated_advice` | `[think-hard]` | 古くなった助言台帳への逆リンク |
| `sources` | `{type, url, checked}` | 出典の種類（公式文書・公式ブログ・CHANGELOG・実践者・研究）と確認日 |

### 5.3 冒頭の要点

kyopro-atlas の「要点」の囲みを引き継ぐ。「何ができるか（概念ページなら何が分かるか）」「いつ引くか」「前提」を基本にし、計算量の代わりに、ページに応じて「強制力（お願いか鍵か）」「確認日と版」を出す。その上にバッジの列（レベル・原理・成熟度・変わりやすさ・確認日）を置き、読者が本文を読む前にどれだけ信用してよい情報かを判断できるようにする。

## 6. 内容の方針

### 6.1 古くなる速さで分ける

| 層 | 例 | 古くなる速さ | 扱い |
| --- | --- | --- | --- |
| 原理 | 基礎・背骨・頼み方の原則・評価・判断 | 年単位 | 本文に書く |
| 機能の使い方 | hooks・skills・/goal の使い方 | 月単位 | 本文に書き、確認日と版を付ける |
| 数値・既定値・名称 | 料金・上限・既定のモデルと effort・research preview の機能名・大会の規則と成績 | 週単位 | 本文に直接書かず、数値ファイル（例：`data/facts.yml`）にまとめ、出典と確認日を付けて参照する |

### 6.2 根拠の強さを本文で示す

- 研究や数値を根拠にする主張には、根拠の強さ（強・中・弱）を付ける。基準は補完調査に合わせる。強は RCT・メタ分析・大規模実験・主催者の規約や公式記録、中は小規模研究・企業の一次報告・複数の実務家の一致、弱は単独の経験談・二次報道・立場表明
- 隣接分野からの類推は「類推」と明記する
- 研究の結果は、どのモデル・どの世代の結果かを書く。補完調査が引く研究の多くは GPT 系や旧世代の Claude の結果である。「どのモデルでも起きる構造的な現象」として扱い、「現行の Claude の傾向」としては書かない
- 小さな研究の結果は「傾向」として、標本の大きさを添える
- 実践者の間で意見が割れる論点は、「公式の立場」「実践者の幅」「この教材の推奨」の三段で書く（`00` §1 に12の論点の表がある）

### 6.3 書かないもの・軽く扱うもの

軽く扱う（公式へのリンクで済ませる）：

- インストールと OS 別の設定、全コマンド・全設定キー・全 hook イベントの網羅、API のパラメータとコード例
- research preview や実験的な機能の操作手順（成熟度のバッジ付きで概念だけ）
- 周辺製品（Claude Design・Science・Duet・Office アドインなど）は一覧ページだけ

書かない（`00` §5、`10` 付録B）：

- 根拠の弱い数値を主張の根拠にすること（「◯倍速くなった」という自己申告、推測された隠しキーワード、出所のはっきりしない経験則の数値）。使うなら「経験則」「自己申告」と明記する
- 安全装置を外す近道を勧めること（`--dangerously-skip-permissions` の普段使いなど）
- 特定の個人の構成を標準として示すこと（反対意見と並べる）
- 「think hard」「CRITICAL: You MUST」のような呪文を効く手法として教えること
- 日付と版のない機能・既定値・価格・利用枠の説明、日付と版のない「この大会では AI が使える／使えない」という断定
- AI 単独の優勝事例を「真似る方法」として紹介すること（勝因の構造だけを取り出す）
- 「考察は人間にしかできない」という断定
- 自律ループで戦略そのものを改善させる手順（仕様の決まった実装タスクに限った、停止条件つきの反復だけを扱う）
- 「複数の AI レビュアーが一致したから正しい」という判断
- 検証済みの数値のない高速化の成功例、ベンダーの効果数値を中立の事実として扱うこと
- モデルの「性格」を固定的な事実として教えること（自分の環境で観察する対象として扱う）
- プレモーテムを効果が実証された手法として紹介すること
- AI を禁止する大会を目指す読者に、本番での利用を前提にした手順だけを教えること

### 6.4 実在の人物・企業・第三者ツール

- 実在の人物と企業の事例は、出典付きで名前を出してよい。自己申告の数値は「自己申告」と書く
- 第三者のツールやプラグイン（cc-sdd・Serena・ccusage など）は、考え方の例として名前を出すだけにし、推薦リストにはしない。成熟度と確認日を付ける

### 6.5 規則（学校・組織・コンテスト）

- 規則が割れる理由と類型（禁止・部門分け・開示）、確認すべき点のチェックリストは本文に書く
- 個別の規則の条文の要約は載せない。日付と版付きのリンクと、「何を確かめるか」だけを書く
- AtCoder の規則は過去問の練習には適用されないなど、練習と本番で扱いが違う点は明記する

### 6.6 演習の代わりの見せ方

| 見せ方 | 内容 |
| --- | --- |
| Before/After | 「Instead of / Try」の対比。何が足されたかを注記する。面ごとのタブで同じ原理の書き換えを並べる |
| 比較表 | front matter の属性から自動生成する（手書きの表と本文の食い違いを防ぐ） |
| 比喩付きの図 | 広い机（コンテキスト）、毎回読み直す受験者（全履歴の送信）、積み木（prompt caching）、議事録だけ残す（compaction）、別室の部下（subagent）、山を張る受験生（ハルシネーション）、お願いと鍵 |
| 注釈付きのセッション記録 | 実際の（または再構成した）やり取りに番号付きの注釈を付ける。日英どちらの既存教材にもなく、差別化の余地が最も大きい |
| 判断例 | 状況・迷う候補・選んだもの・理由の四行。答えを伏せない |
| 検証ノート | 作者や制作セッションが実際に試した結果を、日付と版付きで載せる。データがない論点（日本語と英語の比較、迎合の自己実験など）はこの形にする |
| 診断チェックリスト | 症状ページに、原因を安く確かめられる順に並べた確認欄を置く |
| 雛形 | 設定・CLAUDE.md・プロンプトの雛形を折りたたみで置く（§10.3 の不具合を直してから） |

補完調査の演習の形をした論点（自己実験、自分の敗戦の分析、数か月のカリキュラム）は、判断例・検証ノート・振り返りのチェックリストに作り替える。

### 6.7 頼み方で調査の間に食い違いがあった点の統合方針

| 論点 | 統合した書き方 |
| --- | --- |
| 成果で頼むか、狙いを具体的に書くか | 目的と完了条件は成果で示し、着手点（どこを・何で測るか）は具体的に書く |
| 選択肢を出させるか、最初は AI の案を見ないか | 答えを選ぶ場面では選択肢と推奨案を出させる。独自性が要る発想の場面では、先に自分の案を書いてから AI に問いと反論を求める |
| 原文を見せるか、要約して渡すか | 理解と確認のためには原文を見せる（誤読の検出に使う）。発想の段階で自分の言葉の要約を先に作る、という補完の助言は「類推・弱」として添える |
| 禁止事項を CLAUDE.md に書くか | 例外を許さない禁止は deny ルールや hook で強制し、CLAUDE.md には理由と相談の基準だけを書く（二層） |

## 7. 鮮度と品質を保つ仕組み

Claude Code は 2026年1月〜10月末に約235版が出た（npm の公開記録。v2.0.77 → v2.1.312）。鮮度の管理を後付けにしない。

- **変わりやすさ**：`volatility` に応じて点検の期限を決める（目安：低 365日、中 90日、高 30日）。期限を過ぎたページには、ビルド時に「確認から N 日経っている」という注意書きを自動で出す
- **数値ファイル**：料金・上限・既定値・大会の規則と成績は1つのファイルにまとめ、各項目に出典と確認日を持たせる。公式の情報同士が食い違うときは、両方の出典を残し「食い違いあり」と書く（調査中に3件見つかっている。§10.1）
- **点検の手順**：前回確認した版以降の Claude Code の CHANGELOG、Help Center とプラットフォームのリリースノートの差分を読み、出てくる語を各ページの `tracks` と `aliases` に照らして、影響を受けるページの一覧を出す。影響があったページは出典を読み直し、人が承認してから `verified` を更新する。制作者用の skill として作り、定期実行は任意にする
- **リンク**：公式文書は移転が多い（docs.anthropic.com → code.claude.com など）。リンク切れとリダイレクトの検査を点検に含める
- **外からの報告**：「この情報は古い」という報告を受ける issue のテンプレートを置く
- **書き方の検査**：本文は だ・である調。textlint と prh で表記ゆれを検査する（「日本語で使う」分野で教える方法を、教材自身にも当てはめる）
- **書いた本人に採点させない**：検証は別のサブエージェントが行う。主張と出典の照合、数値が数値ファイルを経由しているか、根拠の強さの表記、版依存の記述に確認日があるか、分かりやすさを確かめる

この教材の制作そのものが、教材の教える「確かめる」「縛る」「握る」の実例になる。制作で使った CLAUDE.md・skills・hooks・サブエージェントの分担と、その結果は、`planning/decisions.md` と `planning/progress.md` に残し、後で用途別レシピや注釈付きのセッション記録の素材にする。

## 8. 使い続けるための仕組み

- **Claude 用の索引**：`llms.txt` と索引ファイルを、各ページのメタデータから自動生成する（kyopro-atlas と同じ）
- **claude.ai で困りごとを相談する**：claude.ai の Projects にこのリポジトリをつなぎ、困りごとを相談すると、逆引き → 症状ページ → 対処の順に教材を引いて答える、という手順ファイルとプロジェクトの指示を `claude/` に置く。答えには根拠のページ・節の URL と確認日を付ける。確認日が古い項目は「公式で確かめること」と添える。これ自体が「Projects の使い方」の実例ページにもなる
- **制作者用の skill**：鮮度の点検（§7）と、事例の記録（作者が出会った困りごとを1件1ファイルで `notes/` に記録する。git の追跡外。検証ノートと注釈付きセッション記録の素材にする）
- **入れないもの**：進捗チェック（「理解した」の記録）と確認問題は、初版では入れない
- **第二版以降の候補**：読者が自分の Claude Code から教材を引ける plugin として配布すること

## 9. このセッションで決めたこと（理由つき）

| # | 決めたこと | 理由 |
| --- | --- | --- |
| D1 | 背骨は「見せる・確かめる・縛る・握る」の四原理と比例則 | 公式の考え方の整理に、補完調査の「評価と採否は人が握る」を加えると、評価リテラシー寄りの方針と、コンテスト以外の業務の両方に通る |
| D2 | 失敗の原因は「Claude 側の六つ」と「人の側の五つ」の二軸にする | 原因の性質と対処の種類が違う。①〜⑥に⑦として足すと、症状ページの診断の順序（安く確かめられる順）が崩れる |
| D3 | 新しい分野「判断と理解を守る」を立てる | 人の側の論点は頼み方・確かめる・組織に散らすと、まとまりが見えなくなる。補完調査の中で一般化できる部分の中心でもある |
| D4 | 「確かめる」を「確かめる」と「評価と実験」に分ける | 補完調査の分を足すと約30ページになる。完了の確かめ方と、検証器を作って実験を回す話は、読者の段階が違う |
| D5 | コンテストは、一般化できるものを各分野に分け、固有のものだけを題材別の1分野に集める | §4.3 の四つの理由 |
| D6 | 大会や学校の規則は、類型と確認表を本文に置き、条文はリンクにとどめる | 規則は月単位で変わる。補完調査の要約にも一次資料と合わないものがあった |

| D17 | 進捗チェックと確認問題は初版では入れない | 演習を作らない方針と、引く辞書という使われ方に合わせる |
| D18 | 鮮度の点検は、制作者用 skill による差分の洗い出しと人の承認で行い、外からの報告は issue のテンプレートで受ける | 点検の手間を減らしつつ、更新の判断は人が握る |
| D19 | ライセンスは本文を CC BY 4.0、スクリプトなどのコードを MIT にする案とする | 引用と再利用を広く許す。公開前に作者の確認を得る（§11 の最初の質問） |

## 10. 既知の誤り・確かめるべきこと

### 10.1 調査資料（`00`〜`06`）の中の誤り・不足

照合の過程で、主報告と下調べノートにも直すべき点が見つかった（`11` 第3節 3-2・3-3）。本文に使う前に直すこと。

- 下調べノート `01` の冒頭の要約にある「コンテキストはすぐ埋まり、埋まるほど性能が落ちる」が中心という書き方は古い。現行の Best practices は、これを「もうやめてよい助言」に入れている（1M と自動圧縮。/clear は質とコストのため）
- output style の組み込みは4種（Proactive・Concise・Explanatory・Learning）ある
- Stop hook は、ツール呼び出しを挟まずに8回続けてブロックすると上書きされる（環境変数で変えられる）
- `Write(path)`・`NotebookEdit(path)`・`Glob(path)` の権限ルールは受け付けられるが、何にも当てはまらない。パスで縛るときは Edit と Read で書く
- Read と Edit の deny は、組み込みのツールと認識できるシェルコマンドにしか効かず、任意の子プロセスには効かない。秘密情報と評価資産は sandbox と併用する
- 圧縮の後に残るものの完全な一覧は、公式の context-window のページにある（`11b` 第2節 #5）。主報告が「空白」としていた点
- agent teams の「約7倍のトークン」は、teammate が plan mode のときの値
- Sonnet 5.5 の既定 effort は、API の文書と Claude Code の文書で食い違う（公式同士の食い違いの3件目）
- 「think hard」は「認識されない」「ただの文字列」ではなく、「effort を上げるキーワードとしては効かない、普通の文として扱われる」が正確
- Claude Code のリリース数は、期間を明記した一つの数字にそろえる（「1年で約310回」と「1〜10月で約235版」が並んでいる）

### 10.2 補完調査（`10`）の疑わしい主張

`11` 第4節に67件ある。読者が行動の根拠にしそうなものを挙げる。どれも一次資料で確かめるまで断定で書かない。

- **長期 AHC の2部門制**：「AHC074 から」「20261026版」「他人の非公開ハーネス以外は自由」は一次資料で確認できなかった。確認できた案の段階の規定は、AHC 専用ツールや自動化システムを禁止しており、含みが違う
- **Codeforces の規則**：本文は断定しているが、補完自身の付録Cは「一次規約は未確認」としている
- **AtCoder の「2026年10月に試行」**：出典が見つからない
- **AWTF 2026 の「Psyho 本人が粉砕された」**：誤認の疑いが強い。報道では Psyho は不参加
- **「AI はほぼ全形式でトップに並んだ」**：補完自身が挙げる反例（難しい CTF で0問など）より強い言い方
- **Claude 以外のモデルの結果が Claude の結果のように読める箇所**：可視テスト97%・非公開テスト0%の C コンパイラは Codex の例。偽の高速化の例は GPT 系。「止まる権利」の効果は Claude Opus 4.1 ではずっと小さいと論文にある
- **古い版の数値・誇張**：SWE-fficiency は論文の古い版の数値。「採点を直しただけで42%→95%」は scaffold の変更も含む
- **小さな研究の断定**：スキル形成の研究の型は各群4人程度。「使い込むほど強まる」は、補完自身が「縦断研究はない」と認めている
- **根拠のない閾値**：0.60、4回、3行などが規則のように書かれている。例示として扱う

### 10.3 補完調査の雛形（付録A）の不具合

`11` 第5節に全件の扱いがある。使う前に直すこと。

- **A-4（評価資産を守る hook）**：jq がない環境では素通しになる（fail-open）。スクリプト側で jq の有無を確かめて止める。判定が部分一致なので止めすぎる
- **A-3 と A-4**：hold-out データを読み取りで塞いでいない。Read の deny を足すか、リポジトリの外に置く。子プロセスは sandbox で塞ぐ
- **A-11（計測つきの高速化）**：出力のビット一致を条件にしながら、出力が変わる候補（乱数生成器の変更、exp の近似）を挙げている
- **A-14（/goal での自律反復）**：/goal の判定役は会話しか読まないので、「テストを変えていない」ことを判定できない。`git status` の出力を会話に出させる
- 版依存の雛形（A-4・A-14、および A-3・A-5・A-6）には確認日と版を付ける

### 10.4 調査で埋まらなかった空白

- 公式情報で未取得のもの：Styles の現行仕様、チャット共有の仕様、断られたときの頼み直し方、IDE 拡張の固有機能、Desktop のローカル MCP、Office アドインの機能、knowledge cutoff の Help Center 記事、`ANTHROPIC_API_KEY` と課金経路の関係、AskUserQuestion の質問数の上限

- データが存在しないもの：5.x 世代での過剰設計・迎合・テスト改ざんの頻度、現行の tokenizer での日本語と英語のトークン比、日本語と英語の指示の精度比較、対戦型・数か月のチーム戦での AI 活用の研究、AI の利用期間と技能形成の縦断研究

データがない論点は、作者や制作セッションが確かめた「検証ノート」にするか、確認日を付けて控えめに書く。

## 11. 制作セッションへの指示

制作セッションは、このドキュメントで決めていない事項を自ら判断する。**教材の作成に着手する前に、必ず全体を深く思考すること。** 目的と読者、教材の使われ方（引く辞書、claude.ai での相談）、分野の全体像と相互の関係、規模と作業の分割、鮮度と品質を保つ方法、起こりうる失敗とその対策までを考え抜き、設計書として文書に残してから作り始める。いきなりページを書き始めてはいけない。

**ユーザーの認識とずれた判断を避けることを重視する。** 分からない点や解釈が分かれる点は推測で埋めず、選択肢付きの質問でユーザーに尋ねる。最初にまとめて質問し、作業の途中でも必要になればその都度質問する。最初の質問には、少なくとも次を含める。

- ライセンス（D19 の案でよいか）と、作者名・サイトの URL の表記
- 初版の範囲と公開の目安（D10 の第一波でよいか）
- 検証ノートを作るとき、作者自身の環境（プラン・OS・使っている面）で試すか、制作セッションの中で試せる範囲に限るか
- このドキュメントと調査資料を読んで、ほかに曖昧だと判断した点

### 制作セッションが判断すること

- 全ページの一覧と目次（§4 の初期案と `00` §3、`11` 第1〜2節を材料に）。各ページの level・優先度・前提関係
- 各分野・各ページに適した構成と、図・比較表・Before/After・判断例・注釈付きセッション記録をどこでどう使うか
- front matter の具体的な形式（schema）と、分類軸の最終形
- 逆引き辞典の項目（`00` §4 の73項目が出発点）と生成方法
- リポジトリのフォルダ構成、MkDocs の設定、図の描画手段、数値ファイルの形式と参照方法
- 鮮度の点検の仕組み、claude.ai 用の手順ファイル、制作者用 skill の中身
- 調査資料の空白（§10.4）のうち、どれを補うか

### 進め方

1. 質問：このドキュメントと `planning/research/` を読み込み、分からない点・曖昧な点を質問形式でユーザーに確認する
2. 調査の補完：既存の調査を読み、§10 の誤りを直し、空白を一次資料で埋める。10-29 以降の変更を確かめる。全部を調べ直す必要はない
3. 設計：目次・分類・編集方針・技術構成・鮮度の仕組みをまとめた設計書を作る。複数の案を比較し、なぜその案を選んだかを書く
4. 設計の見直し：作成者とは別のサブエージェントが設計書を批判的にレビューし、抜けや偏りを直す
5. 決定の提示：着手する前に、設計で決めた内容を簡潔な一覧にしてユーザーに出し、確認を得てから先に進む
6. 土台作り：MkDocs の設定、schema、骨格と索引の生成、検査のスクリプト、数値ファイル
7. 試作：性質の違う型から数ページを作り、設計を検証して直す。少なくとも、症状・概念・機能（設定の雛形を含む）・比較・判断（人の側）・コンテスト・台帳の各型から1ページずつ
8. 本制作：残りのページを作る。逆引き・用語集・比較表は本文と並行して育てる
9. 仕組み作り：claude.ai 用の手順ファイル、鮮度の点検と事例の記録の skill、issue のテンプレート
10. 全体の検証：リンク切れ、前提関係の矛盾、用語・表記の不統一、事実の誤り、確認日のない版依存の記述、根拠の強さの表記漏れを確かめる
11. 公開と鮮度の運用を始める

### サブエージェントの使い方

教材は非常に大きいため、サブエージェントの使用を必須とする。メインのセッションは全体の設計と一貫性の管理に専念し、調査・執筆・検証をサブエージェントに分担させる。

- 調査：分野ごとにサブエージェントを並列で動かし、結果をファイルにまとめさせる
- 執筆：ページまたは小さな分野の単位で割り当てる。設計書・執筆の手引き・用語集・見本のページを必ず渡し、ページ間で書き方がぶれないようにする
- 検証：書いたものとは別のサブエージェントが確かめる（事実・出典・確認日・根拠の強さ・設定の動作・分かりやすさ）。書いた本人に採点させない
- 長期作業の再開：進捗と残り作業をリポジトリ内のファイルに記録し、セッションが途切れても続きから再開できるようにする

### 注意点

- 教材の更新は、まとまった単位で意図を持ってコミットする
- 事実（機能の挙動・数値・既定値・規則）は確かめてから書く。記憶で書かない
- 公式文書を訳して載せない。他者の記事は参考にしても文章を転載せず、自分の言葉で書く。参考にした資料は出典として残す
- 調査資料も AI が書いたものである。根拠が弱いのに断定している箇所に気づいたら、使う前に確かめ、`planning/decisions.md` に記録する
