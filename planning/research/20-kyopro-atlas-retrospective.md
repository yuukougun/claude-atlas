**C4★ 数値の参照の仕方** 【意見。根拠は記憶】

### B. 目次・骨格・front matter

**B1★** 工程8a〜10 の会話は覚えていないので、凍結した理由と、そのあと困ったかは分からない。

工程11 でページを足したときのことは覚えている【記憶】。

- 初期は catalog から雛形を作る。
- 骨格を作った時点で、front matter を正に切り替える（kyopro-atlas と同じ）。

理由は、本文を書くと front matter（sections・related）がページと一緒に変わるからだ。catalog を正本のまま保つと、2 か所を同期し続けることになる。

**B2★**【記憶＋意見】
工程11 で手を入れたキーは、次のとおり。
- **stage**：draft → reviewed → done。#9 で、ページの最後の行に出した。
- **updated**：#9 で表示した。
- **nav_title**：ページの見出しが nav_title（サイドバー用の短い名前）になる不具合（#91）が出た。表示の部品が 1 つのキーを 2 つの役に使うと、事故になる。
- **summary・signs・sections の title**：「平文の欄」の規則（#68）が後から決まり、全ページを当て直した。

キーを増やすときの勧めは、次の 3 つ。
1. キーごとに、次の 3 つを最初に決める。
   - 誰が書くか（執筆者か、道具か）
   - どこに写るか（生成物・表示・llms.txt）
   - 書式（平文か Markdown か）
2. check で型を検査できないキーは作らない。
3. 執筆者に書かせるキーは少なくする。claude-atlas の案の verified・verified_with・maturity などは、執筆者ではなく検証役か道具が書くキーだと思う。執筆の指示に「書かない」と明記するとよい。

### D. サブエージェントとバッチ

**D1★**【記憶】
工程11 の進め方は次のとおり。
- 1 グループに 1 本の Workflow を使った（stage1 で直す → verify → fixup）。
- グループは同時に 2〜4 本。
- 1 グループの担当は 3〜4 人（scopes）。

困ったことは、次の 3 つ。
- **利用上限（5 時間）で止まったとき**
- **端末を閉じて止まったとき**：Workflow の resume は同じ args が要るのに、args がどこにも保存されていなかった。止まった段（verify）から先は、直接 Agent を起動して手で続けた。
- **全ページの render_pages を -j 8 で流したとき**：OOM で止められた。

今ならどうするか【意見】。
- Workflow の args を、毎回ファイル（リポジトリの追跡外）に書いてから起動する。
- 各段の担当が、報告をファイル（planning/batches/fix/<グループ>/<担当>.md）に書いてから終わるようにする。工程11 ではこうしていたので、止まっても報告は残った。再開は「報告のないものだけ流し直す」で済む。

**D2★**【記憶】
- 観点の分け方は、工程11 では「その直しの検証」で、4 観点ではなかった。
- 検証役が見落としがちだったのは、次の 3 つ。
  - **描画の結果**：Markdown だけを読んで、ビルドしない。
  - **自分の担当の外への波及**：節を並べ替えたあとの「上の節」「次の節」などの参照。
  - **公開ページの約束が守れるか**
- よく拾ったのは、次の 3 つ。
  - 事実の誤り。例：floor_sum の m を「法」と書いたもの。正しくは割る数。
  - 記録との食い違い。例：方針ページの「問題文を読まない」と、制作の記録。
  - PR 番号と Issue の対応。
- 意見が割れたときは、メインが手引きに照らして決め、決めたことを decisions.md に書いた。
- 直しは書いた担当に戻した。文脈があるので速く、問題はなかった。直したあとを、もう一度別の担当に見せることはしていない（重いため）。

**D5**【記憶＋意見】
- 共通の指示を 1 ファイル（brief-fix.md・brief-verify.md）にし、各担当には差分だけを書いた。

### I. claude-atlas への助言

**I1★ 持っていくべきもの**【意見】
1. **書いた本人に検証させない分担と、報告の固定の形**（特に「確かめていないこと」の欄）。見落としが減り、再開もしやすい。
2. **値を 1 か所に集め、本文へは道具が書き込み、CI の `--check` で止める方式**。claude.ai が素の Markdown を読む前提に合う。
3. **Issue → グループのブランチ → PR（Closes）→ 作業ツリーで並列**。作者が後で追える。

**I1★ 持っていかないほうがよいもの**【意見】
1. **毎回変わる版のハッシュを、手書きのページや生成物に埋め込むこと**。並列のマージで、毎回衝突する。
2. **規則を手引きの末尾に足していく形**（後の節が優先）。今有効な規則だけを置く。
3. **描画の検査と書き方の検査を後回しにすること**。最初の試作で 0 件にしてから増やす。

**I2★ 鮮度**【意見】
kyopro-atlas の updated は「中身を直した日」だけで、「事実を確かめた日」はなかった。最初に決めておくべきことは、次の 4 つ。
1. 確認日の単位：ページか、主張（数値・既定値）か。数値ファイルに寄せるなら主張の単位で、ページは「含む主張の確認日の最小」を道具が計算する。
2. 期限：volatility ごとに、何日で「要点検」にするか。
3. 期限切れの表示：期限切れを表示に出すか、CI で警告するか。
4. 点検の担当と手順：点検を Issue で回すか。たとえば、週に 1 回、CHANGELOG の差分から「影響するページ」を道具が出して、Issue を作る。

**I3**【意見】
残しておけばよかった記録は、次の 3 つ。
- Workflow のスクリプトと args
- 担当への指示（brief）の版の変遷。たとえば、「確かめていないこと」の欄を足した理由。
- 検証の指摘と、それを直した前後の差分の対応

工程11 の報告は planning/batches/fix/ に残っているが、指示の失敗例（例：cd と & の件、守れない約束を公開した件）は、記録していない。

**I4** 一番伝えたいのは、次のことだ。「AI が書いた約束を、作者の確認なしに公開のページに置かない」。方針ページで、検証役の勧めをそのままメインが採り入れ、作者に外させることになった。claude-atlas は不特定多数が読むので、公開の約束・方針・ライセンスに関わる文は、作者が承認してから出す運用を、最初から CLAUDE.md に書くとよい。
