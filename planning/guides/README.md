## 2. 渡し方

元：design §10.2・§10.3

- 執筆：共通の手引き（読む節を名指しする）、ページの型の手引き、各節の「元」にある設計書の節（名指しする）、見本のページ（§4。「構成をまねない」と添える）
  - あわせて、用語集・catalog の項目・data の該当の項目・材料の調査資料の節・工程2の訂正（research/22〜28）を渡す
- 検証：検証の共通の決まり、観点のチェックリスト、照らす手引きの節（チェックリストの冒頭が名指す）
- 指示には、渡した手引きとチェックリストの版を書く。担当の報告にも、使った版を書かせる

## 3. 直し方

元：design §10.2、design-review DR-12、research/20 の E1・I1

1. **今有効な規則だけを置く**。決定で規則が変わったら、その規則が書いてある所を書き換える。「〜で決めたこと」の節を末尾に足さない。「後の節が優先」の形にしない（kyopro-atlas の反省）。経緯は decisions.md と design.md の変更履歴に書き、手引きとチェックリストには書かない
2. **規則の元を書く**。各節の「元：」に、写した設計書・要件・決定の場所を書く。設計書が変わったら、変わった節の番号（「design §6.4」など）で手引きとチェックリストを探して書き換える
3. **検査の名前を添える**。機械で検査できる規則には、規則の横に「（検査：<名前>）」を、まだ道具がない検査には「（作る予定：<名前>）」を書く。名前は道具の名前か、検査の層に登録した検査の名前（`check_pages.py「summary」` の形）にする。道具ができたら「作る予定：<名前>」を探して「検査：<名前>」に書き換え、検査の名前が変わったら同じように書き換える
4. **チェックリストを検証の4つの観点に合わせる**（design §10.2 の表）。観点を変えるなら、設計書から変える
5. **共通のことは1回だけ書く**。型の手引きと観点のチェックリストには、その型・観点に固有のことだけを書き、共通のことは「共通の手引き §N」「共通の決まり §N」で指す
6. **語彙を写さない**。分野・型・段階・原因などの値の一覧は `schema/site.yml` を正とし、手引きに一覧を写さない（要るときは site.yml のキーを名指す）
7. **版を上げる**。変えたら、版の行（日付と第N版）を直す
8. **試験を通す**。直したら `uv run python -m unittest discover -s tests/guides` を流す。`tests/guides/test_guides.py` は次を確かめる
   - 型の手引きが site.yml の types とそろうか。見本の表にすべての型があるか
   - リンクと「共通の手引き §N」などの参照が解決するか
   - 各節に「元：」があり、元に書いた設計書・要件・決定の場所があるか
   - 「検査：」の印の道具があるか。道具ができた「作る予定：」の印が残っていないか
   - 末尾に決定を足す形の見出しがないか
