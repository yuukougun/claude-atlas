# 型の手引き：ledger

- 版：2026-11-04 第1版（工程6a。試作〔工程7〕で確かめて確定する）
- 共通の手引き（common.md）と一緒に使う。ここには、この型の構成の目安と、この型に固有の注意だけを書く

## 1. 用途と、必ず持つもの

元：design §2.2・§3.1・§7

- 用途：台帳・年表・対応表
- 冒頭の要点のほかに必ず持つもの：データから作る表
- level を持たない

## 2. 構成の目安

元：design §6.3

- 要点 → 生成の表 → 読み方（台帳は「どの原理の回避策だったか」）

## 3. この型に固有の注意

元：design §7・§8.4・§9.1、design-review DR-18、decisions 2026-11-03 方針 A1・「鮮度の更新の承認」

- 表は data（`data/outdated-advice.yml`、数値ファイルの名称の表など）から、道具が目印の間に作る。手で行を書かない。行を足す・直すときは、data への提案にする（共通の手引き §21）
- どのページに何を生成するかは、作る層の設定が持つ。front matter に印のキーを足さない
- 手で書くのは、要点・導入・読み方だけである。古くなった助言の台帳の導入には、回避策が正式な仕組みに置き換わる規則性を書く
- 読み方には、表の欄（data の項目。design §9.1）をどう使うかと、自分の設定や記事で古い助言を見つける方法を書く
- 台帳の行は消さない（古い記事の手順が通じない読者の入口になるため）。消す代わりに、状態（撤回・置換・条件付き）を変える提案をする。公開の後に状態が変わる更新は、作者の承認が要る
- 名前と画面の変更の事実（旧名・今の名前・変わった時期）は、数値ファイルの名称の表を正とし、台帳の行はその id を指す（二か所に持たない）
- 古い助言の出どころの個人や記事を名指ししない。助言の文言・時期・撤回を、一次資料で書く（共通の手引き §15）
- 年表（変更の記録）は、手書きの部分と生成の部分を目印で分ける
