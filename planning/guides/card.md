# 執筆カード

- 版：2026-11-05 第1版（common.md 2026-11-04 第1版と型の手引き9つの写し）
- 渡す相手：執筆と、分かりやすさの検証・直しの担当。読むのは材料の束とこのカードだけ。迷ったときだけ、（common §N）の節か型の手引きを引く
- このカードは写しである。食い違いや足りない所を見つけたら、カードを直さず、報告の「メインに判断してほしいこと」に書く
- 検査は書き終えた後と直した後に1回ずつ：`uv run python tools/check_page.py <id>`（生成・参照・textlint をまとめて流し、指摘だけを出す）

## 1. 書いてよいもの（common §2）

- 自分のページ `docs/<field>/<id>.md`、`snippets/<id>/`、`docs/img/<id>/`、`data/sources.d/<id>.yml`、報告と数値の提案
- front matter で直してよいのは `sections`（節を足す。既にある anchor は変えず、節も外さない）・`stage`（stub を draft に。reviewed 以上にしない）・`updated`（読者に見える中身を変えた日）・`sources`（既にある id だけ）。`verified` 系は書かない
- ほかのキー（title・aliases・summary・signs・prerequisites・related・routes・level など）は直さず、YAML で提案する（§10）
- 目印の間は手で書かない。共有のファイル（用語集・prh.yml・data の3ファイル・catalog・schema・手引き・tools）は直さず提案する
- git と gh の書き込みをしない。止められたら、理由と代わりのやり方に従い、回り込まず報告に書く

## 2. 冒頭の形（common §3）

最初の `##` より前に、要点の囲み・別名の行・導入の順で置く。

```markdown
!!! abstract "要点"
    - **何ができるか**：…（concept は「何が分かるか」）
    - **いつ引くか**：…
    - **前提**：<!-- link:begin request-vs-lock --><!-- link:end -->

<!-- textlint-disable -->
別名：指示を無視される・CLAUDE.md が効かない
<!-- textlint-enable -->

題名を主語にした1〜3文の導入。
```

- 「何ができるか」の1文目は、答えそのもの。summary と食い違わせない。90字ほどまで（囲みの見出し行と行頭の記号も textlint の文字数に入る）。「いつ引くか」は読者の言葉で書き、signs と食い違わせない
- 「前提」は front matter の `prerequisites` を全部、link の目印で並べる。ないときは「なし」
- 別名の行は `aliases` を全部並べ、textlint の無効の囲みで包む。aliases が空なら置かない
- バッジの列と、冒頭・フッターの非公式の文はテンプレートが出す。本文に書かない。型によって項目を足す（feature の強制力など。§11）

## 3. 見出しと節（common §4）

- 本文に `#` を書かない。見出しは `##` から。見出しは平文（バッククォート・リンク・強調・波かっこを使わない）
- `sections` に載せた節は `## <title> {#<anchor>}` で置き、見出しの文字を `title` と同じにする
- 節の最初の文で何の話かを書く。「上の図」「前述の」「この方法」に頼らない。節を1つだけ読んでも通じるようにする
- 型の構成は目安。目安のための薄い節を作らず、並べ替え・省略してよい
- 本文に書かない節：前提・次に読む・関連（テンプレートが出す）、参考（道具が sources から作る）。演習と確認問題も置かない

## 4. 文体と用語（common §5）

- だ・である調。1文を短く、1段落に1つの主張。半角英数字と全角文字の間に空白（「2 回」）。バッククォートのコードも和文と接するときは前後に空白。全角の句読点と括弧の隣には入れない
- 機能名・コマンド・ファイル名・設定のキーは原文のまま。コマンド・ファイル名・キー・コードはバッククォートで囲む
- 用語は用語集（start の glossary）を正とする。表記の揺れは prh が見つける。用語集にない語は本文で短く定義し、追加を提案する
- 英語のまま書く3語：plan mode・effort・allow ルール／ask ルール／deny ルール。日本語の訳は aliases と別名の行にだけ置く
- textlint から外してよいのは2つだけ：別名の行（`<!-- textlint-disable -->`）と、表記の揺れをわざと例に出す所（`<!-- textlint-disable prh -->`〜`<!-- textlint-enable prh -->`）
- 公式の英語の文書の題名はリンクにするか日本語版の題名で書く。原文を引くときは `>` の引用
- 「四つ・一つ・二つ」は textlint の警告になる。「4 つ」と書く。`!!!` の中の入れ子の箇条と判断例の各行は「。」で終える（終えないと次の項目まで1文と数えられる）
- 開発の経験を前提にする。git・ターミナル・プログラミングの基本を説明しない
- textlint は、囲み（`!!!`）・折りたたみ（`???`）・タブ（`===`）の中の、空行の後に続く字下げした段落を検査しない。そこは自分で読んで確かめる。エラーは0、警告は直すか誤検出の理由を報告に書く

## 5. 判断を書く（common §6・§7）

- 機能の説明で終わらせない。どの原因を防ぐか・なぜ効くか・どこまで任せるか・どう確かめるか・効かない場面を書く
- 比例則：任せる幅を広げる内容（自律・並列・無人・権限の緩和）は、見合う守り（verify・eval・enforce・safety のページ）を同じ流れの中で先に示し、link の目印で指す
- 面ごとに手段が違う話は、ページの中のタブ。名前と順は「アプリ」「Claude Code」「API」で、front matter の `surfaces` にある面だけ（`=== "アプリ"` の下に4字下げ）。面に固有の詳しい手順は面の分野のページへ
- 本文はプランに中立。Claude Code は WSL・Linux の CLI を基準にし、ほかの OS と IDE 拡張の動作は「未確認」と書く
- 判断例（答えを伏せない。折りたたまない）：

```markdown
!!! example "判断例：<短い題>"
    - **状況**：…
    - **迷う候補**：…（どちらも筋が通るものに）
    - **選んだもの**：…
    - **理由**：…
```

- Before/After は同じ依頼で並べ、After で何を足したかを注記する。比喩は一覧のものを使い、同じ仕組みには同じ比喩：広い机＝コンテキスト、毎回読み直す受験者＝全履歴の送信、積み木＝プロンプトキャッシング、議事録だけ残す＝圧縮、別室の部下＝サブエージェント、山を張る受験生＝ハルシネーション、お願いと鍵
- 検証ノートは、日付・版・試した場所を付ける。API キーを使わず、偽の秘密と壊れても困らない操作だけ。注釈付きのセッション記録は制作の環境と記録だけから作る
- 食い違う頼み方の論点：目的と完了は成果で、着手点は具体的に／答えを選ぶ場面は選択肢と推奨案を出させ、発想の場面は先に自分の案を書く／理解と確認は原文を見せる／例外を許さない禁止は deny ルールかフックで強制し、CLAUDE.md には理由と相談の基準だけ

## 6. 根拠の強さの印（common §8）

研究や数値を根拠にする主張の後に付ける。公式の文書で確かめた機能の挙動には付けず、出典で示す。

| 印 | 使うとき |
| --- | --- |
| （根拠：強） | RCT・メタ分析・大規模な実験・主催者の規約や公式の記録 |
| （根拠：中） | 小規模な研究・企業の一次の報告・複数の実務家の一致 |
| （根拠：弱） | 単独の経験談・二次の報道・立場の表明 |
| （類推） | 隣接分野の結果の当てはめ（（根拠：強・類推）の併記も可） |
| （推論・実践例なし） | 研究も実践例もない推論・独自の提案。必須ページの中心にしない |

- 研究の結果はモデル・世代を書く。旧世代や他社の結果を現行の Claude の傾向にしない。小さな研究は「傾向」と標本の大きさ。根拠の弱い数値は「自己申告」「経験則」
- 割れる論点は「公式の立場」「実践者の幅」「この辞典の推奨」の三段

## 7. 変わりやすい値と数値の提案（common §9・§21）

数値（料金・上限・回数・割合・トークン・期間）・既定値・成熟度・プランやモデルの名前・名前の変更・入った版・大会の規則の版は、本文に手で書かない。fact の目印で指す。

```markdown
上限は <!-- fact:begin <数値の id> --><!-- fact:end --> である。
```

- ない id を指すと止まる。目印の外に数値ファイルと同じ値を手で書くと警告が出る
- 数値ファイルにない値は本文に書かず、報告とは別の YAML（既定は `facts-<ページの id>.yml`）に提案する。面やモデルで違う値は一つに丸めない。公式同士が食い違うなら両方の出典を書く。本文は、その数字なしで読める形にし、目印を置く場所を `used_in` に書く
- summary・signs・題名に変わりやすい値を書かない
- 研究の結果（割合・件数・対象のモデルの名）は、その研究の時点の固定の記録で、この節の変わりやすい値に当たらない。研究の名・公刊の年・対象（モデル・領域）を添えれば、本文に書いてよい。今のモデルの名・既定値・上限は、今までどおり目印で書く（common §9）

```yaml
proposals:
  - fact: {id: …, title: …, value: …, sources: […], checked: 2026-11-20, status: …}
    used_in: [<ページの id>#<anchor>]
```

## 8. ほかのページを指す（common §10）

- 同じ辞典のページは `<!-- link:begin <id>[#<anchor>] --><!-- link:end -->`。間は道具が書く（未公開は「題名（準備中）」）。前後の文は、相手の題名が入っても読めるように書く
- 節を指す `id#anchor` は、束の「指せる節」にあるものだけ。ないものは指さない
- 手書きの Markdown リンクで未公開のページを指すと止まる。持ち主でない内容は持ち主のページを指し、繰り返さない
- 用語集の語は、最初に出たときに1回だけ指す（見出しの中では指さない）
- 公式の文書は転送先の URL。atcoder.jp・codeforces.com は開かない。競技の練習法と AtCoder の規則の細部は kyopro-atlas を指す
- 出典は `sources` の id で指す。新しい出典は `data/sources.d/<id>.yml`（形は `schema/sources.schema.json`）。足す前に同じ URL がないか探し、新しいドメインは `uv run python tools/check_noai.py <URL>` で確かめる。公式の文書を訳して載せず、文は自分で書く（common §11）
- 主催者の公式 X の投稿は、出典にしてよい（例外ではない。x.com は check_noai.py で断る指定がないと出る。Anthropic のクローラを名指しする組だけを見る決めのため）。投稿の本文だけを読み、投稿の中のリンクはたどらない。出典の種類（source_kinds）は「公式の投稿」にし、domains には x.com を書く（common §11）

## 9. 目印の一覧（common §9・§12。`gen_site.py --list-blocks`）

手書きのページに `<!-- gen:begin 名前 -->` と `<!-- gen:end 名前 -->` を置くと、道具が間を書く。block は目印を1行ずつ、inline は文の中。

| 目印 | 種類 | 書かれるもの |
| --- | --- | --- |
| `routes` | block | 症状の診断の節：原因ごとの振り分け先の表（front matter の routes から） |
| `causes` | block | 症状の原因別の表（symptom の routes から） |
| `compare [<列> …]` | block | 比較の表：ページの tracks の機能の属性。列の指定は下。全行が同じ値の列は表から省き、表の下に「すべて共通：…」の1行で出す |
| `feature <属性>` か `<機能の id>/<属性>` | inline | 機能の属性（強制力・成熟度など）。機能を省くと tracks の最初 |
| `fact-table <数値の id>` | block | 数値ファイルの表と、確認日・出典・食い違い。セルに `sources` があれば、表の下に行ごとの出典の箇条で出す。id が facts にないと check_pages が止める |
| `ledger` | block | 古くなった助言の台帳の行 |
| `ledger-index` | block | 台帳の一覧表（古い助言・状態・変わった時期・面。各行の節へのリンク）。`ledger` の前に置く |
| `snippet <ページの id>/<名前>` | block | 雛形の写し（`snippets/<id>/<名前>.*`）。動作を確かめていない旨も道具が書く |
| `page-links` | block | 前提・次に読む・関連（ページ下部。目印がなければ末尾に道具が足す） |
| `references` | block | 参考の節（sources から。手で書かない） |
| `signs <type>`・`roadmap`・`terms …`・`timeline`・`graph` | block | 逆引き・ロードマップ・用語索引・年表・知識マップ（hub の生成ページ） |

- ほかの目印：`<!-- fact:begin <id> -->`〜`<!-- fact:end -->`、`<!-- link:begin <id>[#<anchor>] -->`〜`<!-- link:end -->`
- 名前の今の呼び方：`<!-- name:begin <names の id> -->`〜`<!-- name:end -->`（段落の中に置く。間に data/facts.yml の names の今の名前が入る。ない id は止まる。間は書き方の検査から外れる）
- `compare` の列：目印の名前に、列を空白で区切って書く。属性の id（`enforcement`）でも表示の名前（`強制力`）でも、確認日（`確認日`）でもよい。書いた順に並ぶ。省くと、値のある属性と確認日。使える属性は 面・成熟度・強制力・読み込みの時期・コンテキストのコスト・圧縮で残るか・入った版。終わりの目印も同じ名前にする
  - 例：`<!-- gen:begin compare 強制力 読み込みの時期 圧縮で残るか -->`〜`<!-- gen:end compare 強制力 読み込みの時期 圧縮で残るか -->`
  - 機能が 2 つ以上あり、全行が同じ値の列は、表から外れて「すべて共通：成熟度 GA。」の 1 行になる（本文でその値を繰り返さない）。列がすべて共通のときは外さない
  - 値が null のセル：既定は「未確認」（確かめていない）。条件で値が変わるものは、data の機能に `conditional: [survives_compaction]`（null の属性の id のリスト）を足してもらうと「条件による」と出る。本文の「条件による」は手で書かず、この表を指す
- `link` で書かないページ（優先度が任意の骨格）を指すと、リンクも「（準備中）」も付かず、題名だけが出る（`#anchor` 付きも同じ）。前提・次に読む・関連の一覧にも出ない
- `link` で分野の入口を指す：`<!-- link:begin field:symptoms --><!-- link:end -->`（`field:` の後に分野の id。間に分野の名前が入り、入口 `<分野>/index.md` へのリンクになる。公開するページがない分野は「名前（準備中）」。`#anchor` は付けない）
- `routes` の表は、行き先を 1 つずつセルの中で改行して並べる（道具がそうする）。題名の中の「・」と区切りが混ざらない
- 目印の組は空で置き、`uv run python tools/gen_site.py --page <id>` で埋める（check_page.py が流す）。間を手で直さない
- 手書きにするのは、導入・注記・選び方・読み方など。比較の表・台帳の行・属性のバッジは道具が作る

## 10. 雛形・図・front matter の提案（common §12・§13・§21）

- 雛形は `snippets/<id>/<名前>.<拡張子>` と `<名前>.expect.yaml`。本文は `<!-- gen:begin snippet <id>/<名前> --><!-- gen:end snippet <id>/<名前> -->`（`--8<--` を使わない。手で写さない）。動作を確かめていなくても、なるべく多く載せる
- 種類（kind）は settings・hook・skill・subagent・claude-md・prompt・other。目次の templates の案を基本にし、分かりやすさに要る雛形は足してよい

```yaml
# snippets/<id>/<名前>.expect.yaml（キーはこれだけ。順もこのとおり。要らないキーは書かない）
title: 雛形の題          # 折りたたみの題（道具が読む）。なければ名前
kind: prompt            # 上の種類のどれか
place: user             # 置く場所。user・project・local、または「依頼の本文」など
safety: false           # 安全とデータの雛形は true（道具が「自分の環境で確かめる」旨を書く）
open: true              # 道具が読む。true なら雛形の枠を開いた状態（???+）で出す。省くと閉じる。本文の流れで中身を先に見せたいときだけ
features: [hooks]       # 道具が読む。要る最低の版の元になる機能の id（data の features の since.claude_code のうち新しい版）。省くとページの tracks
min_version_fact: some-min-version   # 道具が読む。要る最低の版を data の facts の id で指す（その value が版）。features より優先。確認済みの facts にだけ使える
requires: [scripts/collect-changes.sh]   # 一緒に置くもの
conditions:             # 試す前提
  - 新しいセッションで試す
expect:                 # 起きること。完全一致にしない
  - when: 欄を埋めた依頼を出す
    then: 返答が完了に書いた形になる
control: 雛形を置かないとき、同じ依頼で…になる   # 比べる相手（任意）
```

- 道具が読むのは `title`・`features`・`min_version_fact`・`open`・`safety` だけ。ほかは書き手と、動作確認の担当のための記録
- `expect` の項目は「`when`（きっかけ）と `then`（起きること）」の組、または 1 文。「この操作が止められる」「この行が出る」の形で、観察として扱うもの（指示は鍵でないので合否にしない）は then にそう書く。`do`・`result` の組は使わない（`when`・`then` に書き直す）
- `min_version_fact` と `features` の使い分け：雛形の動作に特定の版の機能が要る（Stop フックの `last_assistant_message` など、機能全体の since より新しい版が要る）ときは `min_version_fact`。機能の since のままでよければ `features`

- 試せない雛形（使い捨てのコンテナ・/etc の管理設定・API キーが要る `--bare`・GitHub Actions）は載せず、条件と概念だけ書く。回避された仕組みを守りとして勧める雛形は載せない。`verified.yaml` は書かない
- 図は `docs/img/<id>/`。図の前後に要点を文章で書き、代替テキストも要点を言う。SVG は文字をテキストのまま、`viewBox` と同じ比の `width`・`height`、白い背景、幅 400 程度まで。色だけで区別しない。Mermaid は外の資源を読まない。Anthropic のロゴをまねない
- 表は列を絞り、行き先の列を左寄りに置く（スマホ）。data から作る表を手で書かない
- front matter の提案（YAML）：

```yaml
frontmatter:
  - {id: <ページの id>, key: aliases, before: […], after: […], reason: "…"}
```

用語集・prh・data・手引きへの提案も報告の「提案」に書く。

## 11. 型ごとの構成の要点（型の手引き）

どの型も、構成は目安。冒頭の要点のほかに必ず持つものを持つ。必ず持つものは、束の「型の必ず持つもの」（型の手引き §1・§2 の写し）で確かめ、write.md に、1項目ごとにそれを持つ節の anchor を書く（brief §5）。台帳の行（古くなった助言）に触れたら、`<!-- link:begin outdated-advice-ledger#<行の id> -->` で指す。

- **concept**（原理・技法）：level あり。要点の最初は「何が分かるか」。原理は「何が起きるか（具体的な場面から）→ なぜ（比喩付きの図）→ 何に効くか → 誤解 → 関連」。技法は「頼み方の例（Before/After）→ 何が変わるか → なぜ効くか → 効かない場面・やりすぎ」。`principle`・`prevents`・`pitfalls` を本文で名指す。内部の動きの断定には根拠の印。対処の手順の本体は持ち主のページへ。呪文を効く手法として教えない。「何に効くか」の節で、front matter の `principle`（原理）と `prevents`（防ぐ原因）を本文で名指す。
- **feature**：level あり。1機能1ページ。要点に「強制力」（値は `feature` の目印で、お願い・鍵・モデルの判定・なしのどれか。手で書かない）を足し、何を止められて何を止められないかを一言。「使いどころ（どの原因を防ぐか）→ 最小の使い方（面のタブ）→ 雛形 → 効かない場面・落とし穴 → 比べる相手（comparison を link）→ 古くなった助言（台帳を指し、今どうするかを一言）」。属性・入った版を手で書かない。全オプションは公式へ
- **symptom**：level あり。1症状1ページ、題名は読者の言葉。「要点 → よくある形 → 診断（`{#diagnosis}`。`prevents` の原因を site.yml の並びで、`pitfalls` を後に。1項目に原因の名前・何を見るか・どう確かめるか）→ `routes` の目印 → 判断例 → 予防」。対処の本体は書かない（消された直後・漏れた直後の初動は持つ）。断られた症状は公式が案内する手段だけ。仕組みや研究の要旨は前提のページを指し、症状のページには書かない。診断の最初か最後のどちらかに、六つの原因の外の、いちばん安い確認（障害の情報・上限の取り違えなど）を1項目まで置いてよい。
- **comparison**：level あり。要点の「何ができるか」は「〜なら A、〜なら B」の基準を1文。「比較の表（`compare` の目印）→ 選び方（判断例）→ 組み合わせ方（何をどちらに置くか）」。表の値を本文で繰り返さない
- **recipe**：level あり。「要点 → 先に整える守り（確かめる・縛る）→ 手順（各段に何で終わったかの確かめ）→ 確かめ方（全体）→ 失敗したとき（症状ページへ振り分け）」。原理と機能の説明は繰り返さず link。設定は snippets から、数値は目印で
- **judgment**：level あり。「要点 → 何が起きるか（根拠の印とモデル・世代・課題）→ なぜ（人の側の仕組み）→ 判断例（どちらの候補も筋が通る）→ 握るもの → 確かめ方（記録を付けて測る・やめどきを先に決める。演習の形にしない）」。落とし穴の根拠は一律にせず、当てはめるときは「類推」。実在の個人や著作を名指ししない
- **ledger**：level なし。「要点 → 生成の表（`ledger` などの目印）→ 読み方（表の欄の使い方と、自分の設定や記事で古い助言を見つける方法。台帳は、回避策が正式な仕組みに置き換わる規則性も）」。行は手で書かない。消す代わりに状態を変える提案をする。出どころの個人・記事を名指ししない
- **guide**：level なし。表とリンクが本体で、要点の項目は内容に合わせて変えてよい。方針の文（ai-and-sources、how-to-use の報告と確認日の節）は作者の承認が要る（§13）。守れない約束を書かない
- **hub**：level なし。何から引くか → どのページか、の案内だけ。中身の説明は各ページへ。生成ページの本体は目印の間に道具が作る。表は列を絞り、行き先の列を左寄りに

## 12. 書かないもの（common §14・§15・§17）

- 全コマンド・全設定キーの網羅、インストールと OS 別の設定、API のパラメータ。research preview・experimental の機能の操作手順（概念だけ）。公式へのリンクで済ませる
- 根拠の弱い数値を主張の根拠にすること。ベンダーの効果の数値を中立の事実として扱うこと。日付と版のない、機能・既定値・価格・利用枠の説明
- 安全装置を外す近道（`--dangerously-skip-permissions` の普段使いなど）。攻撃の手口の細部、回避の手順。利用ポリシーを回避する頼み方（断られたときは、本当の目的を足す・巻き戻す・誤判定を報告する・検証の制度を案内するだけ）。AI が書いたと分からなくする方法。文書にない回避方法（見つけても方法に触れない。報告にも書かない）
- 特定の個人の構成を標準として示すこと。モデルの「性格」を固定的な事実として教えること。「複数の AI レビュアーが一致したから正しい」「考察は人間にしかできない」という断定。プレモーテムを実証済みとして紹介すること。自律ループで戦略そのものを改善させる手順。研究や事例の紹介だけの節
- 実在の人物・団体：出典付きなら名前を出してよいが、否定的な文脈（失敗例・古い助言・評価）で個人や著作を名指ししない。第三者のツールは考え方の例として成熟度と確認日を付けて名前を出すだけ。推薦・評価しない
- 安全の既定は、正本の `default-safety-settings#by-stage` を link で指し、段階ごとの既定を書き直さない。大会の規則は版・確認日・類型・リンクだけ（条文を要約しない）

## 13. 作者の承認が要る文（common §18）

- 公開の約束・方針・ライセンスの文は、承認の前は本文に入れず、案を報告の「メインに判断してほしいこと」に書く。対象は ai-and-sources、冒頭とフッターの非公式の文、how-to-use の「誤りや古い情報の報告」「確認日と期限切れ」の節
- ほかのページにも、約束や方針の文（「必ず〜する」「保証する」「返事をする」）と、注意書き（安全を保証しない・法的な助言ではない）を足さない

## 14. 報告の形（common §21。短く）

- 書く担当は `planning/batches/step7/pages/<id>/write.md`、検証と直しの担当は `review.md` に書く。検査は書き終えた後と直した後の2回だけ。報告は書くことのある項目だけを、1項目1〜3行で
- 項目：書いたファイル（front matter で変えたキー）／直したこと（指摘の番号・直した内容・直さない理由）／メインに判断してほしいこと／提案（YAML）／検査の結果（エラーと警告の数・残した警告の理由）／確かめていないこと（空にしない）／使用量（道具の呼び出しの数・Web の取得の数）
- 最後の返答は、報告の場所と結果の要点だけ（報告の中身を書かない）
