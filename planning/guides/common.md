# 執筆の共通の手引き

- 版：2026-11-04 第1版（工程6a。試作〔工程7〕で確かめて確定する）
- 渡す相手：執筆と直しの担当。検証の担当は、照らす規則としてこの手引きを読む
- 一緒に渡すもの：型の手引き（同じフォルダの `<型>.md`）、指示が名指しする設計書の節、見本のページ、用語集（start の glossary）、catalog の項目、data の該当の項目、材料の調査資料の節と工程2の訂正（research/22〜28）
- この手引きには、今有効な規則だけを置く。各節の「元」は、規則を写した設計書（planning/design.md）と決定（planning/decisions.md）の場所である。元と食い違いに気づいたら、自分で判断せず、報告の「メインに判断してほしいこと」に書く
- 規則の横の「（検査：<名前>）」は今ある検査、「（作る予定：<名前>）」はまだない検査である。検査で止まる規則も、自分で守ってから出す

## 1. 読者と、何を書くか

元：design §1.1・§1.2・§6.1、requirements §1

- 読者は、Claude や Claude Code をかなり使っているが、知識が足りず使いこなせていない人である。どのページも開発の経験（git・ターミナル・プログラミング）を前提にし、非エンジニア向けの説明は省く
- 読者は、うまくいかなかった場面・やりたいこと・名前から引く。冒頭の要点で用が足り、必要なら原理へさかのぼれるように書く
- 機能の紹介ではなく判断を教える。なぜうまくいかないか、次に何を足しどう確かめるか、どこまで任せて何を人が握るかを書く（§6）
- 背骨は、四つの原理と比例則、Claude 側の六つの原因と人の側の五つの落とし穴、委任の段階である。値の一覧は `schema/site.yml` の `principles`・`prevents`・`pitfalls`・`levels` にある。本文は、そのページの front matter の `principle`・`prevents`・`pitfalls`・`level` に結び付けて書く
- 読者の AI も読む。AI は llms.txt からページを選び、節の断片だけを読むことがある。1ページで完結させ、節を1つだけ読んでも何の話か分かるように書く（§4）

## 2. 書いてよいものと、触らないもの

元：design §10.2・§3.3・§8.4・§10.5

### 2.1 書いてよいファイル

- 担当のページ `docs/<field>/<id>.md`
- そのページの雛形 `snippets/<id>/`（§12）と、図 `docs/img/<id>/`（§13）
- 出典のファイル `data/sources.d/<id>.yml`（§11）
- 報告と、数値の提案のファイル（§21。置き場所は指示に従う）

ほかのファイルは書かない。

### 2.2 front matter で直してよいキー

| キー | 直し方 |
| --- | --- |
| `sections` | 節を足したら `{title, anchor}` を足す。`title` は見出しに合わせて直してよい。既にある節（骨格で写した節を含む）の anchor は変えず、節も外さない（ほかのページが `id#anchor` で指す。外したいときは提案する）。`level` は任意で、使うならページの level 以上にする（検査：check_pages.py「sections」） |
| `stage` | 書き終えたら `stub` を `draft` にする。`reviewed`・`done` にしない。書き終えられなかったら `stub` のまま報告する（draft にすると公開される。§19） |
| `updated` | 読者に見える中身を変えた日（`YYYY-MM-DD`）。front matter だけ、生成の部分だけの変更では直さない |
| `sources` | `data/sources.yml` か `data/sources.d/` にある id だけを書く（検査：check_pages.py「sources の id」） |

- `verified`・`verified_with`・`checked` は書かない。検証役か点検の道具が書く
- ほかのキー（`title`・`aliases`・`summary`・`signs`・`prerequisites`・`related`・`routes`・`level` など）は直さず、決まった形の YAML で提案する（§21）。直してよいキーのほかが変わっていたら止まる（作る予定：check_pages.py「執筆者のキー」）
- キーの台帳（design §3.3）にないキーを足さない（検査：check_pages.py「形」）

### 2.3 触らないもの

- 目印の間：目印（`<!-- gen:begin … -->`・`<!-- fact:begin … -->`・`<!-- link:begin … -->`）の組を置くのは執筆者で、間を書くのは道具である。間を手で書かない。目印を埋めるときは、自分のページだけを書く `gen_site.py --page <id>` を流す（検査：gen_site.py --check）
- 生成物（ナビゲーション・分野の入口・一覧・llms.txt など）を手で書き換えない（検査：H2 の deny）
- 共有のファイル（用語集・`prh.yml`・`data/facts.yml`・`data/sources.yml`・`data/outdated-advice.yml`・catalog・`schema/site.yml`・手引き・チェックリスト）は直さず、提案する（§21）
- git は読むだけ（status・diff・log・show）にする。commit・push・巻き戻しをしない。gh で書き込まない。生成と commit はメインが行う（検査：H3 の hook）

### 2.4 止められたとき

- hook や permissions に止められたら、返された理由と代わりのやり方に従う。別の道具で回り込まない
- 止められた操作は、報告の「止められた操作」に書く。メインがバッチの終わりに見直す

## 3. 冒頭

元：design §6.4・§5.3、requirements §5.3

本文は次の形で始める。最初の `##` より前に、要点の囲み・別名の行・導入の順で置く（検査：check_pages.py「要点」）。

```markdown
!!! abstract "要点"
    - **何ができるか**：…
    - **いつ引くか**：…
    - **前提**：<!-- link:begin request-vs-lock --><!-- link:end -->

<!-- textlint-disable -->
別名：指示を無視される・CLAUDE.md が効かない
<!-- textlint-enable -->

CLAUDE.md や指示が守られないのは、…（題名を主語にした1〜3文の導入）
```

- 「何ができるか」の1文目は、何ができるか（concept は「何が分かるか」）か、答えそのものにする。summary と食い違わせない。90字ほどまでにする（textlint は要点の囲みを1つの段落として数え、1文目には囲みの見出し行と行頭の記号も文字数に入る。見かけが100字弱でも、120字の警告に当たる）
- 「いつ引くか」は、読者が引く場面を読者の言葉で書き、signs と食い違わせない。機能名を答えとして書かない
- 「前提」は、front matter の `prerequisites` を全部、リンクの目印（§10）で並べる。ないときは「なし」と書く（検査：check_pages.py「要点の前提」）
- 型によって項目を足す（feature の強制力など。型の手引き）。guide と hub は、項目を内容に合わせて変えてよい
- 別名の行には `aliases` を全部並べる。表記の揺れを含むので、書き方の検査から外す印で囲む。aliases が空なら置かない（検査：check_pages.py「別名の行」）
- 導入は、題名を主語にした1〜3文にする
- バッジの列（レベル・原理・成熟度・変わりやすさ・確認日と版）と、冒頭とフッターの非公式の文は、テンプレートが出す。本文に書かない

## 4. 見出しと節

元：design §3.3・§6.1・§6.10・§8.5、requirements §8

- 本文に `#`（H1）を書かない。題名は front matter の `title` からテンプレートが出す。見出しは `##` から（検査：check_pages.py「見出し」）
- `sections` に載せた節は、本文に `## <title> {#<anchor>}` の形で置き、見出しの文字を `title` と同じにする（検査：check_pages.py「sections」）
- 見出しは平文にする（バッククォート・リンク・強調を使わない）。目次・節へのリンク・検索に記法なしで出るため。見出しに波かっこ `{` `}` を書かない（末尾の `{#anchor}` が読まれなくなる）
- 節の最初の文で、何の話かを書く。「上の図」「前述の」「この方法」に頼らない。節を1つだけ読んでも通じるようにする
- 型の手引きの構成は目安である。目安のための薄い節を作らない。内容に合わせて並べ替え、省いてよい
- 本文に書かない節：前提・次に読む・関連（テンプレートがページ下部に出す）と、参考（道具が sources から作る。§11）。型の目安の最後の「関連」も、ページ下部のことである
- 演習と確認問題を置かない。演習の形の論点は、判断例・検証ノート・振り返りのチェックリストにする（§7）

## 5. 文体と用語

元：design §6.2、decisions 2026-11-04「表記が割れている3語」、prh.yml の冒頭の外し方

- だ・である調で書く。1文を短くし、1段落に1つの主張を書く（検査：textlint）
- 数を数える「四つ・一つ・二つ」は textlint の警告になる。「4 つ」「1 つ」「2 つ」と書く（題名など、他のページの題名が link の目印の出力に入る所は目印の間なので検査されない）
- `!!!` の囲みの中の入れ子の箇条と、判断例の各行は、「。」で終える。終えないと、次の項目まで1文と数えられ、文の長さの警告になる
- 半角英数字と全角文字の間に空白を入れる（「2 回」「3 つ」）。バッククォートで囲んだコードも、和文と接するときは前後に空白を入れる。全角の句読点と括弧の隣には入れない（検査：textlint）
- 機能名・コマンド・ファイル名・設定のキーは原文のまま書く。ただし、用語集が訳語を決めた語は用語集に従う。コマンド・ファイル名・設定のキー・コードはバッククォートで囲む
- 用語は用語集（start の glossary）を正とする。訳語は公式の日本語版の本文の多数派に合わせる。表記の揺れは prh が見つける（検査：textlint）
- 公式で表記が割れている3語は、英語のまま plan mode・effort・allow ルール／ask ルール／deny ルールと書く。日本語の訳（plan モード・プランモード・努力レベル・許可ルール・確認ルール・拒否ルール）は、aliases と別名の行にだけ置く
- 書き方の検査から外すのは、次の2つだけにする
  - 別名の行：`<!-- textlint-disable -->`〜`<!-- textlint-enable -->` で囲む（§3）
  - 表記の揺れをわざと例に出す所：`<!-- textlint-disable prh -->`〜`<!-- textlint-enable prh -->` で囲む
- 公式の英語の文書の題名は、リンクにするか日本語版の題名で書く。原文を引くときは引用（`>` の段落）にする
- ほかの書き方の規則は、textlint の設定（`.textlintrc.json` と `prh.yml`）にある。エラーは0にし、警告は直すか、誤検出なら残す理由を報告に書く（検査：textlint）
- 今の textlint は、囲み（`!!!`）・折りたたみ（`???`）・タブ（`===`）の中で、空行の後に続く字下げした段落を検査しない。そこは自分で読んで確かめる
- API の機能名は、Platform の日本語版の訳語を調べるまで英語のまま書く。プロンプトキャッシングだけは、Claude Code の日本語版の多数派に合わせる
- 独自の用語を見出しにし、公式の用語を併記する（例：「お願いと鍵」＝非決定論的な指示と決定論的な制御）
- 用語集にない語は、本文で短く定義し、用語集への追加を提案する（語と、1〜2文の定義。§21）
- 開発の経験を前提にする。git・ターミナル・プログラミングの基本を説明しない

## 6. 判断を書く

元：design §6.1・§3.1・§6.5、requirements §6.7、decisions 2026-11-03「書き方の方針（安全・面・表現）」

- 機能の説明で終わらせない。どの原因を防ぐか・なぜ効くか・どこまで任せるか・どう確かめるか・効かない場面を書く
- 比例則：任せる幅を広げる内容（自律・並列・無人・権限の緩和）を書くときは、それに見合う守り（確かめる・縛る。verify・eval・enforce・safety の分野のページ）を、同じ流れの中で先に示し、リンクの目印で指す
- 面ごとに手段が違う話は、ページの中のタブで並べる（面ごとにページを分けない）。タブの名前と順は「アプリ」「Claude Code」「API」で、front matter の `surfaces` にある面だけを置く（検査：check_pages.py「タブの面」）

```markdown
=== "アプリ"

    …

=== "Claude Code"

    …
```

- 面に固有の操作の詳しい手順は、面の分野（app・cli・api）のページに任せてリンクする
- 本文はプランに中立に書く。プランごとの差は数値ファイルの表に置く（§9）
- Claude Code は WSL・Linux の CLI を基準に書く。ほかの OS と IDE の拡張の動作は「未確認」と書く（方針 B5）
- 調査の間で食い違った頼み方の論点は、次の書き方にそろえる
  - 成果で頼むか、狙いを具体的に書くか：目的と完了の条件は成果で示し、着手点（どこを・何で測るか）は具体的に書く
  - 選択肢を出させるか、先に AI の案を見ないか：答えを選ぶ場面では、選択肢と推奨案を出させる。独自性が要る発想の場面では、先に自分の案を書いてから、問いと反論を求める
  - 原文を見せるか、要約して渡すか：理解と確認には原文を見せる（誤読の検出に使う）。発想の段階で自分の言葉の要約を先に作る助言は、（根拠：弱・類推）として添える
  - 禁止を CLAUDE.md に書くか：例外を許さない禁止は deny ルールやフックで強制し、CLAUDE.md には理由と相談の基準だけを書く（二層）

## 7. 見せ方

元：design §6.10、requirements §6.6、decisions 2026-11-03「検証ノートの実験」「危ない雛形を試す場所」「API キー」と方針 A6

- 見せ方は、Before/After・比較表（生成）・比喩付きの図・注釈付きのセッション記録・判断例・検証ノート・診断のチェックリスト・雛形である。どのページで何を使うかは、メインが試作の始めに作る一覧（planning/shows.md）と指示に従う
- **Before/After**：同じ依頼の前と後を並べ、After で何を足したかを注記する。面ごとに書き換えが違うなら、面のタブの中に並べる
- **判断例**：状況・迷う候補・選んだもの・理由の4行で書く。答えを伏せない（折りたたまない）

```markdown
!!! example "判断例：<短い題>"
    - **状況**：…
    - **迷う候補**：…
    - **選んだもの**：…
    - **理由**：…
```

- **検証ノート**：試した結果を、日付・版（Claude Code の版と系列・モデル）・試した場所（制作の環境か、作者に頼んだか）付きで載せる。数回の試行なら「観察」、回数の上限を決めて繰り返した大事な数件だけ「傾向」と書く
  - 試し方は指示に従う。作者の設定が混ざらないよう、雛形の確認と同じ切り離し（design §8.7）で動かす
  - 偽の秘密と、壊れても困らない操作だけで試す。本物のホームや認証情報に触れる形は動かさない
  - API キーを使わない。環境に `ANTHROPIC_API_KEY` やクラウドの事業者の認証の変数があれば、試さずに報告する
- **注釈付きのセッション記録**：制作の環境と制作の記録（planning/production-log.md など）だけから作る。再構成したものは、そう書く。作者の手元の記録は使わない
- **比喩付きの図**：requirements §6.6 の比喩（広い机＝コンテキスト、毎回読み直す受験者＝全履歴の送信、積み木＝プロンプトキャッシング、議事録だけ残す＝圧縮、別室の部下＝サブエージェント、山を張る受験生＝ハルシネーション、お願いと鍵）を使う。同じ仕組みには、全ページで同じ比喩を使う
- **診断のチェックリスト**は症状のページの本体である（型の手引き symptom）。**雛形**は §12

## 8. 根拠の強さ

元：design §6.6、requirements §6.2、decisions 2026-11-03 方針 A3

研究や数値を根拠にする主張には、主張の文の後に根拠の印を付ける（作る予定：check_pages.py「根拠の印」）。公式の文書で確かめた機能の挙動には印を付けず、出典で示す。

| 印 | 使うとき |
| --- | --- |
| （根拠：強） | RCT・メタ分析・大規模な実験・主催者の規約や公式の記録 |
| （根拠：中） | 小規模な研究・企業の一次の報告・複数の実務家の一致 |
| （根拠：弱） | 単独の経験談・二次の報道・立場の表明 |
| （類推） | 隣接分野の結果を当てはめた主張。強さと並べるときは（根拠：強・類推）と書く |
| （推論・実践例なし） | 研究も実践例もない推論・独自の提案。必須のページの中心にしない |

- 研究の結果は、どのモデル・どの世代の結果かを書く。旧世代や他社のモデルの結果を、現行の Claude の傾向として書かない
- 小さな研究の結果は「傾向」とし、標本の大きさを添える
- 根拠の弱い数値を使うなら「自己申告」「経験則」と書き、主張の根拠にしない（§14）
- 実践者の間で割れる論点は、「公式の立場」「実践者の幅」「この教材の推奨」の三段で書く

## 9. 変わりやすい値

元：design §6.7・§8.4・§9.1、requirements §6.1、decisions 2026-11-03 方針 A7

次のものは本文に手で書かない。`data/facts.yml` の項目を目印 `<!-- fact:begin <id> -->`〜`<!-- fact:end -->` で指し、値・決まった文・確認日は道具が書く。目印は段落の中でも使える。

- 数値（料金・上限・回数・割合・トークンの数・期間）
- 既定値（既定のモデル・effort・設定の既定）と、モデルごとの値や癖
- 成熟度（GA・beta・research preview など）と、research preview・experimental の機能の名前
- プランの名前と中身、モデルの世代の名前
- 名前の変更（旧名・今の名前・変わった時期）、機能が入った版と、要る最低の版
- 大会の規則の版と、AI の成績
- 第三者のツールの成熟度と確認日

決まり：

- 目印の組を空で置き、`gen_site.py --page <id>` で埋める。ない id を指すと止まる（検査：check_pages.py「facts の id」）。目印の外に数値ファイルの値と同じ値を手で書くと、警告が出る（検査：check_pages.py「目印の外の数値」）。この検査は照合の型を持つ項目だけを見るので、検査に頼らず自分で避ける
- 数値ファイルにない値が要るときは、本文に書かず、数値の提案のファイルに書く（§21）。本文は、その数字なしで読める形にし、提案の `used_in` と報告に、目印を置く場所を書く（値が入ったら、メインか本文の担当が目印を置く）。検証役がそれも出典と照らし、メインが数値ファイルに足す
- 面やモデルで違う値は、一つに丸めない（数値ファイルは「モデル × 面」の表で持つ）。公式同士が本当に食い違うときは、提案に両方の出典を書く（数値ファイルが「食い違いあり」と持つ）
- モデルごとの公式の指針は、本文には「既定から始めて測る」ことと症状・対処を書き、モデルごとの値は数値ファイルに置く
- 機能の使い方（月の単位で変わる層）は本文に書いてよい。ページの確認日と版は、検証役が `verified`・`verified_with` に書く
- summary・signs・題名に、変わりやすい値を書かない（提案するときも）

## 10. ほかのページを指す

元：design §8.4・§8.5・§4.2、decisions 2026-11-03 方針 A5・「大会の規則の版」

- claude-atlas のほかのページは、ふつうリンクの目印 `<!-- link:begin <id>[#<anchor>] -->`〜`<!-- link:end -->` で指す。道具が相手の段階を見て、公開しているページならリンクを、未公開のページなら「題名（準備中）」を書く。相手を公開すると、道具が書き直す
- 目印の間の文字は道具が書く。前後の文は、相手の題名が入っても読めるように書く
- 手書きの Markdown のリンク（`../<field>/<id>.md`）で未公開のページを指すと止まる（検査：check_pages.py「未公開のページへのリンク」）。手書きにするなら、相手が draft 以上で、節を指すなら相手の sections にある anchor にする
- 前提・次に読む・関連はテンプレートが出すので、本文に並べない。本文で触れるのは、話の流れで要るところだけにする
- 持ち主でない内容は、持ち主のページ（境界の表。design §4.2）を指し、本文で繰り返さない
- 用語集の語は、ページの中で最初に出たときに1回だけ、用語集の節を指す（見出しの中では指さない）
- 外のサイト：公式の文書は、転送されている URL なら転送先の URL で書く。atcoder.jp・codeforces.com へのリンクは張ってよいが、中身を開かない。競技の練習法と AtCoder の規則の細部は kyopro-atlas を指す（§16）

## 11. 出典と、事実の確かめ方

元：design §6.8・§6.1・§9.1、requirements §11

- 事実（機能の挙動・数値・既定値・規則）は、一次資料で確かめてから書く。記憶で書かない
- 調査資料も AI が書いたものである。材料の調査資料の主張は、使う前に一次資料で確かめる。訂正・注記の付いた主張（research/22〜28 と、各資料の【2026-11-03 訂正】【2026-11-03 注記】）は、訂正の後の内容で書き、訂正の前の主張を根拠にしない
- 公式の文書は改稿される。調査資料の要約でなく、今の公式の文書を読んで確かめる
- ページの `sources` で出典の id を指す。新しい出典は `data/sources.d/<ページの id>.yml` に足す。形は `schema/sources.schema.json` に従う（出典は `sources` に、id・URL・題名・種類・発行者・言語・確認日を書く）（検査：check_pages.py「sources の id」）
- 足す前に、`data/sources.yml` と `data/sources.d/` に同じ URL がないかを探す。同じ URL の出典を二つ作らない（検査：check_pages.py「出典の URL の重なり」）
- 転送されている URL は、転送先の URL を記録する
- 新しいドメインは、資料にする前に `uv run python tools/check_noai.py <URL>` で AI の利用を断る指定を確かめ（検査：check_noai.py）、結果を同じファイルの `domains` に書く。断る指定があれば使わない
- atcoder.jp・codeforces.com は開かない（検査：H1 の deny）
- ページ末尾の「参考」の節は、道具が `sources` から作る（検査：gen_site.py --check）。手で書かない
- 写さない：公式の文書を訳して載せない。ほかの記事の文を転載しない。言い回し・文の並び・例をそのまま使わない。公式の日本語版に合わせるのは訳語だけで、文は自分で書く
- 実在の人物・団体についての主張は、一次資料で確かめたことだけを書く（§15）

## 12. 雛形

元：design §6.9・§8.7、decisions 2026-11-03 方針 B2・「危ない雛形を試す場所」、2026-11-04「文書にない回避方法」

- 本文に載せる設定や雛形（settings.json・フック・スキル・サブエージェントの定義・CLAUDE.md の例・プロンプトの型）は、`snippets/<id>/<名前>.<拡張子>` に置く。期待は `snippets/<id>/<名前>.expect.yaml` に書く
- 雛形の種類は `schema/site.yml` の `template_kinds` にある。載せる雛形は catalog の `templates` に従う
- 期待には、雛形を置く場所（user・project・local）と条件を書き、「この操作が止められる」「この行が出る・出ない」の形にする。出力の完全一致にしない（検査：check_templates.py）
- 本文には、目印 `<!-- gen:begin snippet <id>/<名前> -->`〜`<!-- gen:end snippet <id>/<名前> -->` を置き、道具に写させる（検査：gen_site.py --check）。取り込みの記法（`--8<--`）を使わない。本文に雛形を手で写さない
- 確かめた版・系列・日付と、要る最低の版は、道具が本文に書く。手で書かない
- 確かめた結果の `verified.yaml` は、雛形の動作の検証役が書く。執筆者は書かない
- 雛形は、動作確認の有無にかかわらず、なるべく多く載せる。動作を確かめていない雛形には、道具が「動作を確かめていない雛形」と書く。安全とデータの雛形（`<名前>.expect.yaml` の `safety: true`）には、守りとして頼る前に自分の環境で確かめるよう促す一文も道具が書く（decisions 2026-11-04「雛形の動作確認」。前の決まり「確認を通るまで載せない」は改めた）
- この環境で試せない雛形（使い捨てのコンテナ・/etc に書く管理設定・API キーが要る `--bare`・GitHub Actions）は、既定では載せず、条件と概念だけを書く
- 回避された仕組みを、守りとして勧める雛形は載せない（確認を通らない）
- 静的な検査（検査：check_templates.py）は自分で流してよい。実機の確認（作る予定：check_templates.py --live）は雛形の動作の検証役が行い、執筆者は指示があるときだけ流す。試すときは §7 の決まり（偽の秘密・壊れても困らない操作・API キーを使わない）を守る

## 13. 図と表

元：design §6.10・§8.5・§1.2、catalog/README §4.7

- 図は `docs/img/<id>/` に置く。種類は `schema/site.yml` の `visual_kinds` にあり、載せる図は catalog の `visual` に従う
- 動く図（dynamic）は、動かすことで分かりやすくなるものだけにする（全体で数個）
- 図の前後に、図の要点を文章で書く。図が描かれない環境や、AI が Markdown だけを読むときにも通じるようにする。代替テキストは図の要点を言い、120字以内にする（textlint は代替テキスト全体を1文と数え、120字を超えると警告になる。詳しい中身は図の前後の文章に書く）
- ライトとダーク、幅 390px（スマホ）で読めるようにする。色だけで区別せず、線の種類やラベルも使う（検査：render_pages.py）
- SVG は、文字をテキストのまま置き、`viewBox` と同じ比の `width`・`height` を付け、背景を白で塗る（透明だとダークで読めない）。1枚の幅は 400 程度までにし、横に広いものは2枚に分ける（検査：check_svg.py）
- Mermaid は、サイトに置いた写しで描かれる。外のサイトの画像・フォント・スクリプトを読まない
- Anthropic のロゴと意匠をまねない
- 表は列を絞る（スマホで横に広げすぎない）。列が多くなるなら、縦横を入れ替えるか、2つの列を1つのセルにまとめる
- data から作る表（比較の表・台帳の表など）を手で書かない（型の手引き）

## 14. 書かないもの・軽く扱うもの

元：design §6.11・§4.1、requirements §6.3、decisions 2026-11-03 方針 B1〜B4・B6（B1 は 2026-11-04「文書にない回避方法」で改めた）・「断られたときの頼み直し」

**軽く扱う**（公式へのリンクで済ませる）

- インストールと OS 別の設定、全コマンド・全設定キー・全フックイベントの網羅、API のパラメータとコードの例
- research preview・experimental の機能の操作手順（概念だけにし、成熟度は数値ファイルから出す）。周辺製品は一覧のページだけにする
- ただし、本体に入って読者がふつうに触れる機能（会話の中の Design・Docs、検証に使う Claude in Chrome など）は、使い方まで書く

**書かない**

- 根拠の弱い数値を主張の根拠にすること（使うなら「自己申告」「経験則」と書く）。検証済みの数値のない高速化の成功例。ベンダーの効果の数値を、中立の事実として扱うこと
- 安全装置を外す近道を勧めること（`--dangerously-skip-permissions` の普段使いなど）
- 攻撃の手口の細部（手口は型と仕組みまでにする）。載せる再現は、送信・削除・秘密の読み取りを伴わない無害なものだけにする。回避の手順と、AI を禁じる課題の隠し指示を外す方法は書かない
- 文書にない回避方法：見つけても報告はせず、その方法に触れない形で書く。方法そのものを、本文にも報告にも書かない（報告も公開のリポジトリに残る）
- 利用ポリシーを回避する頼み方（言い換え・分割・偽の文脈）。断られたときは、公式が案内する手段だけを書く
  - 本当の目的と文脈を足す（偽らない）
  - 巻き戻しや新しい会話で、引き金になった内容を会話から外す
  - 誤判定を報告する
  - 専門の仕事には、検証の制度を案内する
  - アプリの自動のモデルの切り替えは、仕組みとして説明する
- AI が書いたと分からなくする方法（「AI 臭さ」は読みやすさの品質として扱う）
- 特定の個人の構成を標準として示すこと（示すなら反対意見と並べる）
- 呪文（「think hard」「CRITICAL: You MUST」など）を、効く手法として教えること
- 日付と版のない、機能・既定値・価格・利用枠の説明。日付と版のない「この大会では AI が使える／使えない」という断定
- モデルの「性格」を固定的な事実として教えること（自分の環境で観察する対象として扱う）
- 「複数の AI レビュアーが一致したから正しい」という判断。「考察は人間にしかできない」という断定
- AI 単独の優勝事例を「真似る方法」として紹介すること（勝因の構造だけを取り出す）
- 自律ループで戦略そのものを改善させる手順（扱うのは、仕様の決まった実装の作業に限った、停止の条件つきの反復だけ）
- プレモーテムを、効果が実証された手法として紹介すること
- AI を禁止する大会を目指す読者に、本番での利用を前提にした手順だけを教えること
- 法令の解釈と、社内規則の回避
- 研究や事例の紹介だけの節（研究や事例は、根拠として各所に置く）

## 15. 実在の人物・団体・第三者

元：design §6.12、decisions 2026-11-03 方針 A1・A2・「本人の振り返りの名前」

- 実在の人物・企業の事例は、出典付きで名前を出してよい。自己申告の数値は「自己申告」と書く
- 否定的な文脈（失敗例・古い助言・評価）では、実在の個人や著作を名指ししない。助言の文言・時期・撤回を、一次資料で書く
- 本人が自分の経験を振り返った記事は、本人の言葉として紹介してよい（名前を出してよい）。順位などは「自己申告」と添え、評価の語を使わない
- 第三者のツールは、考え方の例として名前を出すだけにし、推薦しない（推薦の一覧にしない）。名前を出すときは成熟度と確認日を付ける（§9）
- 既存の書籍・講座は出典に挙げるだけにし、評価や推薦をしない。公式の教材（Anthropic Academy・公式の文書）は案内する
- Anthropic の AI Fluency（4D）は参考文献に挙げるだけにし、構成や共通の言葉に使わない
- 実在の人物・団体についての主張は、一次資料で確かめたことだけを書く

## 16. 大会の規則とコンテスト

元：design §6.13・§4.1、decisions 2026-11-03 方針 A4・A5・「大会の規則の版」「コンテストの分野」

- 大会の規則は、版・確認日・類型（禁止・部門分け・許可と開示）・一次資料へのリンクだけを数値ファイルに持つ。条文の要約を載せない。一次資料で確かめていない値は、下書きでも出さない
- 版は、主催者の公式 X など、AI の利用を断るドメインの外の一次資料で確かめたものだけを使う。確かめられない版は「未確認」とし、規則のページへのリンクだけを置く。作者に確かめを頼まない
- 「過去問の練習には規則が適用されない」と断定しない（確かめられていない。「未確認」と書く）。調査資料 11 の AtCoder の規則の「確認済み一致」を根拠にしない
- 七つの形式（requirements §4.3）を、早見表と確認表で同じ厚さに扱う。例は AtCoder（ABC・AHC）から多く取る。作者の参加の記録は使わない
- 競技の練習法と AtCoder の規則の細部は kyopro-atlas を指し、claude-atlas は AI への渡し方と確かめ方に絞る
- コンテストの分野は、コンテストに固有の論点だけにする。一般化できる論点はほかの分野のページに書き、例の場面にコンテストを使う

## 17. 安全の既定

元：design §6.6、decisions 2026-11-03「安全の既定の勧め方」

- 安全の既定は、公式の既定（auto モード）を基準にしてその限界を書き、比例則に沿って段階ごとに示す。中身は、任せる段階からはサンドボックスと秘密の読み取りの禁止、無人の実行は使い捨ての環境、預かったデータは契約のある面だけ、である
- 正本は safety の安全の早見表の節（`default-safety-settings#by-stage`）である。ほかのページは段階ごとの既定を書き直さず、この節をリンクの目印で指す（食い違わないようにするため）

## 18. 作者の承認が要る文

元：design §6.1・§7・§8.5、decisions 2026-11-03「公開する段階」「作者が目を通す範囲」

- 公開の約束・方針・ライセンスに関わる文は、作者の承認を得てから出す（下書きでも）。承認に回すのは、出典と AI 利用の方針のページ（ai-and-sources。「完成」の意味を含む）、全ページの冒頭とフッターの非公式の文、この辞典の引き方（how-to-use）の「誤りや古い情報の報告」と「確認日と期限切れ」の節である
- これらの文は、承認の前は本文に入れない。案を報告の「メインに判断してほしいこと」に書く（draft にすると公開されるため）
- ほかのページにも、約束や方針の文（「必ず〜する」「〜を保証する」「返事をする」など）と、注意書き（安全を保証しない・法的な助言ではない）を足さない。注意書きは方針のページとサイトの文が持つ
- 守れない約束を書かない

## 19. 段階と更新日

元：design §10.2・§3.3・§9.2、decisions 2026-11-03「公開する段階」「鮮度の更新の承認」

- 段階は、stub → draft（執筆者）→ reviewed（検証役。verified も書く）→ done（メイン）と移る。執筆者が動かすのは、stub から draft だけである
- draft のページは「下書き・未検証」の帯付きで公開される。要点と本文がそろい、検査のエラーが0になってから draft にする
- 直しの担当は、指摘を直して報告する。直した後に段階を動かすのは検証役である。読者に見える中身を変えたら `updated` を直す
- 鮮度の点検の直しで、教材の推奨・安全の既定・古くなった助言の台帳の状態が変わるものは、作者の承認が要る（指示に従う）。日付・数値・名称の直しは要らない

## 20. 書き終える前の検査

元：design §8.6・§10.5

自分のページについて次を流し、エラーを0にしてから報告する。警告を残すなら、理由を報告に書く。コマンドの細かい形は、道具ができたら tools/ の説明に従う。

| 何を | 道具 |
| --- | --- |
| 目印を埋める（数値・リンク・雛形・参考・生成の部分） | `uv run python tools/gen_site.py --page <id>`（検査：gen_site.py --page） |
| front matter・参照・目印・数値と出典 | （検査：check_pages.py） |
| 書き方（prh を含む） | `npx textlint docs/<field>/<id>.md`（検査：textlint）。直せるものは `--fix` を足すと直る。対象の全体は `npm run lint:text` |
| 雛形の静的な検査 | （検査：check_templates.py） |
| SVG | （検査：check_svg.py） |
| 描画（幅 390px のライトとダーク） | （検査：render_pages.py）。できれば自分のページを描いて見る |

- サイト全体のビルドと `tools/check_all.py` は、メインが commit の前に流す。担当が流してもよいが、commit はしない

## 21. 報告の形

元：design §10.3・§10.2・§3.3、design-review DR-12

報告はファイルに書いてから終える（置き場所は指示に従う）。止まっても、報告のない担当だけを流し直せば再開できるようにするためである。見出しはこの順に置き、書くことのない見出しも残して「なし」と書く。「確かめていないこと」は空にしない。

```markdown
# 報告：<担当>（<ページの id>）

- 手引きの版：共通 <版>・型 <版>

## 1. 書いたファイル
## 2. 直したこと
## 3. 範囲を越えたこと
## 4. 止められた操作
## 5. メインに判断してほしいこと
## 6. 提案
## 7. 検査の結果
## 8. 確かめていないこと
## 9. 使用量
```

- **書いたファイル**：パスの一覧。front matter で変えたキー（sections・stage・updated・sources）も書く
- **直したこと**：直しの担当のとき。指摘ごとに、指摘の番号・直したこと・直さなかったならその理由を書く
- **範囲を越えたこと**：書いてよいもの（§2）の外に触れたもの
- **止められた操作**：hook や permissions に止められた操作と、代わりにしたこと
- **メインに判断してほしいこと**：上位の規則との食い違い、決めきれない点、作者の承認が要る文の案（§18）
- **提案**：front matter のほかのキーの直しは、次の形の YAML で書く。メインが承認したら道具が当てる

```yaml
frontmatter:
  - {id: instructions-ignored, key: aliases, before: [指示を無視される], after: [指示を無視される, ルールが守られない], reason: "…"}
```

  共有のファイルへの提案（用語集：語・1〜2文の定義・anchor の案、prh：規則、data：項目、手引き・チェックリスト：直す所と理由）も、ここに書く
- **数値の提案のファイル**：新しい数値は、報告とは別の YAML のファイルに書く。置き場所は指示に従い、指示がなければ報告と同じフォルダの `facts-<ページの id>.yml` にする。`fact` は data/facts.yml の facts の1項目と同じ形（`schema/facts.schema.json`）にし、メインがそのまま写せるようにする。検証役がこのファイルも出典と照らす

```yaml
proposals:
  - fact: {id: …, title: …, value: …, sources: […], checked: 2026-11-20, status: …}
    used_in: [<ページの id>#<anchor>]
```
- **検査の結果**：流した検査と、エラーと警告の数。残した警告とその理由
- **確かめていないこと**：確かめきれなかった事実、試していない面や OS、読めなかった出典など
- **使用量**：道具の呼び出しの回数・Web の取得の回数・かかった時間（分かればトークン）
