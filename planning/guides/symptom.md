# 型の手引き：symptom

- 版：2026-11-04 第1版（工程6a。試作〔工程7〕で確かめて確定する）
- 共通の手引き（common.md）と一緒に使う。ここには、この型の構成の目安と、この型に固有の注意だけを書く

## 1. 用途と、必ず持つもの

元：design §2.2・§3.1・§3.3・§4.1

- 用途：症状 → 原因 → 対処の振り分け
- 冒頭の要点のほかに必ず持つもの：診断のチェックリスト（六つの原因を安く確かめられる順。関われば人の側の落とし穴も）と、原因ごとの振り分け先（front matter の `routes`）
- 1症状1ページにする。題名は読者の言葉である。原因の切り分けと振り分けが本体で、対処の本体は各分野のページに任せる
- level は、その症状に出会う段階である（catalog が決める）。前提は、診断を読むのに要る概念のページだけにする

## 2. 構成の目安

元：design §6.3

- 要点 → よくある形（読者の言葉）→ 診断のチェックリスト（六つの原因を安く確かめる順。関われば人の側の落とし穴）→ 原因ごとの対処へのリンク（routes から生成）→ 判断例 → 予防（仕組みに移す）

## 3. この型に固有の注意

元：design §4.1・§6.3・§8.4、requirements §3.2・§6.6、design-review DR-02

- 「よくある形」は、signs と同じく読者の言葉で、どんな場面で何が起きるかを書く。機能名を答えとして書かない
- 診断の節は、catalog の sections にある anchor（`diagnosis`）で置く。ページの `prevents` の原因を、`schema/site.yml` の `prevents` の並び（安く確かめられる順）で並べ、`pitfalls` があればその後に並べる。1項目に、原因の名前・何を見るか・どう確かめるか（安い手から）を書く（作る予定：check_pages.py「診断の順」）

```markdown
## 原因を安く確かめる順 {#diagnosis}

1. **見えていない**：…を見る。…で確かめる
2. **散らかっている**：…

<!-- gen:begin routes -->
<!-- gen:end routes -->
```

- 原因ごとの対処へのリンクは、診断の節の中のチェックリストの後に目印を置き、道具が routes から書く（検査：gen_site.py --check）。目印の名前は、道具とともに確定する。手でリンクを並べない。振り分け先を変えたいときは、routes の直しを提案する（共通の手引き §21）
- 対処の手順を書かない。ただし、消された直後・漏れた直後の初動はこのページが持つ（対処のページは同じ節を持たず、このページを指す）
- 判断例は、仕組みに移すか、どの原因から手を付けるかなど、読者が迷うところで書く（共通の手引き §7 の形）
- 予防は、繰り返す原因を仕組み（縛る）に移す道を書き、enforce などのページをリンクの目印で指す
- 必須の振り分け先がない原因は、第一波では先が「準備中」になる。それでも診断の項目は書く（「準備中」は道具が出す）
- 断られた・止められた症状は、公式が案内する手段だけを書く（共通の手引き §14）
