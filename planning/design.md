## 1. 前提の整理

### 1.1 読者と目的

- **読者**：Claude や Claude Code をかなり使っているが、知識が足りず使いこなせていない人。どのページも開発の経験（git・ターミナル・プログラミング）を前提にし、非エンジニア向けの説明は省く（decisions 2026-11-03）。公開のリポジトリとサイトで、不特定多数に向けて書く
- **使われ方**：うまくいかなかった場面ややりたいことから引く辞書。冒頭の要点で用が足り、必要なら原理へさかのぼれる（requirements §1）
- **重心**：機能の紹介ではなく判断を教える。なぜうまくいかないか、次に何を足しどう確かめるか、どこまで任せて何を人が握るか
- **核**：症状から引く索引、確かめ方と評価、日本語の出力品質、古くなった助言の台帳（requirements §1）
- **背骨**：四つの原理（見せる・確かめる・縛る・握る）と比例則、失敗の原因の二つの軸（Claude 側の六つの「ない」と、人の側の五つの落とし穴）、委任の段階のレベル（requirements §3、D1・D2・D8）

### 1.2 使われ方と、そこから来る設計の条件

| 使われ方 | 設計の条件 |
| --- | --- |
| 症状から引く（「指示が守られない」） | symptom の signs を読者の言葉で書き、逆引き辞典を生成する。症状のページは、原因を安く確かめられる順の診断と、対処のページへの振り分けを持つ |
| やりたいことから引く（「長い作業を任せたい」） | goal の signs、用途別レシピ、ロードマップ |
| 状況から引く（「チームで導入する」「大会に出る」） | situation の signs と scenes、題材の入口 |
| 名前で引く（機能名・旧名・公式の訳語） | aliases（英語名・旧名・公式の日本語訳）、用語索引、検索 |
| 信用してよいかを見る | 冒頭のバッジ（確認日と版・変わりやすさ・成熟度・強制力）、根拠の強さの表記、期限切れの注意書き、下書きの帯 |
| 次の段階へ進む | level と prerequisites から、ロードマップと知識マップを生成する。比例則に沿い、上の段のページは確かめる・縛るのページを前提に持つ |
| 自分の AI に教材を読ませる | llms.txt（1ページ1行）。どのページも単独で読めるように書く |
| スマホで読む | 表の列を絞り、描画の検査を幅 390px で行う |

### 1.3 成功の条件

1. 症状の言葉で引いて、目的の節に3回のクリック以内で着く（全体の検証で、逆引きの項目から20ほどを試す）
2. どのページも、冒頭の要点で「何ができるか・いつ引くか・前提」が分かり、本文に判断（なぜ・どこまで任せるか・どう確かめるか）がある
3. 変わりやすい値（数値・既定値・名称・成熟度・大会の規則）は数値ファイルを経由し、確認日と出典を持つ。版に依存する記述には確認日と版がある。実在の人物・団体について、一次資料で確かめていない主張がない
4. 用語と表記が全ページでそろう（公式の日本語版の訳語を基準にする）
5. 確認日が期限を過ぎた情報は、読者に見える
6. 制作が止まっても、どこまでできて次に何をするかがファイルから分かり、報告のない担当だけを流し直せば再開できる
7. 公開する前に、描画の検査と書き方の検査がエラー0

## 3. レベルと分類

### 3.1 レベル（`level`）

| level | この段階の読者 | 上がる条件（ロードマップの節目） |
| --- | --- | --- |
| 使う | 対話で頼み、返答を読んで使う | 期待外れの原因を「見えていない／散らかっている」と言い分けられる |
| 整える | 頼み方・資料・会話の長さを整え、結果を確かめて直す | 完了の条件と確かめ方を、依頼に含めて渡せる |
| 任せる | 計画させてから任せ、長い作業を途中で舵取りする | 二回同じ注意をしたら、仕組みに移すと判断できる |
| 仕組みにする | CLAUDE.md・skills・hooks・permissions・MCP・plugins で常設化し、共有する | 無人で動かす前の五つの問いに答えられ、検証器を自分で確かめられる |
| 回す | 並列・無人・定期・プログラムから動かす | ― |

規則：

1. そのページが**最初に要る段階**を level にする（機能の難しさや使用期間ではない。D8）
2. 型が `guide`・`hub`・`ledger` のページは level を持たない（`start` の分野のページはこれらの型にする）。`symptom` は、その症状に出会いやすい段階にする
3. 前提に、そのページより上の段のページを置かない（検査で警告する）
4. **比例則**：任せる幅を広げる内容（自律・並列・無人・権限の緩和）のページは、対応する確かめる・縛るのページ（`verify`・`eval`・`enforce`・`safety` の分野）を前提か関連に持つ（検査で警告する）
5. 節の level（`sections` の level）は任意とし、使うときはページの level 以上にする（kyopro-atlas では手間に見合ったかが分からなかったので、必須にしない）
6. 「使う」のページは少なく短くし、「整える」〜「仕組みにする」を厚くする（requirements §3.3）

### 3.2 分類の軸

| 軸 | キー | 値 | 使い道 |
| --- | --- | --- | --- |
| 分野 | `field` | §2.1 の23 | ナビゲーション |
| レベル | `level` | §3.1 の5段階 | バッジ・ロードマップ・知識マップの色 |
| 優先度 | `priority` | 必須・推奨・任意 | 初版の範囲。必須のページの前提は必須にする（検査） |
| 面 | `surfaces` | `app`・`claude-code`・`api`（複数可） | タブの有無、面ごとの一覧 |
| 原理 | `principle` | 見せる・確かめる・縛る・握る（1〜2個） | 原理のページへの逆リンク、一覧 |
| Claude 側の原因 | `prevents` | 見えていない・散らかっている・確かめていない・縛っていない・合っていない・境界がない | 症状ページの診断、逆引き |
| 人の側の落とし穴 | `pitfalls` | 預けすぎる・同意を根拠にする・やめられない・体感を信じる・みんなの案になる | judgment の一覧 |
| 場面 | `scenes` | 開発・文章・調べもの・データ分析・学習・コンテスト・チーム | 例がどの場面のものか。題材の入口の一覧 |

| `outdated_advice` | 任意 | 目次・執筆者 | 台帳の逆リンク | 台帳にある id |

- 機能の属性（成熟度・強制力・読み込みの時期・コンテキストのコスト・圧縮で残るか）は、ページの front matter に持たず、数値ファイルの機能の項目（§9.1）に出典と確認日付きで持つ。ページは `tracks` でその機能を指し、バッジと比較表は道具が作る（同じ値を何ページにも持つと食い違う。変わりやすい値は道具が書く）
- 1つのキーを2つの表示の役に使わない（kyopro-atlas の `nav_title` の不具合）
- 形式は `schema/page.schema.json`（JSON Schema）で検査する。語彙は `schema/site.yml` から読む

## 4. ページの粒度と分野間の境界

### 4.1 粒度の規則

1. **1ページ＝名前・症状・やりたいことのどれかで引かれ、独自の「なぜ」か判断を持つ1つの単位**。変種は節に、面ごとの違いはタブにする（面ごとにページを分けない。D9）
2. **症状のページは1症状1ページ**で、題名は読者の言葉にする。原因の切り分けと振り分けが本体で、対処の本体は各分野のページに任せる
3. **機能のページは1機能**（密接な系統は1ページにまとめ、節にアンカーを付ける）。公式リファレンスの網羅はしない（requirements §6.3）
4. **比較のページは、混同されやすい組だけ**にする。属性の表は数値ファイルから作り、手書きするのは判断例
5. 研究や事例の紹介だけのページは作らない。根拠として各ページに置く
6. **コンテストの分野は固有の論点だけ**にする（D5）。一般化できるものは各分野のページに置き、`scenes` にコンテストを付ける
7. research preview・experimental の機能は、概念だけの短いページか節にする（requirements §6.3）。周辺製品は一覧のページだけにする（D15）。ただし本体に入って読者がふつうに触れる機能（会話の中の Design・Docs、検証に使う Claude in Chrome など）は、使い方まで書く（decisions 2026-11-03 の方針 B6）

## 5. 目次（catalog）の作り方

### 5.1 形式

- `planning/catalog/registry.yaml`：全候補の id・分野・題名・優先度・材料の一覧。目次の担当どうしが、互いのページを id で指せるように、最初に作る
- `planning/catalog/<field>.yaml`：分野ごとの全ページの詳細。項目は、§3.3 で目次が書くキーに、目次だけの項目（`materials`：執筆の材料になる調査資料の節、`templates`：載せる予定の雛形、`visual`：図の案、`wave`：第一波の核か、`level_evidence`：段階の根拠、`notes`）を足したもの
- 詳しい形式と規則は [catalog/README.md](catalog/README.md)

### 5.2 作り方

1. 担当1つが、調査資料（00 §3、11 第1〜2節、requirements §4.3〜4.4）から `registry.yaml` を作る
2. 分野のまとまりごとの担当が、並列に `<field>.yaml` を書く。ほかの分野のページは registry の id で指す。新しいページは自分の分野にだけ足してよく、ほかの分野への提案は `open_issues` に書く
3. メインが `tools/check_catalog.py` で検査する：形式・語彙・id の一意・前提の解決・循環・レベルの逆転・必須の前提は必須・比例則・入ってくる道のないページ・第一波の数
4. 工程4で、別の担当が目次も批判的に読む。指摘を直して第2版にする
5. 骨格（工程8a）で catalog から front matter を作り、それ以後は front matter が正になる。catalog は凍結し、執筆の指示（materials・templates・visual）としてだけ使う

### 5.3 規則の要点

- **id**：英小文字・数字・ハイフン。題名の英訳か、公式の英語の機能名にする。骨格の後は変えない
- **題名**：読者が引く言葉にする（症状は読者の言葉、機能は公式の名前）。公式の日本語版の訳語に合わせる（§6.2）
- **aliases**：公式の英語名・旧名・公式の日本語訳・よくある言い換え
- **summary**：1文目は何ができるか（何が分かるか）。2文・120字以内。「このページ」「ここでは」「扱う」「紹介する」「まとめる」を使わない（schema/site.yml の summary_banned_words）。**変わりやすい値（数値・既定値・料金・モデルの世代）を書かない**
- **signs**：読者の言葉。symptom は困りごと、goal はやりたいこと、situation は置かれた状況。機能名を答えとして書かない
- **prerequisites**：直接の前提だけ（4つまで）。前提と related に同じページを置かない。入ってくる道のないページを作らない
- **priority**：00 の表を基本にする。新しいページの優先度は目次の担当が決め、理由を `notes` に書く（requirements §4.2）
- **wave**：第一波の核のページに付ける（核の分野の総論と、その分野のほかのページの多くが前提にするページ）
- **工程2の訂正を守る**：訂正・注記の付いた主張（research/22〜28）を、要約やサインの根拠にしない

## 6. 編集方針

### 6.1 共通の原則

1. **判断を教える**：機能の説明で終わらせず、なぜうまくいかないか・どこまで任せるか・どう確かめるかを書く
2. **冒頭で用が足りる**：冒頭の要点（§6.4）で、辞書として引いた人の用が足りるようにする
3. **1ページで完結させる**：前提の説明は繰り返さずリンクするが、節を1つだけ読んでも何の話か分かるように書く（AI が断片で読む場合も同じ）
4. **面はタブで並べる**：同じ原理の面ごとの手段は、ページの中のタブ（アプリ／Claude Code／API）で並べる
5. **変わりやすい値を手で書かない**：数値・既定値・名称・成熟度・大会の規則は数値ファイルを経由する（§6.7）
6. **根拠の強さを示す**（§6.6）
7. **固定のテンプレートにしない**：§6.3 は目安で、薄い節を目安のために作らない
8. **公開の約束・方針・ライセンスに関わる文は、作者の承認を得てから出す**（下書きでも。decisions 2026-11-03）

### 6.2 文体と用語

- だ・である調（D16）。1文を短く、1段落1つの主張
- 開発の経験を前提にする（git・ターミナル・プログラミングの基本は説明しない）
- 機能名・コマンド・ファイル名・設定のキーは原文のまま書く
- **用語の訳語は、公式の日本語版（Claude Code の文書は全228ページに日本語版がある。research/27）の本文の多数派に合わせる**。公式で表記が割れている語（plan モード／プランモード、effort／努力レベル など）は、用語集で1つに決めて prh に入れる
  - 目次の題名は、research/27 §3.1 の案で揃えた（2026-11-04 の統合。表は `planning/batches/step3/brief-integrate.md` の M1）。割れている3語は仮に、plan モード・effort・許可ルール／確認ルール／拒否ルール（Claude Code の日本語版の多数派）とし、工程5で確かめる
  - API の機能名は、Platform の日本語版の訳語を調べるまで英語のまま書く（プロンプトキャッシングだけは Claude Code の日本語版の多数派）
- 独自の用語を見出しにし、公式の用語を併記する（D14。例：「お願いと鍵」＝非決定論的な指示と決定論的な制御）
- 半角英数字と全角文字の間に空白を入れる（kyopro-atlas と同じ。textlint で検査）
- 用語集のページを正とし、prh.yml はそこから作る

### 6.3 型ごとの構成の目安

| type | 目安の流れ |
| --- | --- |
| concept | 要点 → 何が起きるか（例）→ なぜそうなるか（比喩付きの図）→ 何に効くか（原理・原因へ）→ 誤解 → 関連 |
| feature | 要点（強制力・確認日と版のバッジ）→ 使いどころ（どの原因を防ぐか）→ 最小の使い方（面のタブ）→ 雛形（折りたたみ）→ 効かない場面・落とし穴 → 比べる相手 → 古くなった助言 |
| symptom | 要点 → よくある形（読者の言葉）→ 診断のチェックリスト（六つの原因を安く確かめる順。関われば人の側の落とし穴）→ 原因ごとの対処へのリンク → 判断例 → 予防（仕組みに移す） |
| comparison | 要点 → 比較の表（生成）→ 選び方（判断例）→ 組み合わせ方 |
| recipe | 要点 → 前提（確かめる・縛る）→ 手順 → 確かめ方 → 失敗したとき |
| judgment | 要点 → 何が起きるか（研究の根拠の強さを添えて）→ なぜ（人の側の仕組み）→ 判断例 → 握るもの → 確かめ方 |
| ledger | 要点 → 生成の表 → 読み方（台帳は「どの原理の回避策だったか」） |
| guide・hub | 自由（表とリンクが本体） |

### 6.4 冒頭の要点とバッジ

- 要点の囲み：「何ができるか（concept は何が分かるか）」「いつ引くか」「前提」。feature は「強制力（お願いか鍵か）」も出す（requirements §5.3）
- 要点の上のバッジの列：レベル・原理・成熟度・変わりやすさ・確認日と版（読者が、本文を読む前にどれだけ信用してよい情報かを判断できるように）。成熟度と強制力は数値ファイルから
- 要点の後に、aliases を並べた別名の行と、題名を主語にした1〜3文の導入を置く

### 6.5 面のタブ

- 面ごとに手段が違う話は、`pymdownx.tabbed` の「アプリ／Claude Code／API」のタブで並べる
- 面に固有の操作は、面の分野（`app`・`cli`・`api`）に置く
- 本文はプランに中立に書き、プランごとの差は数値ファイルの表に置く。Claude Code は WSL・Linux の CLI を基準にし、ほかの OS と IDE の拡張の動作は「未確認」と書く（方針 B5）

### 6.6 根拠の強さと書き分け

- 研究や数値を根拠にする主張には、根拠の強さ（強・中・弱）を付ける（requirements §6.2）。隣接分野からの類推は「類推」、研究も実践例もない推論・独自の提案は「推論（実践例なし）」と書き、必須ページの中心にしない（方針 A3）
- 研究の結果は、どのモデル・どの世代の結果かを書く。小さな研究は「傾向」とし、標本の大きさを添える
- 実践者の間で割れる論点は、「公式の立場」「実践者の幅」「この教材の推奨」の三段で書く
- 安全の既定は、公式の既定（auto mode）を基準にして限界を書き、比例則に沿って段階ごとに示す（decisions 2026-11-03）

### 6.7 変わりやすい値

- 本文に手で書かない。`data/facts.yml` の項目を、目印（§8.4）の間に道具が書き込む。数値だけでなく、数値を含む決まった文と確認日も道具が書く
- モデルの既定 effort のように面で違う値は「モデル × 面」の表で持つ（research/23）。公式同士が本当に食い違うときは両方の出典を残し「食い違いあり」と書く
- 目印の外に、数値ファイルの値と同じ値を手で書いていたら、検査が警告する

### 6.8 出典と AI の利用の指定

- 出典は `data/sources.yml` に1か所で持ち、ページは `sources` で id を指す。ページ末尾の「参考」の節は道具が作る
- 新しいドメインは、資料にする前に `tools/check_noai.py` で AI の利用を断る指定を確かめ、結果を sources に記録する。atcoder.jp と codeforces.com は開かない
- 転送されている URL は、転送先の URL を持つ（research/28）

### 6.9 雛形

- 本文に載せる設定や雛形（settings.json・hook・skill・subagent の定義・CLAUDE.md の例・プロンプトの型）は、`snippets/<id>/` に置き、本文には取り込みか折りたたみで置く
- 動作確認（§8.7）を通ったものだけを載せる。安全とデータの雛形は、本文を下書きで出すときも、確認を通るまで載せない（方針 B2）
- 確かめた版を記録し、本文に「確かめた版と日付」を道具が書く

### 6.10 見せ方

requirements §6.6 の見せ方を使う：Before/After（何が足されたかを注記）、比較表（生成）、比喩付きの図、注釈付きのセッション記録、判断例、検証ノート、診断のチェックリスト、雛形。

- 注釈付きのセッション記録は、制作の環境と制作の記録だけから作り、再構成したものはそう書く。作者の手元の記録は使わない（方針 A6）
- 検証ノートは、制作の環境で試した結果を日付と版付きで載せる。試行は基本は数回で「観察」と書き、大事な数件（英語への回帰など）だけ、回数の上限を決めて繰り返して「傾向」と書く（decisions 2026-11-03）

### 6.11 書かないもの

requirements §6.3 に、decisions 2026-11-03 の書き方の方針を足したもの：

- 根拠の弱い数値を主張の根拠にすること（使うなら「経験則」「自己申告」と明記）
- 安全装置を外す近道を勧めること。攻撃の手口は型と仕組みまで書き、無害な再現だけを載せる。回避の手順と、AI を禁じる課題の隠し指示を外す方法は書かない（方針 B1）
- 利用ポリシーを回避する頼み方（言い換え・分割・偽の文脈）。断られたときは、公式が案内する手段だけを書く（decisions 2026-11-03「断られたときの頼み直し」）
- AI が書いたと分からなくする方法（「AI 臭さ」は読みやすさの品質として扱う。方針 B4）
- 特定の個人の構成を標準として示すこと、呪文を効く手法として教えること、日付と版のない機能・既定値・価格の説明、モデルの「性格」を固定的な事実として教えること、ほか requirements §6.3 の各項
- 法令の解釈と、社内規則の回避

### 6.12 実在の人物・団体・第三者

- 実在の人物・企業の事例は、出典付きで名前を出してよい。自己申告の数値は「自己申告」と書く（D12）
- 失敗例・古い助言・評価などの否定的な文脈では、実在の個人や著作を名指ししない。助言の文言・時期・撤回の一次資料で書く。本人の振り返りは本人の言葉として紹介し、評価の語を使わない（方針 A1）
- 第三者のツールは例として名前を出すだけにし、推薦しない（D13）。既存の書籍・講座は出典に挙げるだけにする（方針 A2）
- 実在の人物・団体についての主張は、一次資料で確かめたことだけを書く

### 6.13 大会の規則

- 版・確認日・類型（禁止・部門分け・許可と開示）・一次資料へのリンクだけを数値ファイルに持つ。条文の要約は載せない（方針 A4）
- 主催者の公式 X など、AI の利用を断るドメインの外の一次資料で確かめた版だけを入れる。確かめられない版は「未確認」とし、規則のページへのリンクだけを置く（decisions 2026-11-03「大会の規則の版」）

### 8.3 道具（tools/）の層

kyopro-atlas の道具は、分野や段階の名前がコードに直書きされ、大きくなりすぎた（research/20 の C1）。claude-atlas では層に分けて作り直す。

| 層 | 中身 |
| --- | --- |
| 読む層（`tools/lib/`） | front matter・catalog・data・schema/site.yml を読み、ページのモデルを作る |
| 作る層（`tools/gen/`） | 生成物の種類ごとに1つ（nav・入口・一覧・逆引き・索引・知識マップ・ロードマップ・台帳・比較表・参考・数値・llms.txt・症状の原因別の表〔失敗の二つの軸のページの節。症状のページの prevents・pitfalls から〕） |
| 検査の層（`tools/checks/`） | 検査1つを関数1つにして登録する。試験も検査ごとに書く |
| 入口の CLI | `make_skeleton.py`・`gen_site.py`（`--check`）・`check_pages.py`・`check_catalog.py`・`check_templates.py`（`--live`）・`render_pages.py`・`check_svg.py`・`check_noai.py`・`textlint_targets.py` |

- kyopro-atlas から写して直すもの：`render_pages.py`（描画の検査）・`check_svg.py`・`check_noai.py`（写して直し済み）・`textlint_targets.py`、テンプレートの上書きと CSS・JS（バッジ・前提と次に読む・知識マップ・絞り込みの欄）。進捗の部品（解いた・理解した）は外す（D17）
- `tools/check_catalog.py` は工程3で作る（目次の検査）

### 8.4 生成物と目印

- 生成物はコミットし、CI で `gen_site.py --check`（作り直して差分がないこと）を確かめる
- 手書きのページの生成部分は `<!-- gen:begin 名前 -->` 〜 `<!-- gen:end 名前 -->` の間に道具が書く
- 変わりやすい値は `<!-- fact:begin <id> -->` 〜 `<!-- fact:end -->` の間に、道具が値・決まった文・確認日を書く。段落の中でも使える
- ページ末尾の参考の節は `<!-- gen:begin references -->` の間に、sources から道具が作る
- **毎回変わる値（内容のハッシュ・生成の日時）を生成物に入れない**。並列のブランチのマージで毎回衝突するため（research/20 の C2）。マージの後は `gen_site.py` を流し直す（衝突した生成物は main 側を取ってから作り直す）
- 本体を生成するページ（逆引き・用語索引・ロードマップ・知識マップ・台帳・年表）は、front matter に印のキーを持たない。どのページに何を生成するかは、作る層の設定に持つ

### 8.5 表示

- **バッジ**：テンプレートの上書きで、レベル・原理・成熟度・変わりやすさ・確認日と版、feature の強制力を出す
- **下書きの帯**：stage が draft のページに「下書き（別の担当の検証の前）」の帯を出す
- **期限切れの注意書き**：ページに、確認日（`verified` と、ページが含む数値の確認日のうち最も古いもの）と `volatility` を data 属性で出し、ブラウザの JS が今日との差を計算して、期限（365・90・30日）を過ぎたら注意書きを出す。ビルドした日に左右されず、生成物も毎回変わらない（requirements §7 の「ビルド時に出す」を改めた。format-and-operations F6）
- **骨格のページは公開しない**：`gen_site.py` が nav.yml に stub のページを `exclude_docs` として書き、ビルドから外す。公開するページから stub へのリンクは、`mkdocs build --strict` と `check_pages.py` で止める（INHERIT で `exclude_docs` が効くかは土台作りで確かめる）
- **ページ下部**：前提・次に読む・関連、段階と更新日、「このページの誤りを報告する」（Issue）
- **知識マップ**：kyopro-atlas の方式（分野ごとの表示と、ページから開くと祖先と子孫だけの表示）を写して直す
- **検索**：kyopro-atlas の日本語の区切りの設定（separator）を引き継ぐ。主な機能のページに `search.boost` を付けるかは試作で決める
- ライトとダーク、スマホの幅に対応する

### 8.6 検査（CI と手元）

土台作り（工程6）で、試作の前に次を用意する（kyopro-atlas の反省。research/20 の A1・A3）。

| 検査 | 方法 | CI |
| --- | --- | --- |
| サイトのビルド | `mkdocs build --strict`（validation は warn を strict で失敗に） | 毎回 |
| front matter | JSON Schema とキーの台帳（語彙は site.yml） | 毎回 |
| 参照 | 存在しない id・循環・レベルの逆転・必須の前提は必須・比例則・stub へのリンク・推移的に届く前提（警告）・症状のページの sign と同じ文のほかのページの sign（警告） | 毎回 |

### 8.7 雛形の動作確認

- **置き場所**：`snippets/<id>/<名前>.<拡張子>` と、期待を書いた `<名前>.expect.yaml`。確かめた結果は `snippets/<id>/verified.yaml`（版・OS・日付）
- **期待の形**：「出力の完全一致」ではなく、「この操作が止められる」「この行が出る・出ない」の形にする（research/20 の C5）
- **静的な検査（CI）**：JSON・YAML の形、skill と subagent の front matter の必須の項目、settings のキーの名前。公式の文書が案内する SchemaStore のスキーマは新しいキーに遅れる（v2.1.220 ごろのもの。research/28）ので、合わないときは警告にとどめ、実機の確認を正とする
- **実機の確認（手元）**：`tools/check_templates.py --live` が、リポジトリの外の使い捨てのフォルダと、専用の `CLAUDE_CONFIG_DIR` で、`claude -p --setting-sources project,local` を権限モードを明示して動かす（作者の `~/.claude` の設定が混ざらないようにする。research/28）。Claude Code は 2.1.314 以上（`--setting-sources` の漏れと、起動の失敗でも 0 で終わる不具合が直った版。research/22）
- **安全のための決まり**：偽の秘密と、壊れても困らない操作だけで試す。本物のホームや認証情報に触れる形は動かさない（decisions 2026-11-03）。始める前に、環境に `ANTHROPIC_API_KEY` がないことを確かめる（あると、確認なしに API キーで従量の課金になる。research/26）。`-p` では、信頼していないフォルダの `permissions.allow` が効かない点を期待に入れる
- **sandbox の雛形**：bubblewrap と socat で確かめる（2026-11-04 に入れた）
- **ここで試せないもの**（アプリの機能など）：作者にまとめて頼み、検証ノートにする。頼むのは必要最低限にする（decisions 2026-11-03）

## 9. 鮮度と品質を保つ仕組み

### 9.1 データの形

| ファイル | 1項目の中身 |
| --- | --- |
| `data/facts.yml` | id・値（面やモデルで違うなら表）・決まった文の型・出典（sources の id）・確認日・関わる版・状態（確認済み・未確認）・食い違い（公式同士が食い違うなら両方の出典）。機能（features）の項目は、成熟度・強制力・読み込みの時期・コンテキストのコスト・圧縮で残るか・入った版 |
| `data/sources.yml` | id・URL（転送先）・題名・種類（公式文書・公式ブログ・CHANGELOG・リリースノート・実践者・研究・報道）・発行者・言語・確認日・AI の利用の指定の確認（日付と結果）・写しの URL（Internet Archive。公式のページの改稿を見分ける手がかり。research/23） |
| `data/outdated-advice.yml` | id・古い助言・今どうするか・変わった時期と版・状態（撤回・置換・条件付き）・どの原理の回避策だったか・かつてなぜ正しかったか・自分の設定や記事で見つける方法・出典・確認日 |

数値ファイルに持つ表の候補（目次の担当の提案。形は土台作りで決める。提案の全文は `planning/batches/step3/open-issues.md`）：

- 面の属性：面ごとの、手を動かす主体・触れられるもの・動く場所・読む設定・PC を閉じても続くか・できないこと（surfaces#3）
- モデルと effort：既定の effort の「モデル × 面」の表、ultrathink が上げる段と効く版と面、fast mode の対象と料金、退役の予定（models#2）
- プランと料金：プランの表、上位のモデルの枠、usage credits の失効の期間、API の料金、agent teams の倍率とその条件（cost#2）
- 大会の規則と AI の成績：§6.13 の形（contest#4）
- 名称と旧名：今の名前・旧名・変わった時期。用語索引の旧名の表示と、変更の記録に使う（start#5・cost#1）
- 台帳の行の「変わった時期」の材料は、changes の目次の notes と changes#3

### 9.2 確認日と期限

- 確認日は主張（数値ファイルの項目）とページの二段で持つ。ページの確認日の表示は、`verified` と、ページが含む数値の確認日のうち最も古いもの（research/20 の I2）
- 期限：`volatility` が低なら365日、中なら90日、高なら30日（requirements §7）

### 9.3 期限切れの見せ方

- ブラウザで日数を計算して注意書きを出す（§8.5）。CI でも期限切れを警告する（失敗にしない）

### 9.4 点検の手順（鮮度の点検の skill）

1. 前回確認した版より後の、Claude Code の CHANGELOG、Help Center と Claude Platform のリリースノート、Anthropic のニュースを読む（プランの改名のように、リリースノートに載らず Help Center と料金のページにだけ出る変更もある。research/22）
2. 出てくる語を、ページの `tracks`・`aliases` と数値ファイルの id に照らし、影響のあるページと数値の一覧を出す
3. GitHub の Issue にする
4. 直す：日付・数値・名称の更新は、メインの判断と別の担当の検証と機械の検査で行う。**教材の推奨・安全の既定・古くなった助言の台帳の状態が変わる更新は、作者が承認する**（decisions 2026-11-03）。安全の既定の正本は safety の安全の早見表の節（`default-safety-settings#by-stage`）で、点検の skill の手順にこの節を名指しする
5. `verified` と数値の確認日を更新する
6. リンクの切れと転送も確かめる
7. 定期の実行は任意にする（requirements §7）

### 9.5 外からの報告

- Issue のテンプレート（ページの誤り）を置き、種類に「情報が古い」を足し、ページの確認日と版の欄を足す。各ページの「このページの誤りを報告する」から、題名・URL・確認日を入れて開く
- アクセスの解析は入れない（decisions 2026-11-03）

### 10.2 サブエージェントの使い方

| 役割 | 渡すもの | 返すもの |
| --- | --- | --- |
| 執筆 | 共通の手引きと型ごとの手引き（読む節を名指し）、見本のページ（試作で決める。「構成をまねない」と添える）、用語集、catalog の項目、data の該当の項目、材料の調査資料の節、工程2の訂正（research/22〜28） | ページ、雛形、図、報告 |
| 検証（事実・出典・鮮度） | ページ、チェックリスト、data、出典 | 指摘の一覧（主張と出典の照合、数値が数値ファイルを経由しているか、根拠の強さ、版に依存する記述の確認日） |
| 検証（雛形の動作） | 雛形と期待、チェックリスト | 静的な検査と実機の確認の結果 |
| 検証（分かりやすさ） | ページ、前提のページ、チェックリスト | 冒頭で用が足りるか、断片で読んで通じるか、判断があるか、薄い節 |
| 検証（図と描画） | ページ、図、描画の検査の結果 | 描いた結果の崩れ、図の内容 |
| 直し | 指摘の一覧 | 直したページ（書いた担当に戻す。research/20 の D2） |

- 書いた本人に採点させない。メインが書いた直しも、別の担当が確かめる（research/20 の F2）
- 執筆者が書いてよいのは、担当のページ・そのページの雛形（`snippets/<id>/`）・図（`docs/img/<id>/`）だけ。front matter で直してよいのは `sections`・`stage`（draft にする）・`updated`・`sources`（sources にある id）だけで、指示に名指しする。ほかのキーと共有のファイル（用語集・prh・data・catalog・手引き）への変更は、報告に「提案」として書き、メインがバッチの終わりにまとめて反映する
- 検証役は、描画した結果を見る。担当の外への波及（並べ替えた後の「上の節」など）は、メインと道具の検査で見る（research/20 の D2）

### 10.3 バッチの回し方と再開

- ワークフローで、1ページずつ「執筆 → 検証 → 直し」を回す。同時に16〜20体まで（decisions 2026-11-03。規模の目安は 2026-11-04 に large にした）。作者のプランは Ultra で、確認済みのアカウントには5時間の上限がない（週の上限はある。research/22・26）
- 共通の指示を1ファイルにし、担当には差分だけを渡す
- 報告の形を固定する：書いたファイル・直したこと・範囲を越えたこと・メインに判断してほしいこと・検査の結果・**確かめていないこと**・使用量
- 担当は報告をファイルに書いてから終える。止まったときは、報告のないものだけを同じ指示で流し直す
- ワークフローのスクリプトは `.claude/workflows/` に、起動したときの args は `state/` に残す
- ページの一覧は、必ずファイルから機械的に渡す
- 上限の窓の終わりには新しい段を起動しない。ワークフローの「完了」は、報告のファイルと作業ツリーで確かめる

### 10.5 CLAUDE.md と縛り

**CLAUDE.md**：短くし、推測できないことだけを書く（教材が教える原則の実例にする）。例外を許さない規則は hooks と permissions で強制し、CLAUDE.md には理由と相談の基準だけを書く（requirements §6.7 の二層）。中身：何の教材か（1行）、再開するとき（`state/now.md` → `progress.md` → 設計書）、守ること（変わりやすい値を手で書かない、AI の利用を断るサイトを資料にしない、事実を記憶で書かない、書いた本人に採点させない（メインの直しも）、公開の約束・方針・ライセンスに関わる文は作者の承認を得てから出す）、並列の規則（担当のファイルだけ、共有ファイルは提案、生成と commit はメインだけ）。

**hooks と permissions**（`.claude/settings.json`。decisions 2026-11-03）。縛るのは、機械的に判定でき、破ったときの害が大きい規則だけにする。

| # | 規則 | 仕組み | 止めたときに返すこと |
| --- | --- | --- | --- |
| H1 | AI の利用を断るサイト（atcoder.jp・codeforces.com と、sources で断る指定が見つかったドメイン）を開かない | PreToolUse（WebFetch。Bash の curl・wget は見つけられる範囲で） | 「このサイトは AI の利用を断っている。別の一次資料を探すか、報告に書く」 |
| H2 | 生成物を手で書き換えない | permissions の deny（Edit を生成物のパスに） | 「生成物は `gen_site.py` で作り直す」 |
| H3 | 担当（サブエージェント）は commit・push をしない | PreToolUse（Bash。入力の agent_id で担当を見分ける。research/28） | 「commit はメインが行う。報告に書いて終える」 |
| H4 | API キーで課金されないようにする | SessionStart（環境に `ANTHROPIC_API_KEY` があれば知らせる。止めない） | 「API キーがあると従量の課金になる。外してから続ける」 |

ユーザーの注意（「過去に入れた縛りによって柔軟な対応が出来ず不適切な対処をすることも多い」）に沿った決まり：

1. 縛るのは上の表のような、機械的に判定でき、害の大きい規則だけ。判断を含む規則（何が小さな直しか、など）は縛らず、CLAUDE.md と指示に任せる
2. 止めるときは、理由と「代わりにどうするか」を返す。止められた側が、別の道具で回り込むなどの回避策を探さないようにする
3. 当てはめる範囲を狭くする（部分一致で止めすぎない）
4. 止めた記録を残し、バッチの終わりに見直す。不適切な対処を招いた縛りは外すか直し、その例を制作の記録に書く
5. 読者がリポジトリを開いたときにも動くので、軽く安全にする（ネットワークを使わない、壊す操作をしない、標準のものだけで動く）。依存が欠けたときに止めるか通すかを規則ごとに決め、README に書く

hooks がワークフローの担当でも動くかは文書に書かれていないので、土台作りで確かめる（research/28）。入れた hooks と permissions も雛形として扱い、動作を確かめる。

### 10.6 commit と push

- GitHub のリポジトリを作るまでは、ファイルを変えたらその都度 commit し、push はしない
- リポジトリを作った後は、メインが一人で直列に進める間は main に直接 commit・push し、作業ツリーで並列に直すようになったら、グループごとのブランチと pull request にする（decisions 2026-11-03）。並列のときは重なるファイルを表にして順序を決め、decisions.md の表に両方のブランチが行を足して衝突したら、main の行、次に自分の行の順で残す（research/20 の F3）
- commit の本文の終わりに、作業したセッションの記録の行を付ける

### 10.7 使用量と期間

- 実績：工程1は5つの担当で約126万トークン、工程2は14の担当で約680万トークン（progress.md）
- 試作で型ごとにトークン・道具の呼び出し・時間を測り、本制作の見込みを出す。一次資料の確認と雛形の実機の確認が加わるので、kyopro-atlas（1ページ約35〜45万トークン）より重くなる見込みである

### 10.8 ユーザーに確かめる場面

- 工程5（決定の提示）と工程7（試作の出来と使用量の見込み）
- 公開の約束・方針・ライセンスに関わる文（出典と AI 利用の方針のページなど）。第一波の最初のバッチより前に、まとめて見せる
- 鮮度の点検で、教材の推奨・安全の既定・台帳の状態が変わる更新

- 使用量が見込みを大きく超えるとき
- Zensical への移行
- 第一波の最初のバッチの出来

## 12. 決定の一覧（工程5で示す要約の元）

1. **構成**：23分野（§2.1）。型は concept・feature・symptom・comparison・recipe・judgment・ledger・guide・hub。全ページで必ず置くのは front matter と冒頭の要点だけ
2. **レベルと分類**：委任の段階の5段階。軸は分野・レベル・優先度・面・原理・Claude 側の原因・人の側の落とし穴・場面・サイン・前提と関連・追跡・古い助言・変わりやすさ。語彙は schema/site.yml の1か所
3. **キーの台帳**：キーごとに誰が書くか・どこに写るか・書式を決めた。執筆者が書くキーは sections・stage・updated・sources だけ。verified は検証役か道具が書く。機能の属性はページに持たず、数値ファイルに持つ
4. **粒度と境界**：1ページ＝名前・症状・やりたいことで引かれる単位。面ごとの違いはタブ。症状は1症状1ページで振り分けが本体。境界の表（§4.2）
5. **目次の作り方**：先に全候補の id の一覧（registry）を作り、分野の担当が並列に詳細を書き、`check_catalog.py` で検査する。骨格の後は front matter が正
6. **編集方針**：判断を教える、冒頭で用が足りる、1ページで完結、面はタブ、変わりやすい値は道具が書く、根拠の強さ（強・中・弱・類推・推論）、用語は公式の日本語版の多数派、書かないもの（§6.11）、第三者（§6.12）、大会の規則（§6.13）
7. **横断のページ**：引き方・原理・二つの軸・地図・ロードマップ・逆引き・用語索引・知識マップ・出典と AI 利用の方針（作者の承認）・台帳・比較表・一覧・llms.txt
8. **技術**：Material 9.8 系と MkDocs 1.6.1 を固定、Python 3.12、プラグインは search だけ、Zensical の試験ビルド、KaTeX なし。道具は読む・作る・検査の層。生成物はコミットして `--check`、毎回変わる値は入れない。骨格はビルドから外す
9. **数値と出典と台帳**：data/facts.yml・sources.yml・outdated-advice.yml。本文には目印の間に道具が書く
10. **鮮度**：確認日は主張とページの二段、期限は 365・90・30日、期限切れはブラウザで計算して表示、点検の skill、結論が変わる更新だけ作者が承認
11. **雛形**：静的な検査は CI、実機の確認は手元（専用の設定の置き場所と `--setting-sources`、Claude Code 2.1.314 以上、無害な形、API キーがないことを確かめる）。安全の雛形は確認を通ってから載せる
12. **制作の進め方**：執筆 → 検証（4つの観点）→ 直しを、ワークフローで同時に16〜20体まで。報告の固定の形と「確かめていないこと」、報告のないものだけを流し直す再開
13. **記録**：decisions・design の変更履歴・progress・state（追跡外）・batches・制作の記録
14. **縛り**：CLAUDE.md は短く、H1〜H4 の hooks と permissions を5つの決まりで入れる（ワークフローの担当で効くかは土台作りで確かめる）
15. **工程の条件**：描画と書き方の検査を土台作りで作り、試作で0件にしてから本制作へ。全体の検証に「読者の課題から引く」
