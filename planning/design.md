## 1. 前提の整理

### 1.1 読者と目的

- **読者**：Claude や Claude Code をかなり使っているが、知識が足りず使いこなせていない人。どのページも開発の経験（git・ターミナル・プログラミング）を前提にし、非エンジニア向けの説明は省く（decisions 2026-11-03）。公開のリポジトリとサイトで、不特定多数に向けて書く
- **使われ方**：うまくいかなかった場面ややりたいことから引く辞書。冒頭の要点で用が足り、必要なら原理へさかのぼれる（requirements §1）
- **重心**：機能の紹介ではなく判断を教える。なぜうまくいかないか、次に何を足しどう確かめるか、どこまで任せて何を人が握るか
- **核**：症状から引く索引、確かめ方と評価、日本語の出力品質、古くなった助言の台帳（requirements §1）
- **背骨**：四つの原理（見せる・確かめる・縛る・握る）と比例則、失敗の原因の二つの軸（Claude 側の六つの「ない」と、人の側の五つの落とし穴）、委任の段階のレベル（requirements §3、D1・D2・D8）

### 1.2 使われ方と、そこから来る設計の条件

| 使われ方 | 設計の条件 |
| --- | --- |
| 症状から引く（「指示が守られない」） | symptom の signs を読者の言葉で書き、逆引き辞典を生成する。症状のページは、原因を安く確かめられる順の診断と、対処のページへの振り分け（`routes`）を持つ |
| やりたいことから引く（「長い作業を任せたい」） | goal の signs、用途別レシピ、ロードマップ |
| 状況から引く（「チームで導入する」「大会に出る」） | situation の signs と scenes、題材の入口 |
| 名前で引く（機能名・旧名・公式の訳語） | aliases（英語名・旧名・公式の日本語訳）、用語索引、検索 |
| 信用してよいかを見る | 冒頭のバッジ（確認日と版・変わりやすさ・成熟度・強制力）、根拠の強さの表記、期限切れの注意書き、「下書き・未検証」の帯 |
| 次の段階へ進む | level と prerequisites から、ロードマップと知識マップを生成する。比例則に沿い、ロードマップでは任せる幅を広げるページの手前に、確かめる・縛るのページを並べる（§3.1 の4） |
| 自分の AI に教材を読ませる | llms.txt（1ページ1行）。どのページも単独で読めるように書く |
| スマホで読む | 表の列を絞り、描画の検査を幅 390px で行う |

### 1.3 成功の条件

1. 症状の言葉で引いて、目的の節に3回のクリック以内で着く（試作では工程4の読者の課題で、全体の検証では逆引きの項目から20ほどで試す）
2. どのページも、冒頭の要点で「何ができるか・いつ引くか・前提」が分かり、本文に判断（なぜ・どこまで任せるか・どう確かめるか）がある
3. 変わりやすい値（数値・既定値・名称・成熟度・大会の規則）は数値ファイルを経由し、確認日と出典を持つ。版に依存する記述には確認日と版がある。実在の人物・団体について、一次資料で確かめていない主張がない
4. 用語と表記が全ページでそろう（公式の日本語版の訳語を基準にする）
5. 確認日が期限を過ぎた情報は、読者に見える
6. 制作が止まっても、どこまでできて次に何をするかがファイルから分かり、報告のない担当だけを流し直せば再開できる
7. 公開する前に、描画の検査と書き方の検査がエラー0

## 3. レベルと分類

### 3.1 レベル（`level`）

| level | この段階の読者 | 上がる条件（ロードマップの節目） |
| --- | --- | --- |
| 使う | 対話で頼み、返答を読んで使う | 期待外れの原因を「見えていない／散らかっている」と言い分けられる |
| 整える | 頼み方・資料・会話の長さを整え、結果を確かめて直す | 完了の条件と確かめ方を、依頼に含めて渡せる |
| 任せる | 計画させてから任せ、長い作業を途中で舵取りする | 二回同じ注意をしたら、仕組みに移すと判断できる |
| 仕組みにする | CLAUDE.md・skills・hooks・permissions・MCP・plugins で常設化し、共有する | 無人で動かす前の五つの問いに答えられ、検証器を自分で確かめられる |
| 回す | 並列・無人・定期・プログラムから動かす | ― |

規則：

1. そのページが**最初に要る段階**を level にする（機能の難しさや使用期間ではない。D8）
2. 型が `guide`・`hub`・`ledger` のページは level を持たない（`start` の分野のページはこれらの型にする）。`symptom` は、その症状に出会う段階にする。症状のページの前提は、診断を読むのに要る概念のページ（ふつう basics と start）だけにする。振り分け先は前提に置かず `routes` に持つ（§3.3・§4.1 の2）
3. 前提に、そのページより上の段のページを置かない（検査で警告する）。`routes` には段階と優先度の規則を当てない（上の段の対処も、推奨の対処も置ける）
4. **比例則**（推奨の読み。工程5で確かめる）：前提は「知らないと読めない」依存に限る。任せる幅を広げる内容（自律・並列・無人・権限の緩和）のページは、対応する守りのページ（`verify`・`eval`・`enforce`・`safety` の分野）を関連に持ち（知らないと読めないなら前提に）、ロードマップの生成で、同じ段の中でそのページより手前に並べる（§7）。要件 §3.3 の目的（生成されるロードマップが任せる幅を広げる順になる）は、この生成の規則で満たす。守りのページを前提にも関連にも持たないと、検査が警告する（症状のページは routes の先も数える）。ほかの案は、要件 §3.3 のとおり守りのページを前提に持たせる形（前提の鎖が深くなる。比べた理由は §13 の Q）
5. 節の level（`sections` の level）は任意とし、使うときはページの level 以上にする（kyopro-atlas では手間に見合ったかが分からなかったので、必須にしない）
6. 「使う」のページは少なく短くし、「整える」〜「仕組みにする」を厚くする（requirements §3.3）

### 3.2 分類の軸

| 軸 | キー | 値 | 使い道 |
| --- | --- | --- | --- |
| 分野 | `field` | §2.1 の23 | ナビゲーション |
| レベル | `level` | §3.1 の5段階 | バッジ・ロードマップ・知識マップの色 |
| 優先度 | `priority` | 必須・推奨・任意 | 初版の範囲。必須のページの前提は必須にする（検査） |

| 変わりやすさ | `volatility` | 低・中・高 | 点検の期限（365・90・30日） |

語彙は `schema/site.yml` の1か所に持ち、道具はそこを読む（道具のコードに語彙を直書きしない。kyopro-atlas の反省）。

**キーの台帳**（誰が書くか・どこに写るか・書式を、キーごとに決める。型を検査できないキーは作らない。kyopro-atlas の反省）

| キー | 必須 | 書く人 | 写る先 | 書式・検査 |
| --- | --- | --- | --- | --- |
| `id` | 全 | 目次（メイン） | URL・すべての生成物 | 英小文字・数字・ハイフン。一意、ファイル名と一致 |
| `title` | 全 | 目次 | 見出し・一覧・索引・llms.txt | 平文 |
| `nav_title` | 任意 | 目次 | ナビゲーションだけ（ページの見出しには使わない） | 平文 |
| `aliases` | 任意 | 目次（執筆者は提案） | 用語索引・検索・冒頭の別名の行 | 平文。本文の冒頭にあるか |
| `type`・`field`・`chapter`・`order` | 全（chapter は任意） | 目次 | ナビゲーション・一覧 | 語彙 |
| `level` | 型による | 目次 | バッジ・ロードマップ | 語彙。前提の逆転 |
| `priority` | 全 | 目次 | 初版の範囲（表示しない） | 語彙。必須の前提は必須 |
| `surfaces`・`principle`・`prevents`・`pitfalls`・`scenes` | 型による | 目次（執筆者は提案） | バッジ・一覧・逆引き | 語彙 |
| `summary` | 全 | 目次（執筆者は提案） | 一覧・索引・llms.txt・知識マップ | 平文、1〜2文・120字以内。変わりやすい値を書かない |
| `signs` | 型による | 目次（執筆者は提案） | 逆引き辞典 | 平文。読者の言葉 |
| `wave` | 第一波の核のページだけ | 目次（骨格で写す） | 第一波の一覧（道具が routes と前提でたどって出す）・公開の区切り | 1。核の分野の総論と多く前提にされるページ、入口と症状辞典の全ページ（§5.3） |
| `prerequisites`・`related` | 全（related は任意） | 目次（執筆者は提案） | 知識マップ・ページ下部 | id。解決・循環・逆転・比例則。symptom の前提は §3.1 の2、related は routes にない近いページだけ |
| `routes` | symptom は必須（ほかの型は持たない） | 目次（執筆者は提案） | 診断の節の振り分け（目印。§8.4）・知識マップ・症状の原因別の表・第一波の数え方（§2.3） | `[{cause, to: [id[#anchor], …]}]`。cause は prevents か pitfalls の値、to は原因ごとに中心の対処を1〜3件、近い順。解決を検査する。段階と優先度の規則は当てない |
| `tracks` | feature は必須 | 目次（執筆者は提案） | 機能のバッジ・点検 | 数値ファイルの features にある id |
| `outdated_advice` | 任意 | 目次・執筆者 | 台帳の逆リンク | 台帳にある id |
| `sources` | 全（guide・hub は任意） | 執筆者（新しい出典は `data/sources.d/<id>.yml` に足す。§6.8） | 参考の節（生成） | sources にある id、AI の利用の指定を確かめ済み |
| `volatility` | 全 | 目次 | 点検の期限 | 低・中・高 |
| `sections` | 任意 | 執筆者（anchor は一度決めたら変えない） | 目次・節へのリンク | `{title, anchor, level?}`。本文の見出しにあるか |
| `stage` | 全 | 執筆者（draft）・検証役（reviewed）・メイン（done）。移り方は §10.2 | ページの最後の行・下書きの帯・一覧 | stub・draft・reviewed・done |
| `updated` | 全 | 中身を変えた担当 | ページの最後の行 | 日付。読者に見える中身を変えたときだけ |
| `verified`・`verified_with` | reviewed 以降 | 検証役か点検の道具（**執筆者は書かない**） | バッジ・期限の日（§9.2） | 出典を読み直して確かめた日、`{claude_code, channel, models, app}`（channel は latest か stable）。数値の確認日は目印の中に持つ |
| `checked` | 任意 | 点検の担当か道具 | 期限の日（§9.2） | 日付。点検で影響がないと確かめた日（出典は読み直していない） |

- 機能の属性（成熟度・強制力・読み込みの時期・コンテキストのコスト・圧縮で残るか）は、ページの front matter に持たず、数値ファイルの機能の項目（§9.1）に出典と確認日付きで持つ。ページは `tracks` でその機能を指し、バッジと比較表は道具が作る（同じ値を何ページにも持つと食い違う。変わりやすい値は道具が書く）
- 1つのキーを2つの表示の役に使わない（kyopro-atlas の `nav_title` の不具合）
- 形式は `schema/page.schema.json`（JSON Schema）で検査する。page.schema.json は site.yml とキーの台帳から作る（語彙を二か所に持たない）

## 4. ページの粒度と分野間の境界

### 4.1 粒度の規則

1. **1ページ＝名前・症状・やりたいことのどれかで引かれ、独自の「なぜ」か判断を持つ1つの単位**。変種は節に、面ごとの違いはタブにする（面ごとにページを分けない。D9）
2. **症状のページは1症状1ページ**で、題名は読者の言葉にする。原因の切り分けと振り分けが本体で、対処の本体は各分野のページに任せる。振り分け先は `routes` に、原因ごとに中心の対処を1〜3件、近い順に書く。前提は診断を読むのに要る概念のページだけ、related は routes にない近いページだけにする。例外として、消された直後・漏れた直後の初動は症状のページが持ち、対処のページの同じ節は外して症状のページを指す
3. **機能のページは1機能**（密接な系統は1ページにまとめ、節にアンカーを付ける）。公式リファレンスの網羅はしない（requirements §6.3）
4. **比較のページは、混同されやすい組だけ**にする。属性の表は数値ファイルから作り、手書きするのは判断例
5. 研究や事例の紹介だけのページは作らない。根拠として各ページに置く
6. **コンテストの分野は固有の論点だけ**にする（D5）。一般化できるものは各分野のページに置き、`scenes` にコンテストを付ける
7. research preview・experimental の機能は、概念だけの短いページか節にする（requirements §6.3）。周辺製品は一覧のページだけにする（D15）。ただし本体に入って読者がふつうに触れる機能（会話の中の Design・Docs、検証に使う Claude in Chrome など）は、使い方まで書く（decisions 2026-11-03 の方針 B6）

### 4.2 分野間の境界の決定

## 5. 目次（catalog）の作り方

### 5.1 形式

- `planning/catalog/registry.yaml`：全候補の id・分野・題名・優先度・材料の一覧。目次の担当どうしが、互いのページを id で指せるように、最初に作る
- `planning/catalog/<field>.yaml`：分野ごとの全ページの詳細。項目は、§3.3 で目次が書くキーに、目次だけの項目（`materials`：執筆の材料になる調査資料の節、`templates`：載せる予定の雛形、`visual`：図の案、`wave`：第一波の核か（骨格で front matter にも写す。§3.3）、`level_evidence`：段階の根拠、`notes`）を足したもの
- 詳しい形式と規則は [catalog/README.md](catalog/README.md)

### 5.2 作り方

1. 担当1つが、調査資料（00 §3、11 第1〜2節、requirements §4.3〜4.4）から `registry.yaml` を作る
2. 分野のまとまりごとの担当が、並列に `<field>.yaml` を書く。ほかの分野のページは registry の id で指す。新しいページは自分の分野にだけ足してよく、ほかの分野への提案は `open_issues` に書く
3. メインが `tools/check_catalog.py` で検査する：形式・語彙・id の一意・前提の解決・循環・レベルの逆転・必須の前提は必須・比例則・routes の解決・入ってくる道のないページ・第一波の数（内訳：核・前提・routes・正本）
4. 工程4で、別の担当が設計書と目次を批判的に読む。指摘への対応を design-review.md に決め、目次を分野ごとの担当が直す
5. 骨格（工程6c。§10.1）で catalog から front matter を作り、それ以後は front matter が正になる。catalog は凍結し、執筆の指示（materials・templates・visual・notes の見せ方）としてだけ使う

### 5.3 規則の要点

- **id**：英小文字・数字・ハイフン。題名の英訳か、公式の英語の機能名にする。骨格の後は変えない
- **題名**：読者が引く言葉にする（症状は読者の言葉、機能は公式の名前）。公式の日本語版の訳語に合わせる（§6.2）
- **aliases**：公式の英語名・旧名・公式の日本語訳・よくある言い換え。自分の題名とも、ほかのページの題名とも同じ語は入れない
- **summary**：1文目は何ができるか（何が分かるか）、または答えそのもの。2文・120字以内。「このページ」「ここでは」「扱う」「紹介する」「まとめる」を使わない（schema/site.yml の summary_banned_words）。**変わりやすい値（数値・既定値・料金・モデルの世代）を書かない**
- **signs**：読者の言葉。symptom は困りごと、goal はやりたいこと、situation は置かれた状況。機能名を答えとして書かない。わざと1つの問いにまとめる goal はほかのページと同じ文にそろえ（逆引きで1行に束ねる）、まとめないものは場面を書き分ける
- **prerequisites**：直接の前提だけ（4つまで）。前提と related に同じページを置かない。入ってくる道のないページを作らない。症状のページは §3.1 の2
- **routes**：symptom だけが持つ。原因ごとに中心の対処を1〜3件、近い順に書く（§4.1 の2）
- **priority**：00 の表を基本にする。新しいページの優先度は目次の担当が決め、理由を `notes` に書く（requirements §4.2）
- **wave**：第一波の核のページに付ける。入口（start）と症状辞典は全ページ、ほかの核の分野は、総論と、その分野のほかのページの多くが前提にするページ（推奨の案。工程5で確かめる。§2.3）
- **工程2の訂正を守る**：訂正・注記の付いた主張（research/22〜28）を、要約やサインの根拠にしない

## 6. 編集方針

### 6.1 共通の原則

1. **判断を教える**：機能の説明で終わらせず、なぜうまくいかないか・どこまで任せるか・どう確かめるかを書く
2. **冒頭で用が足りる**：冒頭の要点（§6.4）で、辞書として引いた人の用が足りるようにする
3. **1ページで完結させる**：前提の説明は繰り返さずリンクするが、節を1つだけ読んでも何の話か分かるように書く（AI が断片で読む場合も同じ）
4. **面はタブで並べる**：同じ原理の面ごとの手段は、ページの中のタブ（アプリ／Claude Code／API）で並べる
5. **変わりやすい値を手で書かない**：数値・既定値・名称・成熟度・大会の規則は数値ファイルを経由する（§6.7）
6. **根拠の強さを示す**（§6.6）
7. **固定のテンプレートにしない**：§6.3 は目安で、薄い節を目安のために作らない
8. **公開の約束・方針・ライセンスに関わる文は、作者の承認を得てから出す**（下書きでも。decisions 2026-11-03）。守れない約束を書かない。承認に回すのは、出典と AI 利用の方針のページ（「完成」の意味を含む。§10.2）、全ページの冒頭とフッターの非公式の文（§8.5）、この辞典の引き方の「誤りや古い情報の報告」と「確認日と期限切れ」の節
9. **写さない**：公式の文書を訳して載せない。ほかの記事の文を転載しない。参考にした資料は出典に残す（requirements §11）

### 6.2 文体と用語

- だ・である調（D16）。1文を短く、1段落1つの主張
- 開発の経験を前提にする（git・ターミナル・プログラミングの基本は説明しない）
- 機能名・コマンド・ファイル名・設定のキーは原文のまま書く
- **用語の訳語は、公式の日本語版（Claude Code の文書は全228ページに日本語版がある。research/27）の本文の多数派に合わせる**。公式で表記が割れている語（plan モード／プランモード、effort／努力レベル など）は、用語集で1つに決めて prh に入れる
  - 目次の題名は、research/27 §3.1 の案で揃えた（2026-11-04 の統合。表は `planning/batches/step3/brief-integrate.md` の M1）。割れている3語は仮に、plan モード・effort・許可ルール／確認ルール／拒否ルール（Claude Code の日本語版の多数派）とし、工程5で確かめる
  - API の機能名は、Platform の日本語版の訳語を調べるまで英語のまま書く（プロンプトキャッシングだけは Claude Code の日本語版の多数派）
- 独自の用語を見出しにし、公式の用語を併記する（D14。例：「お願いと鍵」＝非決定論的な指示と決定論的な制御）
- 半角英数字と全角文字の間に空白を入れる（kyopro-atlas と同じ。textlint で検査）
- 用語集のページを正とし、prh.yml はそこから作る

### 6.3 型ごとの構成の目安

| type | 目安の流れ |
| --- | --- |
| concept | 要点 → 何が起きるか（例）→ なぜそうなるか（比喩付きの図）→ 何に効くか（原理・原因へ）→ 誤解 → 関連 |
| concept（技法） | 要点 → 頼み方の例（Before/After）→ 何が変わるか → なぜ効くか → 効かない場面・やりすぎ → 関連 |
| feature | 要点（強制力・確認日と版のバッジ）→ 使いどころ（どの原因を防ぐか）→ 最小の使い方（面のタブ）→ 雛形（折りたたみ）→ 効かない場面・落とし穴 → 比べる相手 → 古くなった助言 |
| symptom | 要点 → よくある形（読者の言葉）→ 診断のチェックリスト（六つの原因を安く確かめる順。関われば人の側の落とし穴）→ 原因ごとの対処へのリンク（routes から生成）→ 判断例 → 予防（仕組みに移す） |
| comparison | 要点 → 比較の表（生成）→ 選び方（判断例）→ 組み合わせ方 |
| recipe | 要点 → 先に整える守り（確かめる・縛る）→ 手順 → 確かめ方 → 失敗したとき |
| judgment | 要点 → 何が起きるか（研究の根拠の強さを添えて）→ なぜ（人の側の仕組み）→ 判断例 → 握るもの → 確かめ方 |
| ledger | 要点 → 生成の表 → 読み方（台帳は「どの原理の回避策だったか」） |
| guide・hub | 自由（表とリンクが本体） |

### 6.4 冒頭の要点とバッジ

- 要点の囲み：「何ができるか（concept は何が分かるか）」「いつ引くか」「前提」。feature は「強制力（お願いか鍵か）」も出す（requirements §5.3）
- 要点の上のバッジの列：レベル・原理・成熟度・変わりやすさ・確認日と版（読者が、本文を読む前にどれだけ信用してよい情報かを判断できるように）。成熟度と強制力は数値ファイルから
- 要点の後に、aliases を並べた別名の行と、題名を主語にした1〜3文の導入を置く

### 6.5 面のタブ

- 面ごとに手段が違う話は、`pymdownx.tabbed` の「アプリ／Claude Code／API」のタブで並べる
- 面に固有の操作は、面の分野（`app`・`cli`・`api`）に置く
- 本文はプランに中立に書き、プランごとの差は数値ファイルの表に置く。Claude Code は WSL・Linux の CLI を基準にし、ほかの OS と IDE の拡張の動作は「未確認」と書く（方針 B5）

### 6.6 根拠の強さと書き分け

- 研究や数値を根拠にする主張には、根拠の強さ（強・中・弱）を付ける（requirements §6.2）。隣接分野からの類推は「類推」、研究も実践例もない推論・独自の提案は「推論（実践例なし）」と書き、必須ページの中心にしない（方針 A3）
- 研究の結果は、どのモデル・どの世代の結果かを書く。小さな研究は「傾向」とし、標本の大きさを添える
- 実践者の間で割れる論点は、「公式の立場」「実践者の幅」「この教材の推奨」の三段で書く
- 安全の既定は、公式の既定（auto mode）を基準にして限界を書き、比例則に沿って段階ごとに示す。中身は、任せる段階からは sandbox と秘密の読み取りの禁止、無人の実行は使い捨ての環境、預かったデータは契約のある面だけ（decisions 2026-11-03「安全の既定の勧め方」）。正本は safety の安全の早見表の節（`default-safety-settings#by-stage`）で、検証役はこの節を決定と照らす

### 6.7 変わりやすい値

- 本文に手で書かない。`data/facts.yml` の項目を、目印（§8.4）の間に道具が書き込む。数値だけでなく、数値を含む決まった文と確認日も道具が書く
- モデルの既定 effort のように面で違う値は「モデル × 面」の表で持つ（research/23）。公式同士が本当に食い違うときは両方の出典を残し「食い違いあり」と書く
- 目印の外に、数値ファイルの値と同じ値を手で書いていたら、検査が警告する。照らすのは、照合の型（単位や前後の語）を持つ項目だけにする（短い数や一般的な語で誤った警告を出さないため）

### 6.8 出典と AI の利用の指定

- 出典は `data/sources.yml` と、ページごとのファイル `data/sources.d/<id>.yml`（執筆者が足してよい）に持ち、道具が1つにまとめて URL の重なりを検査する。ページは `sources` で id を指す。ページ末尾の「参考」の節は道具が作る
- 新しいドメインは、資料にする前に `tools/check_noai.py` で AI の利用を断る指定を確かめ、結果を sources に記録する。atcoder.jp と codeforces.com は開かない
- 転送されている URL は、転送先の URL を持つ（research/28）

### 6.9 雛形

- 本文に載せる設定や雛形（settings.json・hook・skill・subagent の定義・CLAUDE.md の例・プロンプトの型）は、`snippets/<id>/` に置く。本文には、目印（`<!-- gen:begin snippet <id>/<名前> -->`）の間に道具が写し（折りたたみも可）、`gen_site.py --check` で snippets/ との一致を確かめる。取り込みの記法は使わない（リポジトリの Markdown を読む人と AI に中身が見えない。§13 の D と同じ理由）
- 確認の形と載せる時期は §8.7 で種類ごとに決める。安全とデータの雛形（`safety: true`）だけは、本文を下書きで出すときも、確認を通るまで載せない（方針 B2）。確かめた版と系列と日付、要る最低の版は、道具が本文に書く

### 6.10 見せ方

requirements §6.6 の見せ方を使う：Before/After（何が足されたかを注記）、比較表（生成）、比喩付きの図、注釈付きのセッション記録、判断例、検証ノート、診断のチェックリスト、雛形。

- 演習は作らない。演習の形の論点は、判断例・検証ノート・振り返りのチェックリストにする（D7）
- どのページで何を使うかは、試作の始めにメインが一覧（`planning/shows.md`）に書く。制作の記録から作れる題材と、繰り返して確かめる検証ノートの数件を名指しする。目次の notes に担当が書いた「見せ方」は、その材料にする（目次は骨格で凍結するので、一覧は目次の外に置く）
- 注釈付きのセッション記録は、制作の環境と制作の記録だけから作り、再構成したものはそう書く。作者の手元の記録は使わない（方針 A6）
- 検証ノートは、制作の環境で試した結果を日付と版付きで載せる。制作の環境で試せないものは作者に頼んだ結果にし（必要最低限。§8.7）、どちらで試したかを書く。試行は基本は数回で「観察」と書き、大事な数件（英語への回帰など）だけ、回数の上限を決めて繰り返して「傾向」と書く（decisions 2026-11-03）
- 動く図「コンテキストの埋まり方」は、公式の対話の図へのリンクを主にし、自作は公式にない点（毎回全部を読み直すこと・圧縮）だけの図にする。動く図にするのは、公式で足りないと試作で分かったときだけ（統合のときの M8 を改めた）

### 6.11 書かないもの

requirements §6.3 に、decisions 2026-11-03 の書き方の方針を足したもの：

- 根拠の弱い数値を主張の根拠にすること（使うなら「経験則」「自己申告」と明記）
- 安全装置を外す近道を勧めること。攻撃の手口は型と仕組みまで書き、無害な再現だけを載せる。回避の手順と、AI を禁じる課題の隠し指示を外す方法は書かない（方針 B1）。文書にない回避方法を見つけたら、その記述と雛形の公開を止め、記録は追跡しない state/ に置き、Anthropic への報告を作者に頼む。報告が済むまで公開しない（工程5で確かめる）
- 利用ポリシーを回避する頼み方（言い換え・分割・偽の文脈）。断られたときは、公式が案内する手段だけを書く（decisions 2026-11-03「断られたときの頼み直し」）
- AI が書いたと分からなくする方法（「AI 臭さ」は読みやすさの品質として扱う。方針 B4）
- 特定の個人の構成を標準として示すこと、呪文を効く手法として教えること、日付と版のない機能・既定値・価格の説明、モデルの「性格」を固定的な事実として教えること、ほか requirements §6.3 の各項
- 法令の解釈と、社内規則の回避

### 6.12 実在の人物・団体・第三者

- 実在の人物・企業の事例は、出典付きで名前を出してよい。自己申告の数値は「自己申告」と書く（D12）
- 失敗例・古い助言・評価などの否定的な文脈では、実在の個人や著作を名指ししない。助言の文言・時期・撤回の一次資料で書く。本人の振り返りは本人の言葉として紹介し、評価の語を使わない（方針 A1）
- 第三者のツールは例として名前を出すだけにし、推薦しない（D13）。名前を出すときは成熟度と確認日を付ける（requirements §6.4）
- 既存の書籍・講座は出典に挙げるだけにする。公式の教材（Academy・docs）は案内する（方針 A2）
- Anthropic の AI Fluency（4D）は参考文献に挙げるだけにし、構成や共通の言葉には使わない（requirements §3.1）
- 実在の人物・団体についての主張は、一次資料で確かめたことだけを書く

### 6.13 大会の規則

- 版・確認日・類型（禁止・部門分け・許可と開示）・一次資料へのリンクだけを数値ファイルに持つ。条文の要約は載せない（方針 A4）
- 主催者の公式 X など、AI の利用を断るドメインの外の一次資料で確かめた版だけを入れる。確かめられない版は「未確認」とし、規則のページへのリンクだけを置く。作者には確かめを頼まない（decisions 2026-11-03「大会の規則の版」）
- requirements §4.3 の七つの形式を、早見表と確認表で同じ厚さに扱う。例は AtCoder（ABC・AHC）から多く取る。作者の参加の記録は使わない（decisions 2026-11-03「コンテストの分野」）
- 競技の練習法と AtCoder の規則の細部は kyopro-atlas へリンクする（方針 A5。§4.2）

## 8. 技術構成

### 8.1 版と依存

- Material for MkDocs 9.8 系と MkDocs 1.6.1 を `uv.lock` で固定する（2026-11-03 の確認：最新は 9.8.0、Python 3.11 以上が必要）。Python は 3.12 を uv で固定する。MkDocs 2.0 は Material と組み合わせない
- 道具は `uv run`（Python 3.12）で動かし、PyYAML などは pyproject の依存にする。hooks は読者の環境でも動くので、標準のライブラリだけの `python3` で動く形にする
- Node.js は textlint だけに使う
- MkDocs の hooks・macros・自作プラグインを使わない。プラグインは search だけ。生成はすべて独立スクリプト（requirements §2）
- Zensical の試験ビルドを CI で並走させる（失敗してもデプロイは止めない）。試験ビルドの Zensical の版は固定し、意図して上げる。評価は土台作りの終わりと初版の公開の前に行い、Material の保守が終わる 2027-05-05 までに移る（decisions 2026-11-03）
- Zensical の評価の基準：stub が出ない、描画の検査が0件、日本語の検索で決めた語が引ける（文書に扱いがない。research/28）、overrides が動く、リンクの検査が通る。stub を docs/ の外に置き、draft にするときに docs/ へ移す形（MkDocs の設定に頼らない）も、土台作りで比べる
- 2027-05-05 までに移れないときは、Material 9.8 を使い続けて依存の脆弱性を見張る案を作者に知らせる（§10.8）
- 数式（KaTeX）は入れない

### 8.3 道具（tools/）の層

kyopro-atlas の道具は、分野や段階の名前がコードに直書きされ、大きくなりすぎた（research/20 の C1）。claude-atlas では層に分けて作り直す。

| 層 | 中身 |
| --- | --- |
| 読む層（`tools/lib/`） | front matter・catalog・data・schema/site.yml を読み、ページのモデルを作る |
| 作る層（`tools/gen/`） | 生成物の種類ごとに1つ（nav・入口・一覧・逆引き・索引・知識マップ・ロードマップ・台帳・比較表・参考・数値・雛形の写し・本文のリンクの目印・診断の節の振り分け・llms.txt・症状の原因別の表〔失敗の二つの軸のページの節。症状のページの routes から〕） |
| 検査の層（`tools/checks/`） | 検査1つを関数1つにして登録する。試験も検査ごとに書く。前提と関連の規則は、catalog と front matter の両方のモデルに当てる |
| 入口の CLI | `make_skeleton.py`・`gen_site.py`（`--check`・自分のページだけを書く `--page <id>`）・`check_pages.py`・`check_catalog.py`・`check_templates.py`（`--live`）・`render_pages.py`・`check_svg.py`・`check_noai.py`・`textlint_targets.py`・`check_all.py`（CI と同じ検査の組。§8.6） |

- kyopro-atlas から写して直すもの：`render_pages.py`（描画の検査）・`check_svg.py`・`check_noai.py`（写して直し済み）・`textlint_targets.py`、テンプレートの上書きと CSS・JS（バッジ・前提と次に読む・知識マップ・絞り込みの欄）。進捗の部品（解いた・理解した）は外す（D17）
- `tools/check_catalog.py` は工程3で作った（目次の検査）。骨格の後は退き、同じ規則は検査の層の関数として front matter に当てる（同じ規則を二か所に作らない）

### 8.4 生成物と目印

- 生成物はコミットし、CI で `gen_site.py --check`（作り直して差分がないこと）を確かめる
- 手書きのページの生成部分は `<!-- gen:begin 名前 -->` 〜 `<!-- gen:end 名前 -->` の間に道具が書く
- 変わりやすい値は `<!-- fact:begin <id> -->` 〜 `<!-- fact:end -->` の間に、道具が値・決まった文・確認日を書く。段落の中でも使える
- ページ末尾の参考の節は `<!-- gen:begin references -->` の間に、sources から道具が作る
- 雛形の写しは `<!-- gen:begin snippet <id>/<名前> -->` の間に道具が書く（§6.9）
- 症状のページの診断の節の振り分け先は、routes から生成の目印の間に道具が書く
- **未公開のページ**：stub のページと、公開から外した試作のページ（波が来るまで。§10.1 の7）を指す。この節と §8.5・check_pages.py は、この定義を使う
- **未公開のページの扱い**：生成物（ナビゲーション・分野の入口・一覧・逆引き・用語索引・知識マップ・ロードマップ・比較表・症状の原因別の表・llms.txt）には、stage が draft 以上のページだけを載せる（波の来ていない試作のページは stub と同じに扱う。§8.5）。ページ下部の前提・次に読む・関連が未公開のページを指すときは、リンクにせず「題名（準備中）」の平文にする
- **本文のリンクの目印**：本文から、まだ公開していないかもしれないページを指すときは、`<!-- link:begin <id>[#<anchor>] -->` 〜 `<!-- link:end -->` を使う。道具が相手を見て、公開しているページならリンクを、未公開のページなら「題名（準備中）」を書く。相手を公開したら道具が書き直すので、前のページへ手で戻らない。手書きの Markdown のリンクで未公開のページを指すものは、`check_pages.py` が止める
- **毎回変わる値（内容のハッシュ・生成の日時）を生成物に入れない**。並列のブランチのマージで毎回衝突するため（research/20 の C2）。マージの後は `gen_site.py` を流し直す（衝突した生成物は main 側を取ってから作り直す）
- 本体を生成するページ（逆引き・用語索引・ロードマップ・知識マップ・台帳・年表）は、front matter に印のキーを持たない。どのページに何を生成するかは、作る層の設定に持つ

### 8.5 表示

- **非公式の表示**：全ページの冒頭とフッターに、Anthropic の公式の教材でないことを書く。フッターに「© 2026 yuukougun」とライセンス。Anthropic のロゴと意匠をまねない（D20、decisions 2026-11-03「作者の表記と URL」）。冒頭とフッターと README には、土台作り（6a）のときから、決定にある最小の文（Anthropic の公式の教材でないこと・© 2026 yuukougun・ライセンスの名前）だけを入れる。言い回しは工程5で示す。それより多い方針の文は、作者の承認の後に足す（§6.1 の8）
- **バッジ**：テンプレートの上書きで、レベル・原理・成熟度・変わりやすさ・確認日と版、feature の強制力を出す。draft は verified がないので、確認日のバッジは「未検証」
- **下書きの帯**：stage が draft のページに「下書き・未検証」の帯を出す
- **期限切れの注意書き**：道具が、ページごとに期限の日（§9.2）を計算して data 属性に出す。ブラウザの JS は今日と比べるだけにし、過ぎたら注意書きを出す。ビルドした日に左右されず、生成物も毎回変わらない（requirements §7 の「ビルド時に出す」を改めた。format-and-operations F6）
- **骨格のページは公開しない**：`gen_site.py` が nav.yml に stub のページを `exclude_docs` として書き、ビルドから外す（INHERIT で `exclude_docs` が効くかは土台作りで確かめる）。試作のページも、そのページの波が来るまで同じように公開から外す。未公開のページへの道と、手書きのリンクの検査は §8.4。MkDocs の `--strict` は stub へのリンクを止めないので頼らない（MkDocs 1.6.1 は、ビルドから外したページへのリンクを INFO でしか記録せず、公開のサイトで 404 になる。工程4の R4-1 がソースで確かめた）
- **ページ下部**：前提・次に読む・関連（未公開のページ（§8.4）は「題名（準備中）」の平文）、段階と更新日、「このページの誤りを報告する」（Issue）
- **知識マップ**：kyopro-atlas の方式（分野ごとの表示と、ページから開くと祖先と子孫だけの表示）を写して直す。辺は前提と routes
- **検索**：kyopro-atlas の日本語の区切りの設定（separator）を引き継ぐ。主な機能のページに `search.boost` を付けるかは試作で決め、使うならキーの台帳（§3.3）に足す
- **外から読まない**：`theme.font: false`（端末のフォント）にし、Mermaid は写しを置いて読む（外のサイトから読まない。読者の情報を集めない決定の趣旨）
- ライトとダーク、スマホの幅に対応する

### 8.7 雛形の動作確認

- **置き場所**：`snippets/<id>/<名前>.<拡張子>` と、期待を書いた `<名前>.expect.yaml`（雛形を置く場所〔user・project・local〕と条件も書く）。確かめた結果は `snippets/<id>/verified.yaml`（版と系列〔latest・stable〕・モデル・OS・日付・対照の結果）
- **期待の形**：「出力の完全一致」ではなく、「この操作が止められる」「この行が出る・出ない」の形にする（research/20 の C5）
- **対照**：期待ごとに「雛形あり」と「雛形なし（同じフォルダ・同じモード・同じ依頼）」を流し、結果が期待どおりに違うことを合格の条件にする。`-p` は承認の要る呼び出しを既定で拒むので、「止められた」だけでは雛形の効き目と言えない（research/28 #32）。雛形が読まれたことを `claude doctor` の出力でも確かめる
- **種類ごとの確認**：settings・hook・skill・subagent・claude-md は、静的な検査と実機（対照つき）。prompt は、実機で数回流した観察を検証ノートの形で添える（合否にしない）。other（点検表・記録表）は静的な検査だけ。安全とデータの雛形（`safety: true`）だけは確認を通るまで載せない（方針 B2）。ほかは確認の前でも下書きで出してよい
- **静的な検査（CI）**：JSON・YAML の形と、skill と subagent の front matter の必須の項目。SchemaStore のスキーマ（公式の文書が案内するもの。v2.1.220 ごろのもので新しいキーに遅れる。research/28 #46）の写しを `schema/` に置き、写した日と相当の版を書く。雛形が使うキーの許す一覧を自前で持ち、CI で誤りにする。skill と subagent は、手元で `claude plugin validate --strict` も流す
- **実機の確認（手元）**：`tools/check_templates.py --live` が、使い捨てのフォルダと専用の `CLAUDE_CONFIG_DIR` で `claude -p` を動かす。Claude Code は 2.1.314 以上（`--setting-sources` の漏れと、起動の失敗でも 0 で終わる不具合が直った版。research/22）。モデルと版を固定して記録する
- **作者の環境から切り離す**：子の環境は許す一覧から作る（偽のホームの HOME・PATH・LANG・CLAUDE_CONFIG_DIR と、認証の token だけ）。偽の秘密は偽のホームに置く。`--strict-mcp-config` と、claude.ai のコネクタと自動メモリを読まない設定を付ける（research/28 #26・#35）。API キーやクラウドの事業者の認証の変数が親にあれば、止めて知らせる（research/28 #33）。使い捨てのフォルダは、上のどこにも CLAUDE.md のない場所（/tmp の下）に作る。ログインは setup-token の token を勧める
- **読者の条件に合わせる**：expect.yaml の置き場所と条件に、道具が合わせる。使い捨てのフォルダは専用の設定で信頼させる（`-p` は信頼していないフォルダの `permissions.allow` を使わない）。defaultMode を決める雛形では、モードを渡さない（research/28 #30）
- **安全のための決まり**：偽の秘密と、壊れても困らない操作だけで試す。本物のホームや認証情報に触れる形は動かさない（decisions 2026-11-03）
- **sandbox の雛形**：bubblewrap と socat で確かめる（2026-11-04 に入れた）。雛形に `failIfUnavailable: true` を入れ、WSL2 で Windows の実行ファイルを起動する経路を期待に足す。seccomp のフィルタを制作の環境に入れて確かめ、版を記録する（research/28 #36・#37）
- **この環境で試せない雛形**（使い捨てのコンテナ・/etc に書く管理設定・API キーが要る `--bare`・GitHub Actions）：既定では雛形を載せず、条件と概念だけを書く（方針 B2 の「写して使う部分だけを止める」）。作者に頼むかは、工程7の終わりの頼み（§10.8）に入れて聞く
- **アプリの機能など**：作者に頼んで検証ノートにする。頼むのは必要最低限にし、工程7の終わりの頼みにまとめる（decisions 2026-11-03）
- **版**：確かめた版の系列（latest・stable）を verified.yaml と verified_with に書く。雛形が要る最低の版は、facts の「入った版」から道具が書く

## 9. 鮮度と品質を保つ仕組み

### 9.1 データの形

| ファイル | 1項目の中身 |
| --- | --- |
| `data/facts.yml` | id・値（面やモデルで違うなら表）・決まった文の型・照合の型（§6.7）・出典（sources の id）・確認日・変わりやすさ（volatility。既定は高）・関わる版・状態（確認済み・未確認）・食い違い（公式同士が食い違うなら両方の出典）。機能（features）の項目は、成熟度・強制力・読み込みの時期・コンテキストのコスト・圧縮で残るか・入った版・主のページ（用語索引。§7）・CHANGELOG とリリースノートで照らす英語の語（§9.4） |
| `data/sources.yml` | id・URL（転送先）・題名・種類（公式文書・公式ブログ・CHANGELOG・リリースノート・実践者・研究・報道）・発行者・言語・確認日・AI の利用の指定の確認（日付と結果）・写しの URL（Internet Archive。公式のページの改稿を見分ける手がかり。research/23）。ページごとの追加は `data/sources.d/<id>.yml`（§6.8） |
| `data/outdated-advice.yml` | id・古い助言・今どうするか・変わった時期と版・状態（撤回・置換・条件付き）・どの原理の回避策だったか・かつてなぜ正しかったか・自分の設定や記事で見つける方法・出典・確認日。名前と画面の変更の行は、名称の表の id を指し、時期をそこから引く |

- 前回の点検の版と日付も data/ に持つ（追跡する。§9.4）
- **名称と台帳の分担**：名前と画面の変更の事実（旧名・今の名前・変わった時期）は、数値ファイルの名称の表を正にする。台帳の行は名称の id を指して時期をそこから引く（二か所に持たない）。台帳の行は消さない。古い記事の手順が通じない読者の入口になるため（例：`/fork` は改名され、今の `/fork` は別の機能）

数値ファイルに持つ表の候補（目次の担当の提案。形は土台作りで決める。提案の全文は `planning/batches/step3/open-issues.md`）：

- 面の属性：面ごとの、手を動かす主体・触れられるもの・動く場所・読む設定・PC を閉じても続くか・できないこと（surfaces#3）
- モデルと effort：既定の effort の「モデル × 面」の表、ultrathink が上げる段と効く版と面、fast mode の対象と料金、退役の予定（models#2）
- プランと料金：プランの表、上位のモデルの枠、usage credits の失効の期間、API の料金、agent teams の倍率とその条件（cost#2）
- 大会の規則と AI の成績：§6.13 の形（contest#4）
- 名称と旧名：今の名前・旧名・変わった時期。名前と画面の変更の事実の正本で、用語索引の旧名の表示と、変更の記録と、台帳の時期に使う（start#5・cost#1）
- 台帳の行の「変わった時期」の材料は、changes の目次の notes と changes#3

### 9.2 確認日と期限

- 確認日と期限は、主張（数値ファイルの項目）とページの二段で持つ（research/20 の I2）。ページの期限は front matter の `volatility`、数値の期限は facts の項目ごとの volatility（既定は高）で決める
- 期限：volatility が低なら365日、中なら90日、高なら30日（requirements §7）
- **期限の日**：道具がページごとに、「ページの確認日＋ページの期限」と「各数値の確認日＋数値の期限」のうち早いものを計算する。ページの確認日は、`verified`（出典を読み直した日）と `checked`（点検で影響がないと確かめた日）の新しいほう。draft は verified がないので、数値の分だけで計算する（バッジは「未検証」。§8.5）
- verified は出典を読み直したときだけ進める。点検で影響がないと確かめただけなら checked を進める

### 9.3 期限切れの見せ方

- ブラウザが期限の日と今日を比べて注意書きを出す（§8.5）。CI でも期限切れを警告する（失敗にしない）

### 9.4 点検の手順（鮮度の点検の skill）

1. 前回の点検の版と日付（data/）より後の、Claude Code の CHANGELOG、Help Center と Claude Platform のリリースノート、Anthropic のニュースを読む（プランの改名のように、リリースノートに載らず Help Center と料金のページにだけ出る変更もある。research/22）
2. 出てくる語を、features の照合の語（英語）・ページの `tracks`・`aliases`・数値ファイルの id に照らし、影響のあるページと数値の一覧を出す
3. GitHub の Issue にする
4. 直す：日付・数値・名称の更新は、メインの判断と別の担当の検証と機械の検査で行う。**教材の推奨・安全の既定・古くなった助言の台帳の状態が変わる更新は、作者が承認する**（decisions 2026-11-03。点検ごとにまとめて頼む。§10.8）。安全の既定の正本は safety の安全の早見表の節（`default-safety-settings#by-stage`）で、点検の skill の手順にこの節を名指しする
5. 出典を読み直したページと数値は `verified` と数値の確認日を、影響がないと確かめたページは `checked` を進める。前回の点検の版と日付を data/ に書く
6. リンクの切れと転送も確かめる
7. 定期の実行は任意にする（requirements §7）

少なくとも手順の1・2・5は、第一波の公開の前に skill に仕上げる（§10.1）。月の点検の量と使用量は試作で見積もる（§10.7）。

### 9.5 外からの報告

- Issue のテンプレート（ページの誤り）を置き、種類に「情報が古い」を足し、ページの確認日と版の欄を足す。各ページの「このページの誤りを報告する」から、題名・URL・確認日を入れて開く。工程5の U3 で推奨（事例の記録の skill を作らない）を選んだら、ページや症状の提案のテンプレートも置く
- アクセスの解析は入れない（decisions 2026-11-03）

### 10.2 サブエージェントの使い方

| 役割 | 渡すもの | 返すもの |
| --- | --- | --- |
| 執筆 | 共通の手引きと型ごとの手引き（読む節を名指し）、手引きが写す設計書の節（名指し）、見本のページ（試作で決める。「構成をまねない」と添える）、用語集、catalog の項目、data の該当の項目、材料の調査資料の節、工程2の訂正（research/22〜28） | ページ、雛形、図、出典（`data/sources.d/<id>.yml`）、報告 |
| 検証（事実・出典・鮮度） | ページ、チェックリスト、data、出典、数値の提案のファイル | 指摘の一覧（主張と出典の照合、数値が数値ファイルを経由しているか、根拠の強さ、版に依存する記述の確認日、出典の文と長く一致する箇所） |
| 検証（雛形の動作） | 雛形と期待、チェックリスト | 静的な検査と実機の確認の結果 |
| 検証（分かりやすさ） | ページ、前提のページ、チェックリスト | 冒頭で用が足りるか、断片で読んで通じるか、判断があるか、薄い節 |
| 検証（図と描画） | ページ、図、描画の検査の結果 | 描いた結果の崩れ、図の内容 |
| 直し | 指摘の一覧 | 直したページ（書いた担当に戻す。research/20 の D2） |

- 書いた本人に採点させない。メインが書いた直しも、別の担当が確かめる（research/20 の F2）
- **段階の移り方**：執筆者が draft にする（verified なし。帯は「下書き・未検証」）→ 検証役が、指摘0件か、直しの差分を確かめ直して reviewed にし、verified を書く → メインが、検査0件と未解決の指摘がないことを確かめて done にする。「完成（done）」は、作者がすべてを確かめた意味ではない。サイトでの言い方は出典と AI 利用の方針のページに書き、作者の承認に入れる
- 執筆者が書いてよいのは、担当のページ・そのページの雛形（`snippets/<id>/`）・図（`docs/img/<id>/`）・出典のファイル（`data/sources.d/<id>.yml`）だけ。front matter で直してよいのは `sections`・`stage`（draft にする）・`updated`・`sources`（sources にある id）だけで、指示に名指しする。新しい数値は、提案のファイルに id と値と出典を書かせ、検証役がそれも照らす
- front matter のほかのキーの直しは、決まった形の YAML（id・キー・前・後・理由）で報告させ、メインが承認したら道具が当てる。共有のファイル（用語集・prh・data・catalog・手引き）への変更は、報告に「提案」として書き、メインがバッチの終わりにまとめて反映する
- 手引きとチェックリストは、format-and-operations F16 の3点で作る：今有効な規則だけを置き、決定のたびに書き換える。機械で検査できる規則に検査の名前を添える。チェックリストを検証の4つの観点に合わせる
- 役割ごとのモデルと effort の初めの案：執筆と事実の検証は上位のモデル、形の検査に近い検証は軽いモデル。試作で測って決める
- 検証役は、描画した結果を見る。担当の外への波及（並べ替えた後の「上の節」など）は、メインと道具の検査で見る（research/20 の D2）

### 10.3 バッチの回し方と再開

- ワークフローで、1ページずつ「執筆 → 検証 → 直し」を回す。同時に16〜20体まで（decisions 2026-11-03。規模の目安は 2026-11-04 に large にした）。作者のプランは Ultra。確認済みの口座には5時間の上限がない（週の上限はある。research/22・26）。作者の口座が確認済みかは、工程7の終わりの頼みで確かめる
- 共通の指示を1ファイルにし、担当には差分だけを渡す
- 報告の形を固定する：書いたファイル・直したこと・範囲を越えたこと・止められた操作・メインに判断してほしいこと・検査の結果・**確かめていないこと**・使用量
- 担当は報告をファイルに書いてから終える。止まったときは、報告のないものだけを同じ指示で流し直す。止まった担当の半端な変更は、既定では、その担当が書いたファイルだけを最後の commit に戻してから流し直す
- ワークフローのスクリプトは `.claude/workflows/`（置き場所は土台作りで決める。§10.5）に、起動したときの args は `state/` に残す
- ページの一覧は、必ずファイルから機械的に渡す
- 上限の窓の終わりには新しい段を起動しない。週の使用量でも、新しい段を起動しない条件を決める。ワークフローの「完了」は、報告のファイルと作業ツリーで確かめる

### 10.5 CLAUDE.md と縛り

**CLAUDE.md**：短くし、推測できないことだけを書く（教材が教える原則の実例にする）。例外を許さない規則は hooks と permissions で強制し、CLAUDE.md には理由と相談の基準だけを書く（requirements §6.7 の二層）。中身：何の教材か（1行）、再開するとき（`state/now.md` → `progress.md` → 設計書）、守ること（変わりやすい値を手で書かない、AI の利用を断るサイトを資料にしない、事実を記憶で書かない、書いた本人に採点させない（メインの直しも）、公開の約束・方針・ライセンスに関わる文は作者の承認を得てから出す）、道具の動かし方（`uv run` で動かす、commit の前に `tools/check_all.py` を流す）、並列の規則（担当のファイルだけ、共有ファイルは提案、生成と commit はメインだけ。担当が目印を埋めるときは、自分のページだけを書く `gen_site.py --page <id>` を使う）。

**hooks と permissions**（`.claude/settings.json`。decisions 2026-11-03）。縛るのは、機械的に判定でき、破ったときの害が大きい規則だけにする。

| # | 規則 | 仕組み | 止めたときに返すこと |
| --- | --- | --- | --- |
| H1 | AI の利用を断るサイト（atcoder.jp・codeforces.com と、sources で断る指定が見つかったドメイン）を開かない | 強制は permissions の deny（`WebFetch(domain:<ドメイン>)` と `WebFetch(domain:*.<ドメイン>)`）。PreToolUse の hook は理由の文と記録だけを受け持つ。Bash は、取得の道具（curl・wget など）の URL の引数のホストがそのドメインのときだけ、hook が照らして止める（ドメインの文字列では照らさない。grep や check_noai.py を止めないため）。sources で断るドメインがすべて deny にあるかを検査で確かめる（§8.6） | 「このサイトは AI の利用を断っている。別の一次資料を探すか、報告に書く」 |
| H2 | 生成物を手で書き換えない | 強制は permissions の deny（Edit を生成物のパスに）。deny と同じ範囲に当たる PreToolUse の hook を1つ置き、理由と代わりを返す | 「生成物は `gen_site.py` で作り直す」 |
| H3 | 担当（サブエージェント）は、読むだけの git（status・diff・log・show）のほかを使わない（巻き戻しの操作は、ほかの担当の変更を消すため）。gh の書き込みもしない | PreToolUse（Bash。入力の agent_id で担当を見分ける。research/28）。制作の印があるときだけ働く | 「担当の git は読むだけ。commit はメインが行う。変更は報告に書いて終える」 |
| H4 | API キーで課金されないようにする | 強制は `check_templates.py` の中の必須の確かめ（あれば止める。§8.7）。SessionStart の hook は、制作の印があるときに知らせるだけ | 「環境に API キーがあると、従量の課金になる」 |

- **制作にだけ要る縛り**（H3・H4）は、追跡しない印（`state/production`）があるときだけ働き、ないときは何もしないで終わる。読者がリポジトリを開いたときは動かない
- 止めた操作は、hook が `state/blocks.log` に1行ずつ記録する。バッチの報告に「止められた操作」の欄を足し（§10.3）、メインがバッチの終わりに blocks.log と照らして見直す

ユーザーの注意（「過去に入れた縛りによって柔軟な対応が出来ず不適切な対処をすることも多い」）に沿った決まり：

1. 縛るのは上の表のような、機械的に判定でき、害の大きい規則だけ。判断を含む規則（何が小さな直しか、など）は縛らず、CLAUDE.md と指示に任せる
2. 止めるときは、理由と「代わりにどうするか」を返す。止められた側が、別の道具で回り込むなどの回避策を探さないようにする
3. 当てはめる範囲を狭くする（部分一致で止めすぎない）
4. 止めた記録を残し、バッチの終わりに見直す。不適切な対処を招いた縛りは外すか直し、その例を制作の記録に書く
5. 読者がリポジトリを開いたときにも動くので、軽く安全にする（ネットワークを使わない、壊す操作をしない、標準のものだけで動く）。依存が欠けたときに止めるか通すかを規則ごとに決める。README には、どんな hooks と permissions が入っていて何をするか、読者の環境で何が動き何が動かないか、依存が欠けたときにどうなるかを書く

hooks がワークフローの担当でも動くかは文書に書かれていないので、土台作りで確かめる（research/28）。効かなかったときの代わりに、バッチの始めと終わりの HEAD を state/ に記録して比べ、動いていたら止めて調べる。入れた hooks と permissions も雛形として扱い、動作を確かめる。制作の権限モードと、`.claude/` への書き込みで確認が出るか（ワークフローのスクリプトの置き場所）は、土台作りで決める。

### 10.6 commit と push

- GitHub のリポジトリを作るまでは、ファイルを変えたらその都度 commit し、push はしない
- リポジトリを作った後は、メインが一人で直列に進める間は main に直接 commit・push し、作業ツリーで並列に直すようになったら、グループごとのブランチと pull request にする（decisions 2026-11-03）。並列のときは重なるファイルを表にして順序を決め、decisions.md の表に両方のブランチが行を足して衝突したら、main の行、次に自分の行の順で残す（research/20 の F3）
- commit の本文の終わりに、作業したセッションの記録の行を付ける

### 10.7 使用量と期間

- 実績：工程1は5つの担当で約126万トークン、工程2は14の担当で約680万トークン（progress.md）
- **概算**（工程5で示す）：kyopro-atlas の1ページ35〜45万トークンを当てると、第一波（125ページの場合）で約4,400万〜5,600万、必須で約6,100万〜7,800万、全部で約1.3億〜1.6億。一次資料の確認・雛形の実機の確認が加わり、検証の観点も多いので、これより重くなる見込みである
- 試作で型と役割ごとにトークン・道具の呼び出し・時間を測り、本制作の見込みを出す。月の点検の量と使用量も見積もる（いまの volatility では、全部を公開した後に月に約130ページが期限を迎える。R4-12）

### 10.8 ユーザーに確かめる場面

作者への頼みは次の5つにまとめる（decisions 2026-11-03「作者が目を通す範囲」「作者が試せる面」）。

1. 工程5（決定の提示）
2. 工程7の終わり：使用量と期間の見込み、方針の文の承認（§6.1 の8）、この環境で試せない確認（§8.7）、口座の状態の確認（§10.3）、第一波の上限と外す順（§2.3）を1回で
3. 鮮度の点検で、教材の推奨・安全の既定・台帳の状態が変わる更新（点検ごとにまとめて）
4. 使用量が見込みを大きく超えるとき
5. Zensical への移行（2027-05-05 までに移れないときの案も。§8.1）

- 試作と第一波の出来は確かめない。別の担当の検証と、工程10の「読者の課題から引く」で確かめる
- ページの追加・統合・削除は decisions.md に記録し、事後に一覧で知らせる。公開済みの URL を変えるときだけ確かめる
- 文書にない回避方法を見つけたときは、報告を作者に頼む（§6.11。工程5で確かめる）。これだけは見つけたときに頼む
- 5つは予定した試しと承認の頼みである。設計で決めていない点でユーザーの判断が要るものは、推測で埋めずにその都度聞き、decisions.md に記録する（requirements §11）
- この環境で試せない確認は、工程7の終わりまでに、第一波と残りの必須のページの分を目次から洗い出してまとめる。後から出たものは、本文に「未確認」と書き、次の点検の頼み（3）にまとめる

## 11. リスクと対策

| リスク | 対策 |
| --- | --- |
| 変わりやすい値が古くなる | 数値ファイル、確認日の二段、期限切れの表示、点検の手順（§9） |

| 実在の人物・団体についての誤り | 一次資料で確かめたことだけを書く。否定的な文脈で名指ししない（§6.12） |
| 形式の不揃いと後からの一括の直し（kyopro-atlas の最大の手戻り） | 規則を試作の前に決め、描画と書き方の検査を土台作りで作り、試作で0件にしてから本制作へ |
| 描画の崩れ | 描画の検査を最初から（§8.6） |
| 雛形が動かない・危ない・効いていないのに通る | 対照つきの実機の確認、作者の環境からの切り離し、無害な形、安全の雛形は確認を通ってから（§8.7） |
| 縛りが柔軟さを奪い、不適切な対処を招く | 縛る規則を絞り、代わりの手段を返し、止めた記録（blocks.log）を見直す（§10.5） |
| 担当の範囲の逸脱・共有ファイルの衝突 | 触ってよいキーとファイルを名指し、担当の git は読むだけ（H3）、生成はメインだけ（CLAUDE.md と指示。担当は `gen_site.py --page <id>`）、報告に「範囲を越えたこと」「止められた操作」 |
| 利用上限で一斉に止まる | 報告をファイルに書いてから終える、args を残す、窓の終わりと週の使用量で起動を止める（§10.3） |
| 並列のマージで生成物が衝突する | 毎回変わる値を生成物に入れない、マージの後に作り直す（§8.4） |
| API キーによる課金の事故 | `check_templates.py` が API キーと認証の変数を見つけたら止める（§8.7）、H4 の hook が制作の環境で知らせる |

| 下書きの公開で誤りが出る | 「下書き・未検証」の帯、安全の雛形は確認の後、早く検証する |
| 読者が大会の規則を誤って信じる | 確かめていない版は出さず、リンクだけ（§6.13） |

## 12. 決定の一覧（工程5で示す要約の元）

**確かめる点**（推奨の案を示して選んでもらう。design-review.md §3 の U1〜U5）

1. **第一波の範囲**（§2.3）：推奨は、核（入口・症状辞典の全ページ・台帳・評価と実験・判断と理解・日本語）と、症状のページの原因ごとの最初の必須の振り分け先（必須の先がない原因は第一波では準備中）と、安全の早見表と、それらの前提。第一波に入る推奨のページは必須に上げる。工程4の後の目次で135ページ（wave: 1 が62、前提で届くもの24、routes から49。必須119・推奨16〔症状のページ15とその前提1〕。推奨を上げると必須は177から193）。ほかの案は、核と前提だけ（88ページ）／振り分け先をすべて（206ページ）／核を必須の症状に絞る
2. **比例則の読み**（§3.1 の4）：推奨は、前提を「知らないと読めない」依存に限り、守りのページは関連に持たせて、ロードマップで任せる幅を広げるページの手前に並べる。ほかの案は、要件 §3.3 のとおり前提に持たせる（前提の鎖が深くなる）
3. **事例の記録の skill**（§10.1 の9）：推奨は作らず、作者が出会った困りごとは Issue のテンプレートで受ける
4. **文書にない回避方法を見つけたとき**（§6.11）：作者が報告し、済むまで該当の記述と雛形を公開しない
5. **公式で表記が割れている3語**（§6.2）：仮に plan モード・effort・許可ルール／確認ルール／拒否ルール（Claude Code の日本語版の多数派）

**決めたこと**（知らせる）

6. **構成**：23分野（§2.1）。型は concept（技法を含む）・feature・symptom・comparison・recipe・judgment・ledger・guide・hub。本体を生成するページも型を持つ。全ページで必ず置くのは front matter と冒頭の要点だけ
7. **レベルと分類**：委任の段階の5段階。軸は分野・レベル・優先度・面・原理・Claude 側の原因・人の側の落とし穴・場面・サイン・前提と関連・振り分け先・追跡・古い助言・変わりやすさ。語彙は schema/site.yml の1か所
8. **キーの台帳**：キーごとに誰が書くか・どこに写るか・書式を決めた。症状のページの振り分け先は routes に持ち、段階と優先度の規則を当てない。執筆者が書くキーは sections・stage・updated・sources だけ（出典は sources.d に足す）。verified は reviewed 以降に検証役か道具が書く。機能の属性はページに持たず、数値ファイルに持つ
9. **段階と「完成」の意味**：draft（下書き・未検証）→ reviewed（検証役が、指摘0件か直しの差分を確かめ直した）→ done（メインが検査0件と未解決の指摘がないことを確かめた）。「完成」は作者がすべてを確かめた意味ではない。サイトでの言い方は方針のページに書き、作者が承認する
10. **粒度と境界**：1ページ＝名前・症状・やりたいことで引かれる単位。面ごとの違いはタブ。症状は1症状1ページで振り分けが本体（消された直後・漏れた直後の初動だけは症状のページが持つ）。境界の表（§4.2）
11. **目次の作り方**：先に全候補の id の一覧（registry）を作り、分野の担当が並列に詳細を書き、`check_catalog.py` で検査する。骨格の後は front matter が正
12. **編集方針**：判断を教える、冒頭で用が足りる、1ページで完結、面はタブ、変わりやすい値は道具が書く、写さない、守れない約束を書かない、根拠の強さ（強・中・弱・類推・推論）、用語は公式の日本語版の多数派、書かないもの（§6.11）、第三者（§6.12）、大会の規則（§6.13）
13. **横断のページと表示**：トップ・引き方・原理・二つの軸・地図・ロードマップ・逆引き・用語索引・用語集・変更の記録（年表）・知識マップ・出典と AI 利用の方針・台帳・比較表・一覧・llms.txt。全ページの冒頭とフッターに非公式の文、フッターに「© 2026 yuukougun」とライセンス、Anthropic のロゴと意匠をまねない（方針のページと冒頭とフッターの文は作者が承認する）。フォントと Mermaid を外のサイトから読まない
14. **技術**：Material 9.8 系と MkDocs 1.6.1 を固定、Python 3.12（道具は uv run）、プラグインは search だけ、Zensical の試験ビルドと評価の基準、KaTeX なし。道具は読む・作る・検査の層。生成物はコミットして `--check`、毎回変わる値は入れない。骨格はビルドから外し、未公開のページは生成物に載せず、本文からは目印で指す
15. **数値と出典と台帳**：data/facts.yml・sources.yml（と sources.d）・outdated-advice.yml。本文には目印の間に道具が書く。名前と画面の変更は名称の表を正にし、台帳の行は消さない
16. **鮮度**：確認日と期限は主張とページの二段（365・90・30日。数値は項目ごと）。道具が期限の日を出し、ブラウザが今日と比べる。点検の skill の手順の1・2・5は第一波の公開の前に作る。作者が承認するのは、教材の推奨・安全の既定・古くなった助言の台帳の状態が変わる更新だけ
17. **雛形**：静的な検査は CI（スキーマの写しと許す一覧）、実機の確認は手元で雛形なしの対照と比べ、作者の環境から切り離す。Claude Code 2.1.314 以上。確認の形は種類ごと。安全の雛形は確認を通ってから載せる。この環境で試せない雛形は既定では載せず、条件と概念だけを書く
18. **制作の進め方と記録**：執筆 → 検証（4つの観点）→ 直しを、ワークフローで同時に16〜20体まで。報告の固定の形と「確かめていないこと」、報告のないものだけを流し直す再開。役割ごとのモデルと effort は試作で決める。記録は decisions・design の変更履歴・progress・state（追跡外）・batches・制作の記録
19. **使用量の概算**：第一波（135ページ）約4,700万〜6,100万、必須（193ページ）約6,800万〜8,700万、全部（357ページ）約1.2億〜1.6億トークン（kyopro-atlas の1ページの値を当てた見当で、これより重くなる見込み）。試作で測って直す
20. **縛り**：CLAUDE.md は短く。H1〜H4 を5つの決まりで入れる。強制は deny（H1・H2）。H3 と H1 の Bash は hook が止める。hook は理由と記録も受け持つ。担当の git は読むだけ。制作にだけ要る縛りは制作の印があるときだけ働く（ワークフローの担当で効くかは土台作りで確かめる）
21. **工程**：骨格を土台作りの終わりに、data の初版を試作の前に置く。本制作は第一波（終わりは第一波のページがすべて draft 以上）と残りの必須（終わりは必須のページがすべて draft 以上）に分け、初版の公開は全体の検証の後（工程11）。推奨は初版の後に足す。描画と書き方の検査を試作で0件にしてから本制作へ。全体の検証に「読者の課題から引く」
22. **ユーザーに確かめる場面**：5つ（工程5・工程7の終わり・点検で推奨などが変わる更新・使用量の大きな超過・Zensical への移行）にまとめる。試作と第一波の出来は確かめない。ページの追加・統合・削除は記録して事後に知らせる（公開済みの URL を変えるときだけ確かめる）。文書にない回避方法を見つけたときの報告だけは、見つけたときに頼む
