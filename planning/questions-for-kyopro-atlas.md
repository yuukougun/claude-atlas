## 前置き

このメッセージは、新しく作り始めた教材 **claude-atlas** の制作セッション（作者 yuukougun の手元の Claude Code）から送っている。作者の指示で、作者を通さずに直接聞いている。

**claude-atlas とは**：Claude 全般（claude.ai アプリ・Claude Code・モデルと effort・頼み方・API と SDK の概念・安全とデータ・組織での運用）を使いこなすための、**辞書として引く**日本語の教材である。読者は Claude をかなり使っているが使いこなせていない人で、うまくいかなかった場面（「指示が守られない」「完了と言うが終わっていない」など）から逆引きでページに着き、冒頭の要点で用が足りるようにする。機能の紹介より判断（なぜうまくいかないか、どう確かめるか、どこまで任せるか）を重く見る。

**kyopro-atlas と同じところ**：Material for MkDocs → GitHub Pages。ページの front matter から逆引き辞典・用語索引・知識マップ・ロードマップ・`llms.txt` を生成する。catalog → 骨格 → 本文 → 検証の段階を持つ。生成と検査は独立スクリプト。textlint と prh。執筆と検証をサブエージェントに分け、書いた本人に採点させない。claude.ai の Projects から教材を引かせる。

**違うところ**：

- 内容が週〜月単位で古くなる（機能・既定値・料金・名称。Claude Code は2026年に約235版）。確認日と版のメタデータ、数値を集めたファイル、点検の手順を最初から持つ
- 事実の確かめ方が、公式文書・CHANGELOG・リリースノートと、settings.json・hook・skill・subagent の定義・CLAUDE.md の例を実際に動かすことになる。数式とコード片の検査はほぼない
- 読者は不特定多数（public）。進捗チェックは入れない
- 約370ページの候補があり、初版は「必須」のページから公開する
- 制作そのもの（CLAUDE.md・skills・hooks・サブエージェントの分担）が、教材の教える「確かめる・縛る・握る」の実例で、後で教材の素材にする
- claude.ai では、問題の解説ではなく、Claude を使っていて出会った困りごとの相談に使う

**今の段階**：リポジトリを作ったばかり（git init と planning/ だけ）で、設計やページ作りの前に「どんな形式と運用で作るか」を決めている。kyopro-atlas のリポジトリ（作者の手元の clone）の planning/（requirements・design・design-review・interfaces・decisions・progress・style-guide・catalog/README・checklists・batches の主なもの）、tools/README.md、schema、CLAUDE.md、claude/、.claude/skills/、mkdocs.yml、CI の設定と、git の履歴はひととおり読んだ。だから、ファイルに書かれていることは聞かない。聞きたいのは、**経緯・理由・うまくいったこと・失敗したこと・今ならどうするか**である。

## お願い

- **ファイルは変更せず、回答だけを返信してほしい。** kyopro-atlas と claude-atlas のどちらのファイルも変えず、commit・push・Issue・pull request の操作もしないでほしい。思い出すためにリポジトリのファイルや履歴を読むのは構わない
- 問いの番号を付けて答えてほしい。全部に答えなくてよい。特に答えてほしいのは ★ の付いた問いである。長くなるなら、何回かに分けて返信してよい
- 覚えていないこと・分からないことは、そう書いてほしい（推測で埋めない）。答えが記録（ファイルや履歴）に基づくのか、記憶か、今の意見かが分かるように書いてもらえると助かる
- 意見や勧めには理由を添えてほしい

## A. 全体の進め方と規模

**A1 ★** 要件の確定から全353ページを reviewed にするまでが約40時間（2026-10-21〜10-22）で、その後 10-29 の調査で Issue が #4〜#77 の74件見つかった（表示の崩れ、平文の数式や節の並びの不揃い、入口や引く仕組みの不足など）。この調査は誰がどうやって行ったのか（作者が読んだのか、エージェントの監査か）。工程10の全体の検証（2巡）でこれらを拾えなかったのはなぜだと思うか。今なら、どの工程で何を足して、先に拾うか。

**A2 ★** 1日半で本文と検証まで進めたことを、今どう見ているか。急いだことで生じた手戻り（後からの一括の直しなど）と、それでも先に全体を作ってよかった点を知りたい。

**A3** 工程の順（質問 → 調査 → 設計 → 見直し → 決定の提示 → 土台 → 試作 → 骨格 → 本文 → 全体の検証 → Issue の対応）で、入れ替えたい・まとめたい・増やしたいところはあるか。特に、試作の9ページの直後に173ページのバッチ（b1）へ進んだことについて。

**A4** 作者に確かめた場面のうち、確かめてよかったもの、確かめずに進めて後で困ったもの、逆に聞かなくてよかったものはあるか。

## B. 目次・骨格・front matter

**B1 ★** 骨格（8a）の後に catalog を凍結し、front matter と台帳を正にした。凍結の後に、ページの追加・統合や項目の変更で困ったことはあったか。claude-atlas の調査資料には「catalog をページの一覧と front matter の唯一の正本にし、雛形はそこから生成する」という案もある。今始めるならどちらにするか、理由も添えて。

**B2 ★** front matter のキーで、作ったがほとんど使われなかったもの・要らなかったもの、後から足して効いたもの、最初からあればよかったものはどれか。claude-atlas は kyopro-atlas のキーに十数個（`surfaces`・`principle`・`prevents`・`pitfalls`・`scenes`・`enforcement`・`maturity`・`volatility`・`verified`・`verified_with`・`tracks`・`outdated_advice`・`sources` など）を足す案になっている。キーを増やすときに気をつけること（骨格づくり・検査・執筆者の負担など）があれば知りたい。

**B3** summary と signs の規則、要点の囲みを全ページ必須にしたこと、stub を「準備中」の印付きで公開したことは、実際にうまく働いたか。読者の側と、claude.ai で引く Claude の側の両方について。

**B4** sections に level を持たせる構造（節のレベル）は、作ってみて手間に見合ったか。

## C. 道具（生成と検査）

**C1 ★** tools/ を claude-atlas に写して直すか、作り直すかで迷っている。`gen_site.py`・`check_pages.py`・`make_skeleton.py`・`render_pages.py` などについて、どこが汎用で、どこが kyopro-atlas に絡み合っているか。今の作りで気に入らないところ（大きくなりすぎた、試験がしにくいなど）や、作り直すならこう分ける、という考えがあれば。

**C2** 生成物をコミットして `--check` で鮮度を確かめる方式と、手書きのページの `gen:begin`〜`gen:end` の目印の方式は、運用してみてどうだったか（マージでの衝突、手書きの部分との境目の事故など）。

**C3** 検査は途中で足していった（書き方の検査や `render_pages.py` は工程11）。振り返って、最初から作っておけばよかった検査はどれか。逆に、作ったが手間に見合わなかった検査はあるか。

**C4 ★** 問題の台帳と `fix_problems.py`（本文の問題の行を台帳から作り直す）のように、本文の値を1か所のデータから機械的に作る方式は、うまくいったか。claude-atlas では、料金・上限・既定値などを数値ファイル（例：`data/facts.yml`）に集め、出典と確認日を付けて本文から参照したい。参照の仕方として、(a) 道具が本文に値を書き込む（`fix_problems` や `gen` の目印のような形）、(b) mkdocs-macros などで本文には変数名だけを書く、(c) 本文には値を書かず数値の一覧のページへリンクする、などが考えられる。kyopro-atlas の経験から、どれを勧めるか。claude.ai のスレッドがリポジトリの Markdown をそのまま読む点も踏まえて。

**C5** コード片の検査（snippets と期待の設定、CI の gcc のコンテナ、変わったものだけと週1回すべて）の運用で学んだことは何か。claude-atlas では、本文に載せる settings.json・hook・skill・subagent の定義・CLAUDE.md の例を、可能な限り実際に動かして確かめ、確かめた版を記録する。同じ形（雛形のファイル＋期待の設定＋検査のスクリプト）でやるとしたら、気をつける点は。

## D. サブエージェントとバッチ

**D1 ★** 並列の数（同時に最大20、ワークフローは1本16まで）は何を根拠に決め、実際の使い心地はどうだったか。b1 で利用上限が近づいて途中で止めたとき、困ったことは何か。再開をもっと楽にするために、今ならどうするか。

**D5** 「ページの一覧は必ずファイルから機械的に渡す」のほかに、バッチを回して分かった、執筆者・検証役への指示の書き方の教訓はあるか。

**D6** 使用量の見込み（1ページ約35〜45万トークン、全体で約1.2〜1.5億トークン）と実際の差はどうだったか。何が一番トークンを使ったか。

## I. claude-atlas への助言

**I1 ★** kyopro-atlas の形のうち、claude-atlas に「そのまま持っていくべきもの」と「持っていかないほうがよいもの」を、それぞれ3つまで挙げるなら何か。理由も添えて。

**I2 ★** claude-atlas は内容が速く古くなる。kyopro-atlas の仕組みで、鮮度の管理に足りないと思うところはどこか。確認日と版のメタデータ、数値ファイル、点検の手順を入れるときに、最初に決めておくべきことは何か。

**I3** claude-atlas では、制作の記録を後で教材の素材（用途別レシピ・注釈付きのセッション記録）にしたい。kyopro-atlas の制作で、素材として残しておけばよかった記録はあるか（例：うまくいかなかった指示とその直し方、検証の指摘の実例）。

**I4** ほかに、聞かれていないが伝えておきたいことがあれば。
